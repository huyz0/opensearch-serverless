# OpenSearch compatibility

The goal is real compatibility with OpenSearch, scoped to the serverless capability: a client that works against an OpenSearch serverless deployment works against this one, for every endpoint and parameter in scope.

## Scope

- **In scope:** the REST endpoints, query DSL, mappings and response shapes a serverless search and indexing deployment serves: index lifecycle, bulk and document APIs, `_search` and its DSL, aggregations, mappings and settings that apply to serverless indices.
- **Out of scope:** cluster administration a serverless deployment does not expose (node, shard allocation and snapshot management APIs), and plugins not yet ported.
- Each endpoint and parameter is listed in a compatibility matrix with one of: **matches**, **differs** (with the difference and why), or **refused** (with the error returned). Unknown parameters fail explicitly; they are never ignored silently.

## How compatibility is tested

- **Golden fixtures** recorded from stock OpenSearch at the version the Java shell builds on (3.10.0, built from upstream's `3.10` branch until it is released): requests, the recorded responses, and normalisation rules for fields that legitimately vary (took, generated ids and uuids). They live in `fixtures/compat/<suite>/`; the format and the recording procedure are in [fixtures/compat/README.md](../fixtures/compat/README.md).
- The harness is `oss-compat`: a bounded loader, the normaliser, a comparator that reports each difference with its JSON pointer and both values, and a runner that replays fixtures against anything implementing its `Target` trait.
- The **compatibility suite** runs every fixture against `oss-node` on the in-process S3 emulator and compares the normalised responses. It is a core check: part of the gate once the first REST endpoint exists, and a stage gate in the [roadmap](roadmap.md). Until then the fixtures check themselves: they load, every rule matches its recording, and they replay cleanly against their own recordings with every normalised field changed.
- OpenSearch's own REST YAML suites for in-scope APIs are run the same way, with skips listed and justified.
- Recording fixtures needs a running OpenSearch, so it is a separate, occasional step. Checking them needs nothing but this repository.

Invariant I-13 in [invariants.md](invariants.md) holds the suite to this: `crates/compat/tests/node_search.rs` replays every `_search` step of `fixtures/compat/search/` against a reader node over the shell's blobs of the same indices ([fixtures/compat-blobs/](../fixtures/compat-blobs/README.md)).

## `_count` on a reader node

`GET|POST /{index}/_count` with a body of `query` alone, or none, answers `count` (the exact total of that query's search) and the search's `_shards`, over one shard or several ([count-api](specs/count-api/SPEC.md)). The URL parameter `min_score` counts only matches scoring at least it (`-1` is none), and `q` with `df`, `default_operator`, `analyzer`, `analyze_wildcard` and `lenient` counts a Lucene query string when the body gives no query ([uri-query](specs/uri-query/SPEC.md)). The wildcard options `allow_no_indices`, `ignore_throttled` and `expand_wildcards=open` are accepted and change nothing, here and on `_search` ([count-pit-url-params](specs/count-pit-url-params/SPEC.md)). **Refused:** `/_count` without an index, every URL parameter but `min_score`, the `q` family, `routing`, `preference`, `ignore_unavailable` and those (`terminate_after` and the rest), and any body key other than `query`, as 400 `illegal_argument_exception` where OpenSearch answers a `parsing_exception` for an unknown key.

## `q` on `_search` and `_count`

`q` with `df`, `default_operator`, `analyzer`, `analyze_wildcard` and `lenient` on `_search` and `_count` builds one `query_string` query as stock builds it from the URL; on `_search` it replaces a query in the body, on `_count` a query in the body wins ([uri-query](specs/uri-query/SPEC.md)). **Differs**: `analyze_wildcard=true` and an analyzer other than `standard` are refused as the `query_string` query refuses them; a `_count` with `q` and a body with no query counts `q`, where stock ignores `q` whenever there is a body. `_msearch`, `_search/template` and `_validate/query` still refuse the parameter.

## `_render/template` and `_search/template` on a reader node

`GET|POST /_render/template` and `GET|POST [/{index}]/_search/template` take an inline mustache `source` (or `inline`, `template`) with `params` and `explain`, render it with a port of mustache.java 0.9.14 as lang-mustache runs it, and answer `{"template_output":...}` or the search response ([search-template-api](specs/search-template-api/SPEC.md)). Rendering is checked against the Java engine byte for byte, error messages included. A request may name a stored template instead: `id` in the body or `/_render/template/{id}`, a mustache script put with `PUT /_scripts/{id}`, read from the stored-script set (one marker GET on a warm node; the later of `id` and a source in one body wins, the path id wins over the body; [stored-search-templates](specs/stored-search-templates/SPEC.md)). A missing id answers 404 `resource_not_found_exception`. **Refused:** a stored script of another language (**Differs**: stock runs it in its own engine), `profile`, a `search_pipeline`, partials and extend sections, `_search/template` without an index, and rendered text over 1 MiB or nested over 512 levels. **Differs:** a template that fails while running answers 500 `general_script_exception` with this node's text, not the Java reflection error's.

## `_rank_eval` on a reader node

`GET|POST /{index}/_rank_eval` evaluates rated requests, given inline or by template (a template is written in the body or is a stored script, `"template":{"id":..}`), with the `precision`, `recall`, `mean_reciprocal_rank`, `dcg` and `expected_reciprocal_rank` metrics, and answers `metric_score`, `details` and `failures` ([rank-eval-api](specs/rank-eval-api/SPEC.md)). **Refused:** `summary_fields`, a rated request with a `sort`, no index or a list, pattern or `_all`, and every URL parameter. **Differs:** the requests run one at a time; a rated request naming a template that does not exist answers 400, not 500; the response shape follows the Java source and has not been recorded from a running OpenSearch.

## `_validate/query` on a reader node

`GET|POST /{index}/_validate/query` with a body of `query` alone, or none, answers `valid` and `_shards` of `total` 1 (stock validates on one shard of each index) ([validate-query-api](specs/validate-query-api/SPEC.md)). A body that does not parse and a query that fails to build answer 200 `valid: false`, as OpenSearch does. **Refused:** `/_validate/query` without an index, the URL parameters `explain`, `rewrite`, `all_shards` and the indices options, and a query this node does not support yet (400, never `valid: false`). **Serves:** `q`, `df`, `default_operator`, `analyzer` and `lenient` with no body, as the `query_string` query a search builds from them (a body's query wins; `analyze_wildcard` is refused as in a search). **Differs:** a body key that parses as a search default (`{"size":10}`) is valid here and invalid in OpenSearch; the index must be one concrete name.

## `_field_caps` on a reader node

`GET|POST /{index}/_field_caps?fields=` over comma-separated concrete index names answers each mapped field (multi-fields included) by type with `searchable`, `aggregatable`, and `indices` or `non_*_indices` where the indices differ ([field-caps-api](specs/field-caps-api/SPEC.md)). **Refused:** `/_field_caps` without an index, a wildcard or `_all` as the index, an alias of several indexes (501), and the parameters `include_unmapped`, `filters`, `types`, `index_filter` and the `fields` body key. **Differs:** the metadata fields (`_id`, `_index`, `_source` and the rest) are not listed, so `fields=*` answers fewer entries than OpenSearch. An alias of one index is read as that index and the answer names the index ([search-on-alias](specs/search-on-alias/SPEC.md)).

## `_msearch` on a reader node

`GET|POST /_msearch/template` and `/{index}/_msearch/template` take a template request on each body line and answer as `_msearch` does ([msearch-template](specs/msearch-template/SPEC.md)); the refusals of `_search/template` and `_msearch` both apply.

`GET|POST /_msearch` and `/{index}/_msearch` run the searches of an NDJSON body, header line then body line, each as `_search` runs it, and answer `{"responses":[...],"took":N}` with each item's `"status"` ([msearch-api](specs/msearch-api/SPEC.md)). A failing item answers its own error body and the others run. **Serves** the header keys `index`, `routing`, `preference`, `ignore_unavailable`, and without effect `search_type` (`query_then_fetch`), `request_cache`, `ccs_minimize_roundtrips`, `allow_no_indices`, `max_concurrent_shard_requests`, `pre_filter_shard_size`, `ignore_throttled` and `expand_wildcards` of `open`; and the URL parameters `rest_total_hits_as_int`, and without effect `search_type`, `max_concurrent_searches`, `max_concurrent_shard_requests`, `pre_filter_shard_size` and `ccs_minimize_roundtrips` ([msearch-tuning-params](specs/msearch-tuning-params/SPEC.md)). **Refused** (the item answers 400 `illegal_argument_exception`): other header keys, an `index` that is an array, a pattern or `_all`, and an item with no index; every other URL parameter is refused (`typed_keys` among them). **Differs:** the answer streams, so `took` is the last key and a fault after the first item is an item, not a 400; a malformed header or body line fails its item and the later lines run, where OpenSearch fails the request; searches run one at a time.

## `_analyze` on a reader node

`GET|POST /_analyze` and `/{index}/_analyze` with `text` (a string or an array) and `analyzer` of `standard` (the default) or `keyword` answer `tokens` with `token`, `start_offset`, `end_offset`, `type`, `position` and `positionLength` where above 1, carrying positions and offsets across an array as the Java does (position gap 100 with an index, 0 without; offset gap 1) ([analyze-api](specs/analyze-api/SPEC.md)). An index in the path must exist. **Refused** (400 `illegal_argument_exception`): `field`, `tokenizer`, `filter`, `char_filter`, `normalizer`, `explain`, `attributes`, other keys, analyzers other than `standard` and `keyword` (the built-ins this node lacks as "not supported"; others as `failed to find [global ]analyzer`), and every URL parameter. **Differs:** the token limit is `index.analyze.max_token_count`'s default of 10,000, not settable, and answers the Java's `IllegalStateException` as a 500 read from `ExceptionsHelper.status`; an index's own analyzers do not exist here, so with an index only the gap changes.

**Differs:**

| What | OpenSearch | This node | Why |
|---|---|---|---|
| Content after the body's object (`{"size":1} {}`) | `parsing_exception` "Unexpected token [START_OBJECT] found after the main object." | `json_parse_exception` "Unexpected character ... after the root value" | the streaming tokenizer stops at the first root value |
| A `term` or `match` value longer than the 1 MiB a body's recording holds | searched | 400 | the recording is bounded (ADR 0004) |
| A keyword-sorted window larger than the request-body pool holds at 32 KiB a value (the longest term) | answered | 429 `circuit_breaking_exception` | hits are reserved before the search runs (ADR 0004) |
| A newer commit of an open index | seen at the next refresh | seen only once the node is told of it | the node never polls the object store for an index (I-4) |
| `"size":0` with aggregations | `"terminated_early":true` when the shard's hit count needs no collecting (a match-all or a lone term) or passes 10,000 | no `terminated_early` | the flag comes from concurrent segment search's count collector; the hits and aggregations are the same |
| A metric over a shard of many segments | its concurrent segment search may split the segments into slices and reduce their results, which can change a sum's last bits | one pass over every segment in order, as without concurrent search | slices depend on the node's CPU count, so OpenSearch's own answer varies between nodes |
| The acknowledgement of `PUT /{index}` | `acknowledged`, `shards_acknowledged`, `index` | the same plus `shards` | the shell's create reports the shard count; the compat replay removes it |
| A `precision_threshold` (or `rehash`) number outside a long | `x_content_parse_exception` caused by Jackson's `input_coercion_exception`, its reason ending in the number's byte offset | the same exception and reason, with one `input_coercion_exception` cause whose reason has no offset | the tokenizer does not keep Jackson's source location |
| Two sibling aggregations of one name | `json_parse_exception`: Jackson refuses the duplicate key | `illegal_argument_exception` "Two sibling aggregations cannot have the same name" | the tokenizer does not detect duplicate keys; the message is the one `AggregatorFactories.Builder` gives |
| A percent or rank value written as a hexadecimal string (`"0x1p3"`) | read as `Double.parseDouble` reads it | `number_format_exception` | rare enough not to port Java's hexadecimal float grammar |
| A `percents` or `values` element that is `null`, a boolean, an object or an array | `x_content_parse_exception` caused by Jackson's exception, its reason ending in the byte offset | the same exception with an `input_coercion_exception` cause whose reason has no offset | the tokenizer does not keep Jackson's source location |
| A NaN or infinite `percentile_ranks` value | `illegal_argument_exception` "Invalid value: NaN" once the shards have searched | the same error, before searching | `MergingDigest.cdf` refuses it while the response is written; refusing it first saves the search and gives the same body, unless a shard would have failed first |
| A `tdigest` compression of NaN, infinity or above 10,000 | served up to what the heap holds; NaN fails the shard with `arithmetic_exception` "/ by zero", and infinity exhausts the heap | refused as not supported | a digest's arrays, and the sort keys lucene-aggs keeps per thread after it, grow with the compression; up to 10,000 they are reserved before searching, about 8 MB (ADR 0004) |
| `took` | the shard's time | the node's time, parse to last hit chosen | normalised in the fixtures |


## `_delete_by_query` on a writer node

`POST /{index}/_delete_by_query` with a body holding `query` walks the index's shards through the reader's search, sorted by `_seq_no`, and deletes each hit through the `_bulk` path conditional on the hit's `_seq_no` and `_primary_term`. The answer counts `total`, `deleted`, `batches`, `version_conflicts` and `noops`. A document rewritten after the search is a version conflict: with `conflicts=abort` (the default) the answer is 409 with the id in `failures`, with `conflicts=proceed` it is counted and the walk goes on. `max_docs`, `refresh`, `scroll_size` and `timeout` are honoured ([node-delete-by-query](specs/node-delete-by-query/SPEC.md), [coordinator-by-query](specs/coordinator-by-query/SPEC.md), [by-query-search](specs/by-query-search/SPEC.md)). **Refused** (400): `wait_for_completion=false`, `slices` other than 1, `requests_per_second` other than -1, a body without `query` or that is not JSON. **Differs:** a document with a custom `_routing` is not found by its default shard, and `_update_by_query` does not exist yet.

## `realtime=false` on a forwarded get

A get of a shard another node owns is forwarded to its owner. The Java `ForwardedGetRequest` has no `realtime` field and its owner always reads realtime, and a Java peer refuses a message it did not read whole, so a `realtime=false` get cannot be sent to one with a new field. A node of this project publishes the build version `oss-rust/<version>` in its lease; to a peer whose lease says that, a get that is not realtime carries one trailing byte and is answered from refreshed data only. To any other peer the get is sent in the Java layout, and the owner reads realtime: the answer may then include a write not yet refreshed. A get served on the node that owns the shard honours `realtime` either way.

## The security configuration API (`serverless.security.enabled`)

**Matches** (the replay of `fixtures/compat/security/`, recorded from the stock security plugin 3.10.0): `GET`, `PUT` and `DELETE` of one document under `/_plugins/_security/api/{roles,rolesmapping,internalusers,tenants,actiongroups}/{name}`: the acknowledgements, the `Invalid configuration` and `Wrong datatype` bodies, a mapping for an absent role, and an internal user's hash never returned ([security-config](specs/security-config/SPEC.md)).

**Differs**: the list form (`GET` with no name), `PATCH`, `hidden` and `reserved` documents, and the `securityconfig` API are not served. A key unknown to a nested entry is a 400 `Invalid configuration` where the plugin answers 500 with a Jackson message. A document kind holds at most 1,000 entries. The password policy is a minimum of 8 characters. Configuration lives in the object store, not an index: a change reaches another node within the refresh interval once authentication reads it ([ADR 0043](adr/0043-security-configuration-as-document-sets.md)).

**Authentication** (`serverless.security.enabled`, [security-authn](specs/security-authn/SPEC.md)): HTTP basic against the stored internal users and one static administrator from `OSS_SECURITY_ADMIN_USER` and `OSS_SECURITY_ADMIN_HASH`. A request without valid credentials is `401 Unauthorized` (text), a non-administrator on the management API is the recorded 403, and `GET /_plugins/_security/authinfo` answers the recorded shape. **Differs**: a change reaches another node within `OSS_SECURITY_REFRESH_MS` (default 10 s, at least 1 s); the node answers 503 when it cannot read the configuration for three intervals; more than 5 wrong passwords for a user in 10 s are `429`; `authinfo` carries `remote_address: null` and the tenants of the user's name (an administrator also the global, admin and stored ones); client certificates, JWT, LDAP and the other authentication backends are not served. 

**Authorization** ([security-authz](specs/security-authz/SPEC.md), [ADR 0051](adr/0051-authorization-at-the-route-by-action-table.md)): roles' cluster and index permissions, action groups (built-in and stored) and the plugin's wildcard rule decide each request, answered with the recorded 403 `security_exception` naming the action. **Differs** (stricter than the plugin, never looser except as noted): names are matched as written, so an alias or a wildcard that would resolve to allowed indices only is refused unless the user is granted the name, and an alias made onto an index reaches it for whoever holds the alias's name; `_bulk`, `_msearch`, `_mget`, `_search` without an index, `_delete_by_query`, aliases, templates, ingest pipelines, snapshots, `_cat`, anything that lists index names and every plugin route need `all_access`; a `terms` lookup in a search body that reads another index is not checked, as in the plugin; tenants, document-level and field-level security and `/regex/` patterns are not enforced.

## Snapshots, index templates and ingest pipelines

**Stored scripts** ([stored-script-routes](specs/stored-script-routes/SPEC.md)): `PUT|POST|GET|DELETE /_scripts/{id}` over the `scripts/` document set a Java node shares, a body `{"script":{"lang","source","options"}}` with `lang` `painless`, `mustache` or `expression`; a `source` may be a string or an object, which is stored as its compact JSON text with `options.content_type` `application/json; charset=UTF-8`. **Refused:** a script context in the path (`/_scripts/{id}/{context}`, 501), an id beginning with `_` (501), an unknown `lang`, an empty or over 65,535-byte source, and options other than `content_type` (400). **Differs:** a script is stored without being compiled, so one that does not compile is refused where it is first used; no script is run yet. The routes need `all_access`.

**Settings update** ([settings-update-route](specs/settings-update-route/SPEC.md)): `PUT /{index}/_settings`, a flat or nested body, with `preserve_existing=true` and a null to remove a key. Each change bumps the index's settings version. **Refused:** `index.number_of_shards`, a replica count other than 0, `index.search.default_pipeline` (accepted when search pipelines are on), `index.serverless.shard_mode`, static settings (including the bucket and cost keys), and a key a create does not accept (400 unknown). **Write blocks** ([index-blocks](specs/index-blocks/SPEC.md)): `index.blocks.write`, `index.blocks.read_only` and `index.blocks.read_only_allow_delete` (`true` or `false`) refuse a bulk's index, create and delete items with 403 `cluster_block_exception` (a delete passes under the allow-delete block). **Read and metadata blocks** ([index-blocks-read-metadata](specs/index-blocks-read-metadata/SPEC.md)): `index.blocks.read` makes a reader refuse to open the index (403 `cluster_block_exception`), taking effect when a reader next opens it and lifting at once; `index.blocks.metadata` refuses a settings update that sets anything but `index.blocks.*` keys, an alias add or remove naming the index, and the index's deletion (403; [index-metadata-block-aliases-delete](specs/index-metadata-block-aliases-delete/SPEC.md)). **Differs:** a realtime get on a writer node is not stopped by the read block. **Result window** ([index-max-result-window](specs/index-max-result-window/SPEC.md)): `index.max_result_window`, a whole number from 1 to 10,000, lowers the window a search may ask for (`from + size`); above 10,000 is refused 400, since a search's hits are held in memory. A reader takes the value when it opens the shard, so a reader that already holds the index open keeps the old one until it next opens it. **Differs:** a block takes effect when the writer next confirms the index, within one confirmation window (`OSS_INDEX_CONFIRM_MS`, 5 s by default), not instantly, and the owner of a forwarded bulk applies the block too;  The route needs `all_access`.

**Aliases** ([alias-routes](specs/alias-routes/SPEC.md)): `PUT|POST /{index}/_alias/{name}` (with `is_write_index`), `DELETE /{index}/_alias/{name}`, `POST /_aliases` with `add` and `remove` actions (`index` or `indices`, `alias` or `aliases`), `GET|HEAD /_alias/{name}`, `GET /{index}/_alias` and `GET /{index}/_alias/{name}`. Every name is literal and a change costs requests in proportion to the members it adds, with no listing. **Refused 501:** `filter`, `routing`, `index_routing`, `search_routing`, `is_hidden`, `must_exist`, `remove_index`, wildcards, `_all` and comma lists in a name, and `GET /_alias` without a name. **Differs:** the actions of one `POST /_aliases` apply in order and each is atomic, but the list is not: an action that fails leaves the ones before it applied. The routes need `all_access`. **Search:** `_search`, `_count` and `_msearch` (a path default or an item's `index`) naming an alias of one index run against that index, with the concrete name in every hit's `_index`; the alias is read again on every request (one failed open of its own name and one register GET on top of the search), and an index that opens is never looked up as an alias. An alias of several indexes, and a comma list of names, is served by `_search`, `_count`, `_msearch` and `_field_caps`, as is a comma list of names, over the shards of every index ([search-several-indexes](specs/search-several-indexes/SPEC.md)); `ignore_unavailable=true` on `_search`, `_count` and `_field_caps`, and as an `_msearch` header key, skips a name that is no index ([ignore-unavailable-msearch-caps](specs/ignore-unavailable-msearch-caps/SPEC.md)). `_field_caps`, `_validate/query`, `_rank_eval` and point-in-time searches on an alias, are refused as before ([search-on-alias](specs/search-on-alias/SPEC.md)). **Routing:** `routing` on `_search` and in an `_msearch` header visits only the shards its values route to on an index of several (a routing partition visits all), and `preference` is accepted with no effect, as a shard has no copies ([search-routing](specs/search-routing/SPEC.md)); `_count` takes both the same way ([count-routing](specs/count-routing/SPEC.md)); a point-in-time create takes `preference` and a search of a view refuses `routing` and `preference` as OpenSearch does ([pit-routing](specs/pit-routing/SPEC.md)); `routing` on a create stays 501.

**Data streams** ([data-stream-routes](specs/data-stream-routes/SPEC.md)): `PUT|GET|DELETE /_data_stream/{name}` over the stream's alias record, a Java node's streams read and delete here and the reverse. A create needs a template that declares `data_stream`; it makes `.ds-<name>-000001` under the template that wins the stream's name, mapping the timestamp field as a date. `DELETE /{index}` of a stream's write index is refused 400. **Refused 501:** a wildcard, `_all`, a comma list, `GET /_data_stream` with no name. **Differs:** the backing index has no `_data_stream_timestamp` mapper, so a document without the timestamp field is not refused for lacking it. The routes need `all_access`. **Rollover** ([rollover-route](specs/rollover-route/SPEC.md)): `POST /{alias-or-stream}/_rollover[/{new_index}]` with `dry_run` and the `max_age` and `max_docs` conditions (`max_docs` is the sum of the exact totals of a search of no hits over each shard of the old index, the cost of `_count`): a stream gets `.ds-<name>-<next generation>`, an alias with a write index gains the new index as its write index, one without moves to it. An alias rollover's body may carry `settings`, `mappings` and `aliases` (only `is_write_index` on an alias; a stream refuses all three 400). **Differs:** the body aliases join the new index after the move is published, so one that fails then leaves the roll done and answers its error. **Refused 501:** size conditions (`max_size`, `max_primary_shard_size`: no size is reachable without a walk over the index's blobs), a pattern as target.

**Snapshots** (on by default, [snapshots-default-on](specs/snapshots-default-on/SPEC.md); `OSS_SNAPSHOTS_ENABLED`, `OSS_SNAPSHOTS_TAKE_ENABLED`, `OSS_SNAPSHOTS_RESTORE_ENABLED`, each `false` to turn off): `PUT|GET|DELETE /_snapshot/{repo}`, `POST /_snapshot/{repo}/_verify`, `PUT|GET|DELETE /_snapshot/{repo}/{name}` and `POST /_snapshot/{repo}/{name}/_restore`. A snapshot is the shallow kind a Java shell node takes (the repository setting `remote_store_index_shallow_copy`): it records which blobs hold each shard and copies none, so a take costs requests in proportion to shards, and a delete of an index reads the snapshots before it purges its blobs. A Rust node and a Java node take and restore each other's snapshots. A restore copies the captured files into a new index (new uuid, `rename_pattern` and `rename_replacement` supported; `index_settings` and `ignore_index_settings` change the created indices' settings, [restore-index-settings](specs/restore-index-settings/SPEC.md)); the copy streams through two buffers and a restore the memory pool cannot hold is 429 and writes nothing. **Differs**: standard (copying) snapshots, `include_global_state` is refused 501 when set to `true` (set to `false`, as `partial`, `include_global_state` and `ignore_unavailable` may be, they change nothing: [restore-default-flags](specs/restore-default-flags/SPEC.md)); a restore over an index that exists is 400. With `serverless.snapshots.restore.background.enabled` (`OSS_SNAPSHOTS_RESTORE_BACKGROUND_ENABLED`, off by default, with `_MAX` 1 to 16 and `_GRACE_MILLIS`) a native restore without `wait_for_completion=true` answers `{"accepted":true}` once the indices exist marked and copies on a thread; a failure is then not returned to the caller (the thread deletes what it made and logs it) and a shutdown cancels the copy ([restore-background](specs/restore-background/SPEC.md), [ADR 0063](adr/0063-a-restore-may-run-in-the-background.md)); a stock repository's restore stays synchronous. With `serverless.snapshots.take.capture_aliases` (`OSS_SNAPSHOTS_TAKE_CAPTURE_ALIASES`, off by default until the Java shell reads the fields) a take records each index's aliases, one read for each distinct alias, and a restore with `include_aliases: true`, `rename_alias_pattern` and `rename_alias_replacement` adds them to the created indices, one mutation for each distinct alias after every index is unmarked ([snapshot-aliases](specs/snapshot-aliases/SPEC.md), [ADR 0065](adr/0065-a-snapshot-captures-the-aliases-of-its-indices.md)). **Differs**: `include_aliases` defaults to false here (core's is true); `alias_write_index_policy` stays refused and a restored index writes only where its alias had no write target; an alias that cannot be added leaves the restored index, is named in `failed_aliases` of the answer (or logged by a background restore) and cannot be retried through restore; an index in more than 64 aliases records the first 64 by name (`aliases_truncated`); aliases are read per alias, not atomically with the shards; a stock repository's snapshots and the export to one carry no aliases. With `serverless.snapshots.take.partial_shards` (`OSS_SNAPSHOTS_TAKE_PARTIAL_SHARDS`, off by default until every node reading the repository has both changes) a take with `partial=true` keeps an index whose shard published nothing and records the shard in `failed_shards`; the snapshot then answers `PARTIAL` with `shards.failed` exact and at most 1,000 `failures`. **Differs**: a shard created and never written to counts as failed, a restore of a snapshot with failed shards is refused 500 `snapshot_restore_exception` unless `partial: true` is sent, which creates the index whole with the failed shards empty and answers `shards.failed` (stock answers 0), and with the setting off `partial=true` still skips the whole index as before ([snapshot-partial](specs/snapshot-partial/SPEC.md), [ADR 0066](adr/0066-a-partial-snapshot-records-the-shards-it-could-not-capture.md)). With `serverless.snapshots.take.capture_global_state` (`OSS_SNAPSHOTS_TAKE_CAPTURE_GLOBAL_STATE`, off by default until every node reading the repository carries the member through) a take with `include_global_state: true` records the persistent cluster settings, index and component templates, ingest and search pipelines and stored scripts, read before any shard work: 6 requests for an empty state, one more for each document, at most 4 MiB, else 400 `snapshot_too_large` naming the set ([snapshot-global-state](specs/snapshot-global-state/SPEC.md), [ADR 0068](adr/0068-a-snapshot-captures-the-global-state-it-is-asked-for.md)). **Differs**: a snapshot answers `include_global_state: true` only when it holds the state (stock's take default is true; here it records nothing unless asked and enabled); a restore with `include_global_state: true` puts each document back by name through its PUT route's validator and merges the persistent settings key by key, after the indices and aliases, deleting nothing (stock replaces the sets and settings wholesale, applies them with the indices and validates settings); a document that no longer validates or a setting that cannot be merged is named in `failed_global_state` and the indices stay, a retry is refused because the indices exist so the list is the only record; a set that would pass 1,000 documents is 400 `illegal_argument_exception` before any write; a restore that selects no index (`"indices":[]`) applies only the state; a snapshot without state answers `global_state_restored: 0`; the permission the ADR names is `all_access`, which this node already requires for every snapshot route. A node that dies part-way through a restore leaves an index that Rust nodes refuse (search 503 `cluster_block_exception`, writes find no index) until it is deleted and restored again; a Java node refuses it the same way for a search and a write ([snapshot-restore](specs/snapshot-restore/SPEC.md) AC-9).

**Stock snapshot restore** (in progress, [stock-snapshot-restore](specs/stock-snapshot-restore/SPEC.md), [ADR 0060](adr/0060-stock-snapshot-restore-reads-a-source-repository.md)): `serverless.snapshots.stock.enabled` (`OSS_SNAPSHOTS_STOCK_ENABLED`, off by default), the allow-lists `OSS_STOCK_REPO_ROOTS` and `OSS_STOCK_REPO_S3_ROOTS` (empty by default: nothing is readable until an operator names a root) and `OSS_STOCK_RESTORE_FANOUT` (8, 1 to 64) are read by a node. A repository registers as a stock one with `settings.format: "stock"` over type `fs` (`location`) or `s3` (`bucket`, `base_path`, `readonly`); another stock setting is 501 and an unknown one 400. Every `/_snapshot` route is already `all_access`. A restore from a stock `fs` repository under a listed root reads `index.latest`, `index-N`, the snapshot and each requested index's metadata, then each shard, with no LIST, and copies each file whole into a new index with its length and Lucene footer CRC checked; the source is opened read-only. A stock `s3` repository (`bucket`, `base_path`) is read the same way through this node's own S3 endpoint and credentials, only under a `bucket/prefix` in `OSS_STOCK_REPO_S3_ROOTS` that does not overlap this deployment's own bucket and prefix; a node whose store is a directory answers 501 for one. **Differs**: the switch off answers 501 for a stock repository, and the round-trips budget row (AC-9) is not yet recorded. A snapshot recorded from a stock 3.10 node restores and answers the searches that node answered ([fixture](../fixtures/snapshots/stock/README.md)); the index's `index.replication.type: DOCUMENT`, which 3.10 writes on every index, is dropped, any other value is 501.

**Stock snapshot export** ( [stock-snapshot-export](specs/stock-snapshot-export/SPEC.md), [ADR 0062](adr/0062-a-snapshot-is-exported-to-a-stock-repository-by-copying.md)): `PUT /_snapshot/{repo}/{name}` into a repository registered `format: "stock"` copies each named index's files into a layout a stock 3.10 node restores, writing `index-N+1` by a conditional create. Off by default: `serverless.snapshots.stock.export.enabled` (`OSS_SNAPSHOTS_STOCK_EXPORT_ENABLED`) and the allow-lists `OSS_STOCK_EXPORT_FS_ROOTS` and `OSS_STOCK_EXPORT_S3_ROOTS` (empty: nothing is writable). The target is written only by creates, never deleted from or listed. **Refused:** `include_global_state`, `partial`, an index in a bucket and a mapping or settings stock cannot hold (501); a name outside `[A-Za-z0-9._-]` (400); a target outside the allow-lists (400). **Differs:** the switch off answers 501 after reading only the repository record; a registered repository is not yet checked for a cluster admin (403).

**Search queue** (off by default, [search-queue](specs/search-queue/SPEC.md), [ADR 0056](adr/0056-over-share-searches-wait-off-the-workers-in-a-bounded-queue.md); `OSS_SEARCH_QUEUE_SIZE` above 0): a search from a tenant over its share while workers are scarce waits off the worker pool, up to the queue size node-wide. A full queue, or a wait past the limit, answers `429 es_rejected_execution_exception` with `Retry-After: 1` and closes the connection; shutdown answers waiting searches 503. **Differs**: stock OpenSearch answers 429 from its search thread pool queue per node, not per tenant, and keeps the connection open.

**Index templates** (off by default, `OSS_INDEX_TEMPLATES=true`, [boot-templates-ingest](specs/boot-templates-ingest/SPEC.md)): `PUT|POST|GET|HEAD|DELETE /_index_template/{name}` and `/_component_template/{name}`, and a create that inherits the winning template's shard count and mappings. **Differs**: a create (request or template) stores `index.refresh_interval`, `index.routing_partition_size` and `index.number_of_routing_shards` after checking them ([index-create-settings](specs/index-create-settings/SPEC.md)), stores the core settings that have no effect on this node (`index.codec`, `index.translog.*`, `index.priority`, the slow log, allocation filter and cache ones; [core-index-settings](specs/core-index-settings/SPEC.md)) after checking their values, and refuses 501, naming the keys, any other setting rather than dropping it, the bucket and cost ones aside; the definition is stored as sent. A create costs one GET more with templates on.

**Search pipelines** (off by default, `OSS_SEARCH_PIPELINES=true`; [search-pipelines](specs/search-pipelines/SPEC.md)): `PUT|GET|DELETE /_search/pipeline/{id}` and `GET /_search/pipeline`, and `?search_pipeline=<id>` on `_search` (`_none` runs nothing), or `"search_pipeline":"<id>"` in a search body, including each `_msearch` item ([search-pipeline-body](specs/search-pipeline-body/SPEC.md); the parameter wins over the body, the body over the index default). Runs request processors `oversample` and `filter_query` and response processor `truncate_hits`. **Refused:** any other processor OpenSearch ships (`script`, `rename_field`, `collapse`, `sort`, `split`, the routing processors) is 501 `not_implemented` naming it when the pipeline is stored, as are `phase_results_processors` and `ignore_failure: true`; an unknown processor or option is 400 `invalid_pipeline`; `POST` of a pipeline, a `search_pipeline` object in the body, `_count` with a pipeline parameter and `_search/template` with a pipeline stay refused. `index.search.default_pipeline` (an id or `_none`) is the pipeline a `_search` of one named index runs when it names none; a point in time and `_search` without an index take no default, while each `_msearch` item and `_count` run their index's ([search-default-pipeline](specs/search-default-pipeline/SPEC.md), [count-default-pipeline](specs/count-default-pipeline/SPEC.md)). **Differs:** `truncate_hits` is applied as a cap on the hits written, so a hit list is the same as in OpenSearch but a failing `truncate_hits` (no target and no `oversample`) fails the search before it runs.

**Ingest pipelines** (off by default, `OSS_INGEST_PIPELINES=true`): `PUT|POST|GET|DELETE /_ingest/pipeline/{id}` and `GET /_ingest/pipeline`, and the pipeline a `_bulk` item or a `_doc` write names runs over its source before it is applied. **Differs**: only the supported processors are accepted (an unsupported one is refused with the list), `_simulate` answers each document's source or error but no `_ingest.timestamp` and refuses `verbose` (501), and with pipelines off a write that names one fails that item.

## A `_bulk` with `Connection: close` on a Java shell node

The Java shell answers a `_bulk` request that carries `Connection: close` with the head of a chunked reply and closes before the body, so the client reads `200` and no body. A Rust node answers it whole (`crates/rest/tests/peak_memory.rs` sends one). Found by the mixed-fleet soak ([mixed-fleet-soak](specs/mixed-fleet-soak/VERIFIED.md)). **Not fixed:** the Java shell is under a code freeze ([ADR 0001](adr/0001-strangler-and-crate-layout.md)), so the soak keeps its connection open; a client of a mixed fleet that cannot keep one open should read the bulk's effect from a later `_count`, not from the body.

## `PUT /_serverless/extensions/modules` on a node

An administrator uploads an extension module (a WebAssembly module of at most 8 MiB) as the request body. The node hashes it, checks that it loads, and stores it under `ext/modules/<sha256>.wasm`; it answers 201 with the id, or 200 when the module was already stored. One upload runs at a time a node (a second answers 429, and a client that sends its body slowly holds the place until the read times out). With security off, like every route, it is open to anyone who can reach the node; with security on it is `all_access`. The route exists only on a node built with the Cargo feature `extensions` and started with `OSS_EXTENSIONS_PERCENT` above 0. **Differs:** this is not an OpenSearch endpoint; no point is wired to a request path yet ([extension-abi](specs/extension-abi/SPEC.md)).

## A pinned analyzer on an index (extension point `analyzer`)

An index created with `index.analysis.analyzer.<name>.type: serverless_module`, a `module` (the sha256 of an uploaded module) and `version: 1` analyses the text fields that name `<name>` as their `analyzer` with that module, at index time, in the overlay of a pushed tail and in the text of `match`, `match_phrase`, `multi_match`, `query_string`, `simple_query_string` and `_validate/query`. A create that pins is accepted only when the cluster setting `serverless.extensions.pins.allowed` is true (default false) and the caller is `all_access`; the coordinator records the resolved `fuel`, `memory_bytes` and `deadline_ms` beside the pin. A node that cannot run a pin (no extension runtime, the module absent or not matching its hash) answers 503 `extension_unavailable` and never serves the index with the standard analyzer. A write whose module fails answers 429 `extension_busy` (capacity), 502 `extension_malformed` (the module broke the contract) or 400 `extension_failed` (a failure a retry would repeat). **Refused:** `index.analysis.*` in a settings or mapping update (final, as in the Java), highlighting a field that pins an analyzer (400; a wildcard passes it over), `_analyze` with a pin's name (`failed to find analyzer`), and a frozen or point-in-time search over a pinned field. **Differs:** this is not an OpenSearch analyzer type, and a Java shell node refuses to open an index that pins one ([analyzer-extension](specs/extension-analyzer/SPEC.md), [ADR 0053](adr/0053-the-analyzer-extension-point.md)).

## `/_serverless/ready` and `/_serverless/drain` on a node

`GET /_serverless/ready` answers 200 while the node takes new work and 503 once it is draining, for a Kubernetes readiness probe. `POST /_serverless/drain`, for a `preStop` hook, starts draining and answers after `OSS_DRAIN_SETTLE_MS` (`serverless.search.drain.settle`, default two thirds of the lease TTL, at most a minute); the node's next lease renewal then carries no `search` role, so no coordinator ranks it as a reader or pushes it a tail, while its `ingest` role and its shards stay. A second drain answers at once. **Differs:** the shell also hands its warm blocks to its peers and can start warming on join (`warm_on_join`); this node does neither yet ([node-ready-drain](specs/node-ready-drain/SPEC.md)).

## A Java coordinator's forwarded shard search

When a Java reader refuses a shard as behind the log, a Java coordinator asks the shard's owner with `internal:serverless/search/shard`. A Rust node that writes the shard answers it from its own view, which holds the writes it acknowledged and has not published ([ADR 0057](adr/0057-a-rust-owner-answers-the-java-search-shard-action.md)). It answers only while it has renewed its own lease within `serverless.search.shard_action.max_lease_age_millis` (default 10,000), and refuses a shard it does not hold, an index recreated under another uuid, a full pool, and a peer below 3.10.0. The request is read in field order for `match_all`, `term`, `terms`, `range`, `bool`, `ids` and `exists`, with `boost`, `size`, `from`, `track_total_hits`, `min_score`, `terminate_after` and `_source` filtering; anything else is refused by name and the Java coordinator reports that shard as failed. Not served yet: a query with `_name` (the answer carries no `matched_queries`), a `range` with `format`, sort, aggregations and highlight. The request's `now` and `timeout` are read and not applied, and equal scores keep the shard's document order rather than `_id` order. `serverless.search.shard_action.enabled` (`OSS_SEARCH_SHARD_ACTION`, default on) turns it off, and `serverless.search.shard_action.max_concurrent` (`OSS_SEARCH_SHARD_ACTION_MAX_CONCURRENT`, default 2) bounds the searches at once.

## A write the node refused after an earlier window failed

With `OSS_WRITE_PIPELINE_DEPTH` above 1, several groups of one shard wait for the node log together. When a window fails, every group after it is refused, and a refused group's records may already be in a window that landed. A refused write can therefore reappear after a replay of the log, as a write that timed out can; the client sees the refusal and the retry is idempotent by `_id`. At the default depth of 1 the shard takes one group at a time and none is in flight behind a failure ([ADR 0050](adr/0050-writes-to-one-shard-share-a-commit-window.md)).
