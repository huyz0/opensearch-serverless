# 0050: Writes to one shard share a commit window: the slot lock is released before the wait

**Status:** Accepted

## Context

A write group takes the shard's slot lock, applies its items to the engine, stages their records in the node log's committer and waits for the window holding them to land, all under the slot lock (`WriterRole::group_admitted`). Two write requests to one shard therefore never share a window: each waits its own, and a shard takes one request a window. Measured (provisional, debug build, file store, a 250 ms window, bulks of 20 documents): four clients writing one index take 1,015 ms a bulk and the node does 27 bulks in 6 s; four clients with an index each take 254 ms and do 96. A tenant's top-load target is about 10,000 writes a minute on one index, from many requests, so one request per window per shard is a ceiling the target can reach.

The lock is held across the wait for one reason: order. The engine assigns sequence numbers under the lock, records are staged in the same order, and a failed commit releases the shard so that nothing is acknowledged after a write the log does not hold.

## Decision

1. **Split the commit.** `NodeLogCommitter::stage(shard, term, records)` joins the windows exactly as `commit` does, marks the youngest window driven as `commit` does under the same hold of the committer's lock (so a waiter whose window is no longer the youngest is not left to linger), and returns a `Staged` holding the latches of the windows joined. `Staged::wait(&committer)` is the rest of `commit` (drive or linger, read the results, `CommitError::Lost` for a window never written) and `Staged::finish(&committer)` drives or waits until every window is final without reading a result. `commit` is `stage` then `wait`, unchanged for every other caller. Windows of this node's one committer are written one at a time in order, so when a group's window has finished, every earlier one has.
2. **A slot keeps a pipeline** in its own module (`writer/pipeline.rs`; `writer/mod.rs` is at its size limit): a ticket counter, `in_flight` (entries: ticket, `Staged`), a sticky `failed` flag, a `quiescing` counter, and a small mutex with a condvar for waits. Under the slot lock a group applies its items and stages their records, so the log order of one shard's records is its sequence order. It then takes a ticket (above depth 1 only), joins `in_flight`, and drops the slot lock. A group with no record to stage takes no ticket. A group that finds `failed`, `released()`, `asleep`, or `quiescing` does not stage (`asleep` wakes the shard as today; `quiescing` waits on the condvar without the slot lock and then re-checks all of them).
3. **Depth is bounded and is the switch.** `OSS_WRITE_PIPELINE_DEPTH` (node scope, 1 to 64, default 1) bounds `in_flight` per slot: a group that finds it full waits on the condvar, without the slot lock, and re-checks. The ticket is taken under the same hold of the slot lock as the apply and the stage, so ticket order is sequence order. The depth check runs **before the apply**, under the slot lock: a group that finds `in_flight` at the depth drops the lock, waits, takes it again and re-checks `failed`, `released()`, `asleep` and `quiescing` before applying. At depth 1 the group takes the **existing path unchanged** (`commit` under the slot lock, as at `writer/mod.rs:462` today): no ticket, no guard, no relock, no pipeline mutex (`std::sync::Mutex` is not reentrant, so rules 4 to 6 apply only above depth 1). The existing tests therefore pin the old behaviour and new tests run both depths. The write limiter's permit (429, never a wait) is held for the whole group as now; it does not bound the pipeline when none is set, the depth does.
4. **Finishing, in ticket order.** After its stage, a group holds a **guard that is created only after the slot lock is dropped and is dropped with the slot lock only in the order rule 5 gives**; no code that can panic runs between the stage and the guard. (a) Wait for its windows (`Staged::wait`), measured for the limiter as the window wait only, not the ticket wait or a quiesce stall. (b) Wait for the previous ticket to finish, without the slot lock. (c) Take the slot lock. If its own windows failed, or `failed` is set (an earlier group's failure sets it before its ticket is released, so the sticky flag is the check), set `failed` and refuse, even if its own blob landed (its outcome is unknown to the client, as for a write that timed out). (d) Otherwise run the acknowledgement effects **under the slot lock**: `appended` for the limiter, `publishing.written`, the tail overlay's `acked`, and advance the slot's **acked high-water mark** (`acked_seq_no`). They run in ticket order, which is sequence order, and only on a slot that is not failed. (e) Advance the ticket, remove the entry, wake the waiters. If the slot is `failed` and `in_flight` is now empty, this group is the last out: it drops the slot lock and then releases the slot (`release`: the shards map, `newest`, the lazy-publish state, the tail overlay, in that order after the slot lock, as `release` runs today).
5. **The guard on an early return or a panic** (a drop guard, **disarmed on the normal path** once rule 4e has run, and declared **before** the slot lock's guard in the function so that on an unwind the slot guard drops first and the pipeline guard never finds the lock held by its own thread; a panic in rule 4c to 4e, such as inside `acked` or `written`, therefore unwinds the slot guard, then runs this guard, which takes the lock afresh): it first drives every window of its `Staged` to final (`Staged::finish`), **which catches panics from the write and never unwinds** (`await_landed` re-raises a write panic with `resume_unwind`, and a second panic during unwinding aborts the process; the caught panic is recorded as the group's failure) and may block for the committer's patience, so a window another thread has not yet driven cannot stay queued and land after a reopen; then it takes the slot lock, sets `failed`, advances the ticket, removes the entry, and does the last-out release if it empties `in_flight`. A refused or panicking group therefore never leaves a window unwritten and never holds the ticket.
6. **Every failure path goes through `failed` and last-out.** A `stage` error (an encode failure, or a join that returns `Lost`) after items were applied, the incarnation-mismatch branch, and a commit failure all set `failed` under the slot lock; the slot is removed from the map only when `in_flight` is empty (by the group itself when it is alone). A failed slot lingers in the map and refuses new groups ("released after a failed write", as today), so no reopen reads the log while a staged window of the old slot can still extend it, and no sequence number is issued twice.
7. **Readers of the slot's sequence state read the acked mark.** `max_seq_no` as the tail overlay's floor and claim (`tail_serve`, `tail_await`) and the refresh-visibility wait use `acked_seq_no`, not the engine's maximum: a group applied and staged but not yet acknowledged is not claimed as refreshed, and its records reach the keep when it is acknowledged. Anything that read the engine's maximum only under the slot lock for a decision about published state (`publishing.written`) keeps doing so after the quiesce of rule 8.
8. **Publish, hibernate, evict and refresh's publish quiesce the shard first.** A caller takes the slot lock and increments `quiescing` (a counter, so two quiescers do not release each other; cleared by a drop guard, so an early return such as `held.snapshot()?` cannot leave writes parked); if `in_flight` is not empty it drops the lock, waits for every entry to finish, and takes the lock again. It then re-checks `failed` and `released()` and aborts without a snapshot if either is set, **unconditionally** (also when `only_if_due` is false: a refresh of a failed lingering slot must not publish). For a publish the quiesce ends once the snapshot critical section has captured `max_seq_no`, the logged position and the snapshot (a later failure cannot put unlogged data into that commit), so writes go on during the upload as today. For hibernate and evict it spans their publish and the second critical section that sleeps and releases the slot and is cleared only after the slot is slept and released. An `only_if_due` publish checks due, `released()` and `failed` under the slot lock first and quiesces only if due, then re-checks. The `last_position` and `on_published` pairing is safe only because of the quiesce, and the comment "every write is logged while the slot is held" in `refresh.rs` is rewritten with it; waiters re-check `asleep`, `failed` and `released()` after waking. `publishing.gate()` is taken before the quiesce and held across it: taking it after would hold a slot lock while waiting for the gate, against the gate-then-slot order every publish already follows. The cost is that other shards' publishes wait behind one shard's in-flight windows, about one window, and publishing is infrequent. Give-back works on asleep records with no slot and does not quiesce; retire quiesces through hibernate. A quiesce stalls new writes to that shard for up to about one window (the wait for the groups in flight), not for an upload; publishing is infrequent. The depth, ticket and quiesce waits test their predicate under the pipeline's mutex and a counter bumped under that mutex by every state change closes the lost-wakeup window between dropping the slot lock and waiting; a test forces that interleaving. The depth is read once when the role is built.

No new request, timer or format: the records, windows and blobs are as before; more groups ride one window, so a node makes fewer PUTs for the same writes.

## What readers see

A realtime get, a refresh, an update and a delete-by-query read the engine under the slot lock, and the engine now holds writes applied but not yet in the log. A read can see a write that a failed window then refuses. OpenSearch's engine behaves the same (a realtime get sees an operation before its translog sync). It is accepted here: reads of unacknowledged writes are not promised, a client whose write was refused is told so, and an update based on it is refused by rule 4c (it staged after the failure or its own earlier-entry check finds it). A search sees only a refreshed or published commit, as before.

## Why this does not break the invariants

- *Acknowledged means in the log.* A group returns success only after its own windows landed with no failure for the shard, no earlier window of the slot failed and the slot is not failed (rule 4c), checked under the slot lock.
- *No acknowledged write after a missing one,* whichever thread wakes first: the failure is found by the sticky flag or by reading the earlier windows' results, both under the slot lock. A blob after a gap can still land (an admission refusal of the earlier window does not end the epoch); after the slot is released the shard replays the later records without the earlier one (replay applies full-document and delete records above the committed sequence and tolerates gaps, a state a write that timed out already leaves, asserted by test 13's gap case against the replayed state, and noted for the Java shell's reader in `docs/compatibility.md`; the engine continues from the replayed maximum). Those writes were refused, so replay holds only writes no client was told succeeded: the state a write that timed out after its blob landed leaves.
- *No sequence number is issued twice* (rules 5 and 6): a reopen cannot read the log until every staged window of the old slot is final, including windows orphaned by a dead thread.
- *One write log per node, one blob per window, fencing by conditional create* are untouched. Admission is checked once per (shard, term) in an epoch; a later window of a taken-over shard is stopped by the successor's fence closing the epoch (`CommitError::Fenced`), as when the lock was held. Hedged PUTs resolve to one outcome a window, so they add no failure mode.
- *Panic mid-apply* is as today, not worse (see Sequence-state readers).
- *Bounds* (ADR 0004): `in_flight` is bounded by the depth per slot, and a **node-wide reservation** bounds the memory of groups in flight: the bytes in flight are those of requests the bulk budget and the body reservation already bound, the same at any depth, so a deeper pipeline adds no memory beyond the groups of requests admitted; the limiter, when set, is a second bound. No new reservation is added. Test 14 asserts the in-flight bytes of groups never exceed the budget's total at depth 64; the ticket and quiesce waits are on a condvar with no allocation; entries are removed when their group finishes.
- *Lock order*: slot lock, then the committer's lock, as now; the committer never takes the slot lock; the last-out release runs after the slot lock is dropped, so no new order among the slot, `shards`, `newest` and the tail locks exists; the ticket, depth and quiesce waits hold no lock but the pipeline's own small mutex, and no thread waits for the slot lock while holding it. A thread panic mid-apply leaves a recovered poisoned lock with applied-but-unstaged writes, as today; the new code does not worsen it.

## Sequence-state readers

These read the engine's maximum sequence number and are each justified in the implementation: `hibernate.rs` (the max before and after the sleep), `capacity.rs` (the eviction candidate's max), `refresh.rs` (the visibility wait and the publish), `takeover.rs` (the handoff), and the public `max_seq_no`. Each takes the acked mark, or runs after the quiesce of rule 8, and carries a `// ACKED:` or `// QUIESCED:` comment saying which, which the check requires beside each call (it cannot tell which is right, a reviewer does); a check in `scripts/` (planted in `scripts/selftest-checks.py`, a row in `docs/mechanical-gates.md`) fails a call to the engine's `max_seq_no()` outside an allow-list of justified sites (`mod.rs`, `capacity.rs`, `hibernate.rs`, `refresh.rs`, and `takeover.rs` for a freshly opened slot). A quiesce is needed before a publish because `snapshot` commits applied writes, and an applied-but-unacknowledged write would put unlogged data into a published commit. For hibernate and evict the parked writers wait for the groups in flight and the publish upload (a rare, idle-shard event), and nothing calls them while holding `shards`, `newest` or the role gate (checked in the implementation, with a test). The quiesce for a publish ends after the snapshot, so a hot shard with a 1 s refresh interval stalls up to about one window a publish; this is measured before the default moves. A panic mid-apply is the one exception to the claim of no acknowledged write after a missing one: it leaves a recovered poisoned lock with applied but unstaged writes, as today, and test 19 pins that a later group still acknowledges only what it staged. At every depth the slot advances `acked_seq_no` under the slot lock it already holds (at depth 1 too, so the tail readers of rule 7 work at the default), with a depth-1 test. The incarnation-mismatch branch's `release` (today before the slot lock is taken) moves after `failed` is set under the lock. A group refused because an earlier window failed reports `landed=false` to the limiter (test 15). A refused write can reappear after a replay, as a write that timed out can; this goes into `docs/compatibility.md`.

## Consequences

- A hot shard takes as many requests as one window carries, bounded by the window's limits, the limiter and the depth.
- A failed window fails every in-flight group of the slot, not only the one that held the lock when it failed.
- The slot lock is held for the engine apply, staging and finish only, never for a window (at depth above 1).
- A failed slot now lingers in the map until its last group is out; a request for it is refused as for a released slot.

## Tests and the crash plan

A test store gates and fails PUTs on demand (hold a window's PUT, refuse it, or land it and then answer an error: the landed-but-unknown case, which the committer counts as unpublished). Thread wake order is forced by holding and releasing windows, not left to the scheduler. Both depth 1 and a deeper pipeline run. Each is seen failing against the rule it protects:

1. Two groups on one shard share a window: one blob, one window of latency; at depth 1 two windows, as today.
2. A refused PUT with three groups in flight: all three refused, none acknowledged; the shard reopens only after the three are final; the replayed state holds none of their writes.
3. A's window fails and B's lands after it, with A's thread forced to run first and then last: B is refused either way; after the reopen the replayed state is asserted; no client was told either succeeded.
4. A fails, C is staged behind it, a request for the shard arrives before C is final: it is refused, and once C lands the reopened slot issues sequence numbers above C's.
5. A group whose thread dies between stage and wait (the guard): its windows are driven to final, no reopen happens and no sequence number repeats while one is unwritten, later groups are refused not hung.
6. A `stage` error on a quiet slot, and the incarnation-mismatch branch with groups in flight: the slot fails and is released by the last group out, never earlier, and no effect repopulates the tail or lazy-publish state afterwards.
7. The effects of a landed group run after a later group's failure: skipped.
8. Effects in ticket order: many concurrent groups call `acked` in sequence-number order.
9. A subscriber or claim taken while a group is staged: after the group is acknowledged its records reach the overlay (the acked mark, not the engine maximum).
10. A publish while groups are staged waits for them; with one failed the publish aborts; the same for hibernate and evict and for a refresh of a failed lingering slot; two concurrent quiescers; an early return leaves `quiescing` clear.
11. The depth bound: a group beyond it waits and proceeds when an entry finishes; no more than the depth are ever in flight.
12. A write racing a hibernate or retire: no write acknowledged after the shard is asleep, none lost.
13. Crash, emulated by a new `WriterRole` opened over the same fs store while the old committer is dropped mid-window (the test store holds, refuses or lands-then-errors the PUT, and the old role's threads are abandoned), at: before the PUT; between the PUT landing and the acknowledgement; with A's window unwritten and B's landed (a gap): restart replays B without A, B was never acknowledged, the next sequence number is above B; during a quiesce; after a publish that covered only landed records. After restart every acknowledged write is present; an unacknowledged one may or may not be.
14. The memory reservation: groups beyond it wait, and none allocates past it.
15. A group refused because an earlier window failed reports `landed=false` to the limiter.
19. A panic mid-apply: a later group acknowledges only what it staged.
20. At depth 1 the tail readers see `acked_seq_no` advance.
16. Request count: N groups to one shard make one PUT above depth 1 and N at depth 1 (an `exact` row in `docs/request-budgets.md` bound by `check-budgets.py`, and a pipelined variant of I-5 in `docs/invariants.md`).
17. A write that panics while the guard runs during an unwind: the process does not abort, the slot is failed and released. A panic inside `acked` or `written` under the slot lock: no deadlock, the slot failed and released, the ticket advanced.
18. Writes proceed during a publish's upload.

Each test is named by an `AC-n` in `docs/specs/write-pipeline/SPEC.md` with its red-then-green evidence in `VERIFIED.md`, both depths run in CI, and the switch gets a `docs/how-to` entry. The lock order is held by a test under a debug assertion on the slot lock's owner, not a script. `docs/specs/write-pipeline/SPEC.md` is written first.

## Switch

`OSS_WRITE_PIPELINE_DEPTH`, default 1 (today's behaviour). It moves to a deeper default only when the crash and forced-order tests above pass and a measurement shows no worse p99 at one client, no extra store requests, and the gain at many clients; until then the downsides listed above (a failed window fails the groups in flight, reads can see unlogged writes, a quiesce stalls writes for a window) are not accepted by default.
