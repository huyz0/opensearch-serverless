# 0042: Snapshots are taken shallow first, in the Java's protocol, behind the switch

**Status:** Accepted, 2026-11-24 (independent review: accept with fixes, applied)

## Context

[ADR 0038](0038-snapshots-read-first.md) made snapshots readable and [ADR 0040](0040-repository-registration.md) made repositories writable. Taking a snapshot is the next piece: `PUT`/`POST /_snapshot/{repo}/{name}` in the shell's `SnapshotOperations.capture` and `SnapshotStore.create/finish`. A snapshot is a name register (`snapshot-states/<sha256 of "<repo>#<name>">`, a compare-and-swap value), a discovery marker blob under `snapshots/`, and a record naming each captured index's uuid, shard count, mapping, settings and each shard's commit (a term and the files in it). A standard snapshot also copies every shard blob under `snapshot-data-v2/<generation>/...`; a shallow one only names the live blobs, which the janitor already holds for any index a snapshot names ([janitor-snapshot-pins](../specs/janitor-snapshot-pins/SPEC.md)).

## Decision

- **Shallow first.** A repository whose `remote_store_index_shallow_copy` setting is true (the shell's `shallowByDefault`, the only selector the Java has) takes shallow snapshots: no shard data moves, so a take costs requests that scale with indices and shards, not bytes. A standard repository answers 501 `unsupported_snapshot_storage` until a later ADR decides the copy.
- **The Java's protocol.** (1) Read the repository (404 `repository_missing_exception`); the Java reads it twice, Rust once. (2) Describe every named index (404 `index_not_found`; `ignore_unavailable` skips; a system index 403 `system_index`). (3) Create the name's state register with a reservation record naming each index (uuid, shard count, mapping, settings) and no commits, under a fresh storage generation and marker `v2-<sha256 repo>#<sha256 key>#<generation>`: `create_register` when the name has none, a compare-and-swap over a released one, up to 16 tries; a held name is 400 `snapshot_already_exists`. Each try reads the register, and when it is absent also the legacy blob `snapshots/<repo>#<name>`, as the Java does, so a name held by a legacy snapshot is refused; a key over 255 bytes is 400 `invalid_snapshot_name_exception`, never the Java's LIST. (4) Write the protective marker with a conditional create and re-read the register to confirm it still names this marker. The marker body is the stripped record: the same indices with null mapping, empty settings, no shards and `end = start`. The janitor and index delete pin an index's incarnation from this point, not from the finish. (5) Verify each index's uuid is the described one; a change fails the take. (6) Read each shard's published commit by `CommitManifest::parse` and copy `term`, `files` and `lengths` verbatim; `wal_ordinal` and `stage_seq` are dropped, so a snapshot captures the published commit and not the unpublished log tail. A shard with none is 409 `nothing_published`, or with `partial` that whole index is skipped (it stays in the reservation and marker until the finish). If every index is skipped the take answers 409 `nothing_published` (a deliberate divergence: the Java finishes an empty `SUCCESS`). (7) Finish by a register read and a compare-and-swap to the finished record with the finished flag.
- **Layouts.** The record's shard count must equal the shards listed. An index with a layout or a split (live units fewer than slots) answers 501 `unsupported_snapshot_layout`, because the Java's own record parser refuses such a record; the shard bound counts the listed shards.
- **Cleanup.** A failure after (3) releases only this take's lifetime (uuid and storage generation) by compare-and-swap, then removes the marker only if that release applied or the register no longer names it; release first, so a marker without a register is skipped. A racing delete and re-take of the name is never wiped. A cleanup failure is suppressed and the original error returned; an orphaned marker is skipped by reads.
- **Failures without their own name:** a changed incarnation, a capture no longer active, a register conflicted 16 times and a delete during the marker write are 409 `snapshot_conflict`; the Java's typed failures keep their names and statuses; an invalid repository or snapshot name is 400 `invalid_snapshot_name_exception`. Index names in `indices` are not name-validated; duplicates collapse and count once toward the bound.
- **Request.** The body takes `indices` (a list or a comma string; empty is 400 `missing_indices`), `ignore_unavailable`, `partial` and `include_global_state` (read and reported false); `metadata` is 501 `unsupported_snapshot_option` and any other key 400 `unknown_parameter`. Without `wait_for_completion` the answer is 200 `{"accepted":true}`; with it, the `snapshot` object the read slice renders. The take is synchronous either way. The route runs behind the same admin gate as the other snapshot write routes.
- **Cost, no LIST.** 1 GET repository; per index 2 GETs (describe, incarnation check); per shard 1 GET for its commit, and one GET per bucket manifest when members share a bucket (the take reads each bucket once, into a bounded buffer); register: 1 GET per create try plus 1 legacy GET when absent, 1 create PUT, 1 marker PUT, 1 confirm GET, 1 finish GET, 1 swap. A fresh one-index, one-shard take is 11 requests. Two indices of two shards each add 2 describe GETs per index and 1 GET per shard. No count depends on the bytes of an index. Bounds, deliberate divergences from the Java which has none: 100 indices and 4,096 shards in total (400 `snapshot_too_large`), found before the reservation. A record over 16 MiB is 413 `snapshot_record_too_large`, raised when the finish record is built, with cleanup; the write cap is the same constant as the read slice's. The record is built into one buffer reserved from the request-body pool (429 when it cannot be).
- **Fencing is the register's compare-and-swap and the marker's conditional create**; no lock. A node that dies mid-take leaves an `IN_PROGRESS` snapshot holding its indices' blobs until a delete releases it. Rust has no delete yet, so this is the downside that makes the take a setting of its own.
- **Switches:** the take needs `serverless.snapshots.enabled` and `serverless.snapshots.take.enabled` (`OSS_SNAPSHOTS_TAKE_ENABLED`), default false until the mixed-fleet proof passes and a snapshot delete exists or the stuck case is documented as accepted. With either off the take answers 501.
- **Placement:** the record writer and state encoding in `oss-format`, the reservation, marker, finish and cleanup in `oss-meta`, the decisions in `oss-coordinator`'s `snapshot_admin`, the orchestration and route in `oss-node`. Records are compared by content with the Java fixtures, not by key order.

## Remaining for the build

- A Rust-written `FileLocation` (pack and range text) must be read by the Java's `manifest.location(...).referencedBlob()`, and a Rust `lengths` entry must name a captured file: proved by the mixed-fleet test (recorded Java fixtures plus a Java-side test over a Rust-written record; nothing needs Docker).
- Restore and snapshot delete remain 501.

## Consequences

Easier: a deployment can snapshot its indices without copying data. Harder: a shallow snapshot is only as durable as the live index's blobs, so a deleted index's blobs must stay pinned while any snapshot names them (the janitor already does this, held by the incarnation). Standard snapshots are not available.

## Alternatives rejected

- Standard (copying) snapshots first: scales with bytes, needs its own cost and crash decisions.
- A Rust-only snapshot format: the Java must read what Rust takes, in both directions.
- Taking asynchronously: the Java is synchronous, and a background take needs a timer or a worker that this node has no use for.
