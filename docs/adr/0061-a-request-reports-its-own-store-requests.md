# 0061: A request that asks reports the store requests it made, in a response header

**Status:** Accepted after independent review (2026-11-25; the reviewer found no S3-cost, memory or scalability trade; two rounds, the first with four required changes, the second with one, a null scope for the commit window's append, now stated)

## Context

The roadmap lists "per-request blob cost in responses" under cost guardrails. Today the node knows what each *index* costs ([ADR 0037](0037-per-index-store-usage.md): a ledger fed by the store's meter) and judges tenants by it ([ADR 0041](0041-tenant-cost-levels.md)), but a caller cannot see what one request cost. That is the number an operator needs to tune a query or a bulk shape, and the one that turns "requests scale with nodes and bytes" from a rule into something a client can check on its own call.

The meter is called on the thread that makes a store request, and the ledger already reads two thread-locals there (the owner of the key, and the indices a shared upload is split across). A request is served on one worker thread, but its store requests are not all made on it: a cold open reads files on scoped threads (`reader::prefetch::primed`), loads modules beside the commit (`search_open`), and the coordinator's fan-out drains items on scoped threads (`coordinator::fanout`). Some work for a request is shared (a page-cache fill another request started, a log PUT a commit window shares) and some is not for any request (the janitor, timers, takeover).

Forces: no extra store request ([principles](../principles.md)); bounded memory with reservation before allocation ([ADR 0004](0004-bounded-memory-and-streaming.md)); no cost on a request that does not ask; the report must never be read as a bill it is not.

## Decision

**A request that carries `X-Opensearch-Serverless-Cost: report` is answered with an `X-Opensearch-Serverless-Cost` response header counting the store requests made on its behalf on this node; a request without it pays nothing.**

1. **Scope.** `oss_blob::cost::RequestCost` is a small set of atomic counters (milli-requests by `S3Op`, bytes read, bytes written; about 100 bytes), created by the REST edge only for a request that asks, and held in a thread-local scope on the worker for the length of the request. The ledger's tap (`LedgerTap`, which the meter holds once) adds each request and byte count to the scope as well, whatever line the ledger charges it to: the scope is a second, independent sum, not another branch of the owner-then-split rule. A request that does not ask sets no scope; its cost is one more thread-local read per store request, beside the two the ledger already makes.
2. **Carrying it across threads.** `RequestCost::capture()` returns a handle (an `Arc`) or none, and `handle.enter()` is a guard that sets the scope on another thread and clears it when dropped, also on unwind. The guard on the worker is dropped between requests, so a pooled worker never keeps a scope into the next request (a test panics a handler and checks the next request sees none). Hand-off sites on a request path that make store requests, each capturing at the spawn and entering inside it, each with a test: the cold open's scoped file reads (`reader::prefetch::primed`), the module load beside a commit's open (`node::search_open`), and the coordinator fan-out's helper threads (`coordinator::fanout`). A search that waits in the over-share queue ([ADR 0056](0056-over-share-searches-wait-off-the-workers-in-a-bounded-queue.md)) is replayed as a new connection whose head is read again, so it needs no capture. A site that is missed under-counts and never fails the request.
3. **What is counted, and what is not.** Counted: the store requests, and their bytes, made by threads working on the request, including a page-cache fill or cold open the request itself led. Not counted, by design: a fill or open another request led that this one waited for (single-flight waiters pay nothing; the lead pays all), the janitor, timers, tail flushes, the overlay builder's fetch (a transport call to the writer, not a store request), takeover, warm-join copies and anything else no request caused. **Writes report no share of the log PUT in this change.** The commit window's PUT is made by whichever request's thread drives the window and by hedge threads, for all the writes in it, and the ledger's split weights are per index and not per request, so a request cannot be given an exact share without the window carrying each asking joiner. The window's write runs with the request scope suspended (a null-scope guard around the driver's append in `writer::log::committer`; hedge threads start with none), so no write's number holds the window's PUT, and two asking writers that share a window each report `put=0` for the log append (a test). A write that asks is answered with the store requests made on its own thread tree (a mapping update, say) and `shared=log`, which says the window's PUT is not in the number; the per-request share is a follow-up that makes the window carry `(handle, bytes)` for each asking joiner and enter a splitting scope on its driver and hedge threads. Requests another node made for a forwarded request are not counted either (the transport carries no headers); the header says `scope=node`.
4. **The header.** `X-Opensearch-Serverless-Cost: get=12;get_range=3;head=0;put=0;copy=0;list=0;delete=0;bytes_read=48211;bytes_written=0;units=1.040;node=<id>;scope=node`. A request count is the thousandths the meter kept rounded to the nearest whole request; `bytes_*` are body bytes; `units` is the ledger's cost in PUT-equivalents ([ADR 0037](0037-per-index-store-usage.md)) to three places, so a test compares a header to the ledger within the rounding and does not sum it exactly. `scope=node` says the numbers are a lower bound for the request's cost across a cluster. The header is written with the response head, so it counts what was made before then. A route that writes its head before its work is done (the streaming `_msearch`) does not carry the header and a request that asks it gets none, never a partial one. An error response made after the work carries it; `HEAD` carries it as the same `GET` would. A node with no usage ledger (store usage off) has no tap to add the scope to: the header is omitted. The header is honoured only after authentication and authorization have passed, so an unauthenticated caller cannot make the node allocate a scope.
5. **Memory and bounds.** One counter set a request that asks, freed with the request; counters are fixed-size, so there is nothing to bound by records, documents or indices. A request header longer than the server's header limit is refused as today.
6. **Authorization.** The header reveals counts only, to the caller whose request produced them; it names no other tenant or index and is subject to the route's authorization as the response is.
7. **Switch.** No node setting: the request header is the switch, and a request without it is as it was. Both modes are tested. A cluster setting that refuses the header (a deployment that treats counts as sensitive) is a follow-up if one is asked for.

## Consequences

- A client can read what a search, a get or a bulk cost, and a test can assert a request's store requests from the response, which strengthens the request-budget tests: they read it from the response instead of the meter.
- The counted work depends on every thread hand-off carrying the scope; the per-site tests and a note in the crate READMEs keep that list honest, and a missed site shows as a low number, not a wrong one.
- The report is a lower bound and not a bill: shared and background work is attributed by the ledger, not here. The header says so (`scope=node`).
- Nothing changes for a request without the header, for the ledger, or for the guardrails.
- `docs/request-budgets.md`, `docs/compatibility.md` (an added header) and `crates/blob/README.md` change when it lands.

## Alternatives rejected

- **Always send the header.** It would add bytes to every response and make the lower bound look like a fact; opt-in keeps the cost where it is wanted.
- **Take the cost from the ledger by diffing counters around the request.** Other requests' work lands in the same counters; the diff is wrong under concurrency, the case that matters.
- **A request id on every store call.** Changes the store trait and every call site for a number that thread scopes give for the few hand-offs.
- **A trailer.** Not every client reads them, and the HTTP/1.1 server answers the common case with a whole body.
- **A per-request share of the window's PUT now.** Needs the window to carry each asking joiner and a splitting scope on the driver and hedge threads (`writer::log::committer`, `hedge`), which is a change to the write path's hot code; left for a follow-up with its own measurement.

## Amendment: a write's share of its commit window

**Status:** Proposed; needs an independent review and the owner's decision, because it touches the write path's hot code ([spec](../specs/request-cost-window/SPEC.md)).

Decision 3 left the window's PUT unreported and named a null scope and `shared=log`; neither was built (the request scope reached the window's driver, so the one writer that happened to drive a window was charged all of its PUT and the others none). This amendment replaces them with the follow-up the alternatives list ends on.

- A window keeps the counters of each writer that joined it with a request scope and the bytes that writer put in. The thread that writes the window enters a **splitting scope** for the whole write (the epoch's lease, admissions, the blob), and the hedge threads of its PUT enter the same one. Every store request and byte count made in it adds to each asking writer its bytes' share of the window's total bytes, in thousandths of a request. A writer that did not ask contributes its bytes to the total and is charged nothing, so the shares add up to at most the window's PUT.
- A write that asks therefore reports a share of the log PUT, not `put=0` and not the whole blob; `scope=node` still says the number is a lower bound. `shared=log` is not used.
- Cost: a thread-local read and, for a writer that asked, one entry in the window and a clone of its counters' handle; nothing for a write that did not. No store request is added and none changes: the window's requests are the same with and without a scope. Both modes are tested.
- Rejected here: charging the whole PUT to the driver (what happened without a scope, and it depends on which thread wins the window); charging it to every asking writer (the shares would add to more than the PUT).
