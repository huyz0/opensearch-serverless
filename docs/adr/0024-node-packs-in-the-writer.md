# 0024: Node packs in the writer: one PUT for the segments a node publishes together

**Status:** Accepted after independent review, 2026-11-21 (for the writer half; the collector needs its own decision before the switch can be on)

## Context

A publish writes one blob per new segment of one shard ([segment publish](../specs/segment-publish/SPEC.md)). A node holding thousands of small shards that publish within the same second pays a PUT per shard per publish, however small the segment is. The Java shell measured this (1,000-shard soak, 2026-11-12): node packs cut PUT-class requests per publish from 2.09 to 0.68, with first-search latency no worse, at a takeover cost the shell accepted (the Java's `NodePackWriter`, `NodePackStore`, `NodePackLedger`). Reads already work: the Rust reader follows a manifest's `@<node>/e=<epoch>/<ordinal>#<offset>:<length>` locations ([blob formats](../specs/blob-formats/SPEC.md)). Nothing in Rust writes a pack, so a mixed fleet gets packs only from Java nodes.

## Decision

Port the Java's pack writer, as-is on the wire, in `oss-writer::pack`, in pieces: the format writers ([node-pack-format](../specs/node-pack-format/SPEC.md)), the store, batching writer and ledger (`node-pack-writer` spec), and the publisher's placement. **The collector is not decided here:** it re-reads shard manifests on a backoff, an elapsed-time cost per shard that the owner's rules forbid unless bounded, so it needs its own ADR. Until that ADR is accepted and built, the switch below cannot be turned on anywhere.

- **One pack per window.** A publish hands its small segment blobs (at most `max_blob_bytes`, default 8 MiB; larger blobs keep their own PUT) to the node's one pack writer. The first blob into an empty batch becomes the leader, waits up to `linger` (default 50 ms) or until the batch holds 64 MiB, then writes the batch as one blob with create-if-absent. No thread of its own. A node whose publishes never overlap pays the PUT count it paid without packs, but every lone publish also waits the full linger (50 ms): that is a real cost, and one reason this is a switch.
- **Fenced by reachability, not by lock.** A pack is created once under `packs/<node>/e=<epoch>/<ordinal>` and never changed. It becomes reachable only through a shard's manifest swap, itself fenced by the register's term. A stale writer's pack is therefore inert. A swap made more than `SWAP_DEADLINE` (5 minutes) after its pack landed is refused, which is what lets a future collector delete a pack nothing names once it is three deadlines old. That argument rests on clocks and has a residual window: a writer paused between its age check and the register's compare-and-swap can still swap a pack the collector has judged. The collector's ADR must close it (the check immediately before the CAS, on a monotonic clock from the landing, and a margin of three deadlines that dwarfs any pause the node's own timeouts allow) and must count every reference: manifests, point-in-time views, frozen views, snapshots and clones that share segments, and no judgement while a view is being captured. The constant has one home when the publisher uses it; the coordinator's settings hold a copy today.
- **No LIST.** Names are derived: the epoch is the wall clock at writer start, ordinals count up, and a per-node ledger register (`packs/<node>/ledger`) records each epoch with how far collection has got and the highest ordinal seen. The ledger is written when a writer starts packing and when a collection pass moves, never per pack. A node that never packs never writes it. The epoch is the larger of the wall clock and one past the ledger's highest epoch, so a clock that steps back across a restart cannot reuse a name. Ordinals spent by failed writes leave gaps; a collector that probes past the recorded high stops after a bounded run of misses, so a longer run of gaps leaks the packs behind it (to be decided with the collector, as is who collects the packs of a node that never returns, since nodes own nothing).
- **Streaming.** A pack is a PUT body made of the header and each part's source, pulled through one 64 KiB buffer: no pack is held in memory (asserted by a counting-allocator test over a 64 MiB pack).
- **A switch, `serverless.segments.node_pack.enabled`, default off** in this repository until the R11 exit measures, under the emulator with latency, what the Java measured: PUT-class requests per publish down, cold open and warm search within 5%, takeover within the bar the owner set. The flip is its own PR. With it off, publish is unchanged and nothing in this ADR runs; tests pin both values.

## Consequences

- Requests: a publish window of `n` shards is 1 PUT plus its register swaps instead of `n` PUTs plus swaps; the swaps still scale with shards, the blobs no longer do. 0 LIST. A ledger create at first pack, a swap per collection pass that moves it.
- Memory: the batch holds `Part`s (names and open sources) for the shards publishing in one linger. It is bounded by the publish pool, not strictly by `max_pack_bytes` (a part that arrives after the threshold and before the leader wakes still joins); bytes stream.
- Idle indices make zero requests from the writer: nothing runs without a publish. The collector's cost for an idle shard is decided in its ADR.
- Latency: a publish waits up to `linger` for its pack (50 ms default), on its own publishing thread.
- Cost of failure: a failed pack fails every publish in it; each retries on its next publish. A spent ordinal is never reused.
- Collection is a separate decision and must exist before packs are on anywhere: until then the switch stays off, so no pack is ever written that nothing can delete.
- A leader that fails while writing must not strand its batch: the followers' answers are dropped with it and they get an error, never a wait (tested with a source that panics).
- Rules out: a per-shard pack, packs keyed by anything but computed names, a LIST to find packs.
