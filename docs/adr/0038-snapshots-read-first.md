# 0038: Snapshots arrive read-only first, over the shell's records, behind a switch

**Status:** Accepted after independent review, 2026-11-24 (two rounds by a separate subagent given the ADR, the spec and the Java; round one found the state source, the released-register order, the memory bound, the listing bound, name checks and the cost table; round two the order of the name checks and the long-key rule, both answered below)

## Context

The shell keeps repositories and snapshots in the deployment's own object store ([R14](../roadmap.md)): a repository is a record `repositories/<name>`; a snapshot is a record whose current state sits in a CAS register `snapshot-states/<sha256 of "<repo>#<name>">` (a name's lifetime is a unique storage generation; the register holds the record, a discovery marker and a finished flag), with a discovery marker blob under `snapshots/` that a list walks. A standard snapshot copies shard blobs under `snapshot-data-v2/<generation>/<index>/<shard>`, a shallow one references the live shard's blobs. A Rust node shares the bucket with Java nodes, so whatever it writes the Java must read, and whatever the Java wrote it must read. The janitor already reads snapshot records for their pins ([janitor-snapshot-pins](../specs/janitor-snapshot-pins/SPEC.md)); nothing else does.

Taking, restoring and deleting a snapshot touch the write path, shard blobs, pins and index creation. Reading does not. Doing the read side first gets the format right against the Java's own records before anything can write one.

## Decision

- **Slice one is read-only:** `GET /_snapshot`, `GET /_snapshot/{repo}`, `GET /_snapshot/{repo}/{snapshot}` (one exact name, `_all` and `*` refused for now) answer from the shell's records. `PUT`, `DELETE`, `_restore` and the snapshot create route answer `501 unsupported_operation` with a reason naming the slice. Nothing here writes a blob, so a Rust node cannot corrupt a Java snapshot; the legacy-record adoption the Java does on a read (creating the state register) is not done: a legacy record is read as it is.
- **Switch:** `serverless.snapshots.enabled`, default false, a node setting. Off, the routes are not registered (the pre-change 400 answer for an unknown route) and no request is made. It turns on by default only in a PR of its own when a mixed-fleet read of a Java snapshot has been measured, per the switch rule; it has no downside while read-only (no request unless asked) but the answers need the Java records of a live deployment to be verified first.
- **Formats** are the Java's, read strictly and written nowhere: `RepositoryDescriptor` (`name`, `type`, `created_at`, `settings`), `SnapshotRecord` (the fields `SnapshotRecord.fromStream` takes, including `storage_generation`, `shallow`, per-index `uuid`, `number_of_shards`, `mapping`, `settings` and per-shard `term`, `files`, `lengths`), and the state register's value (a vInt-prefixed marker string, a vInt-prefixed record, a boolean; the released form `{"_released":true}` reads as no snapshot). Fixtures are recorded Java outputs under `fixtures/snapshots/`, as for the bucket manifests.
- **What a read answers, from the record.** A snapshot's `state` is `IN_PROGRESS` when the record says so (an index with `number_of_shards > 0` and no captured shards, the Java's `SnapshotRecord.inProgress`), else `SUCCESS`; the register's finished flag is not read for the answer, as the Java does not. The answer is the Java's shape: `{"snapshots":[{...}]}` with the fields `SnapshotOperations` writes, `shards.total` and `successful` the sum of the captured shards and `failed` 0.
- **Lookup order.** The state register `snapshot-states/<sha256 hex of "<repo>#<name>">` first. Present and released: no snapshot, and no fallback. Present and held: its record, whose key must equal `<repo>#<name>`. Absent: the legacy blob `snapshots/<repo>#<name>`, whose own key must equal the same; absent too: no snapshot. This order matters in a mixed fleet: the Java releases the register before it deletes the marker, so a fallback after a released register would show a deleted snapshot. Nothing is cached between requests. The discovery marker's body is never the truth (it is never rewritten when a snapshot finishes); the register is.
- **Names.** In this order: first the non-exact forms are recognised, `_all`, `_current`, any name containing `*` and any list containing `,`, and answer 501 `unsupported_operation`, for the snapshot and the repository alike (`/_snapshot/_all` and `/_snapshot/a*` are never read as an exact name). Then the shell's `Names.validateId` and the `#` check run on what remains, before any request, and answer 400 `invalid_snapshot_name_exception` (the key is `<repo>#<name>`, so `a#b`/`c` would collide with `a`/`b#c`). The register is always read first, whatever the key's length (its own key is a 64-character hash); only the legacy blob read is affected by a key past 255 bytes, which the Java guards with a LIST and an fs store cannot name: Rust makes no LIST and answers a missing legacy blob (or its "name too long" error) as no snapshot. A long-key snapshot held in a register is served.
- **Bounded memory.** A snapshot record and a register value are read through a buffer reserved from the request-body pool at `MAX_SNAPSHOT_RECORD_BYTES` (16 MiB, as a point-in-time record is); a value that does not fit answers 500 `snapshot_unreadable` naming the limit, never a partial read. The record is parsed as a summary (no files copied; a `shards` entry is counted and checked, not kept). A repository record is capped at 1 MiB.
- **Cost, no LIST on the common path:** `GET _snapshot/{repo}`: 1 GET (a 404 is `repository_missing_exception`; the Java spends a HEAD and a GET). `GET _snapshot/{repo}/{name}`: 1 GET when the register holds or released it, 2 when it is absent (the register, then the legacy blob; a missing snapshot costs 2), and a legacy snapshot 2. `GET _snapshot` lists the repositories container: one LIST per 1,000 keys and 1 GET per repository, the Java's listing. A LIST is unavoidable here: the Java writes no index of repositories, so an index document would be a Rust-only write the Java never updates and would drift as soon as a Java node registers one; adding it needs a Java change and its own ADR, and the cost is a request the caller makes rarely, never a timer (a repository is operator-registered and human-scale, a request the caller makes and never a timer; the listing carries `// LIST:`), refused with 500 `too_many_repositories` once 257 keys are seen (the listing stops there, a deliberate deviation from the Java, which has no cap) so the fan-out is bounded. An unreadable repository record is omitted, as in the Java. Listing the snapshots of a repository (`_all`) is not in this slice: it is two LISTs (`<repo>#` and `v2-<sha256 repo>#`) and no GET a v2 snapshot beyond its register, which a later ADR decides with its budget row.
- **Placement:** record parsing in `oss-format` (`repository_record.rs`, `snapshot_record.rs`; `snapshot_pins.rs` stays the pins' reader and reuses the new parser later), the store reads in `oss-meta`, the routes in `oss-node` as the other admin routes are. No new crate in this slice; the take and restore slices decide `oss-snapshot`.

## Consequences

Easier: the formats are proved against the Java's records before anything writes them; the coordinator's snapshot admin surface starts answering for deployments that Java nodes snapshot. Harder: `_all` and repository registration are visibly missing, and clients that PUT a repository first get a 501 until the write slice. Ruled out: a Rust node adopting legacy records (a write) on read.

## Open for the write slices

Native repository type only (`fs`, the shell's `TYPE_NATIVE`); others refused with the Java's `unsupported_repository_type`. A restore must register snapshot pins with the janitor and create the index under a new uuid.
