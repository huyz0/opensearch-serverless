# 0039: Repositories are registered and removed over REST, the Java's way, before snapshots are taken

**Status:** Accepted after independent review, 2026-11-24 (one round by a separate subagent given the ADR, the spec and the Java; it found the check order, `verify` as a URL parameter, the settings text form, comma lists on delete, the delete scan's prefixes and per-key reads, the orphan and race consequences, and the verify answer, all answered above)

## Context

[ADR 0038](0038-snapshots-read-first.md) made repositories and snapshots readable. The next piece with no shard data in it is the repository itself: `PUT`, `POST` and `DELETE /_snapshot/{repo}` in the shell's `RepositoryHandler` and `RepositoryStore`. A repository is one blob, `repositories/<name>`, which a Java node and a Rust node both read. Taking, restoring and deleting snapshots write shard blobs and pins and are separate decisions.

## Decision

- **Switch:** the routes are served under `serverless.snapshots.enabled` (ADR 0038); a second switch is not added, because registering a repository writes one small blob and changes nothing else. With the switch off the routes are not registered, as before.
- **`PUT`/`POST /_snapshot/{repo}` is an upsert**, as the Java's: one PUT of `repositories/<name>`, the record `{"name","type","created_at","settings"}` with `created_at` the node's clock in milliseconds, rewritten on each registration. No read first, no condition: two callers registering one name is the operator's coordination, as in the Java. 1 PUT.
- **Request, in the Java's order.** (1) `POST /_snapshot/{repo}/_verify` is recognised first (below). (2) A name starting with `_` other than `_all` answers 501 `not_implemented` ("repository names beginning with an underscore are reserved for APIs"), before the body is read. (3) The name goes through `Names.validateId` (400, so `_all` and any other rejected name answer 400 in validateId's words; the read slice's `check_name` is that port). (4) The body, an object, is read: `type` defaults to `fs`, and any other type answers 501 `unsupported_repository_type` in the Java's words; then `crypto_settings` answers 501 `unsupported_repository_setting`. `settings` are stored as the Java's `Settings` flat form: every scalar becomes text (`5` is stored `"5"`, `true` as `"true"`), a nested object becomes dotted keys, an array stays an array of text; fixtures cover each form. The key order of `settings` in a record is not fixed by the Java (`Map.copyOf`), so records are compared by content, not bytes. `verify` is a URL parameter in the Java (default true) and a no-op here: there is one store. The body is bounded at 1 MiB (the record's read limit) through the request-body pool (429 on a failed reservation): these two bounds are Rust-only, deliberate divergences. The Java also calls `PutRepositoryRequest.validate()` (a missing name); the route always has a name, so it is not reachable.
- **`DELETE /_snapshot/{repo}`.** The name is split on commas, as the Java does, and each name is deleted in turn; every name is validated first (`validateId`, so `_all` and `_x` answer 400 as in the Java, and a pattern is refused with the "repository mutations require concrete repository names" 400), so no name is deleted when another is refused. A name not registered answers 404 `repository_missing_exception`; one that holds a readable, held snapshot answers 409 `repository_in_use`; otherwise the blob is deleted. The existence check is a GET of the record (the Java's `blobExists` is a HEAD; one request either way, and a Rust read of the record also proves it parses, but an unparseable record is still deleted). The in-use scan is the Java's `SnapshotStore.list`: two LISTs (`snapshots/<repo>#` for the legacy layout and `snapshots/v2-<sha256 of repo>#` for the current one), merged, then per key a read of its register (a legacy key then its marker blob). A snapshot is held when its record is present, its marker matches and its repository equals this one; a released, mismatched, missing or unreadable one is omitted, as the Java omits it, so a corrupt snapshot does not block the delete and is left orphaned. The Rust scan stops at the first held snapshot (409), where the Java reads every key, and refuses with 500 `too_many_snapshots_to_check` once more than 1,000 keys are seen across both prefixes (the Java has no cap; a deliberate bound on fan-out). An empty repository costs 1 GET, 2 LISTs and 1 DELETE. A LIST is unavoidable: the Java keeps no per-repository count, and an index document would be a Rust-only write the Java never updates. It is an operator action, never a timer, and carries `// LIST:`. A snapshot taken between the scan and the delete is not prevented, as in the Java: the delete then orphans it, and a lock is forbidden by the invariants.
- **`POST /_snapshot/{repo}/_verify`** is checked before the `_` rule, so `_x/_verify` answers 400 from `validateId`. It answers 404 `repository_missing_exception` for an unregistered name, and otherwise 200 `{"nodes":{"<node id>":{"name":"<node name>"}}}` for this node. Cost: 1 GET (the Java spends a HEAD and a GET); a record that cannot be parsed answers 500 `repository_unreadable`.
- **Idempotent, visible:** a repeated `PUT` of the same body answers 200 and rewrites the blob; a `DELETE` of a name already gone answers 404.
- **Answers:** `{"acknowledged":true}` with 200.
- **Placement:** the record writer in `oss-format` (`RepositoryRecord::to_bytes`, tested against the record the Java wrote), the store writes and the in-use check in `oss-meta`, the request decisions in `oss-coordinator`'s `snapshot_admin`, the routes in `oss-node`'s `snapshot_route`, replacing the 501 handlers for these paths only.

## Consequences

Easier: a deployment can register its repository from a Rust node, and the repository's registration is proved byte-compatible with the Java in both directions before snapshots write anything. Harder: a delete's in-use check costs LISTs, the price of the Java's format. Snapshot creation, restore and snapshot deletion stay 501.

## Alternatives rejected

- A repository-count index document: a Rust-only write, stale as soon as a Java node writes a snapshot.
- Refusing re-registration: the Java upserts, and clients written against OpenSearch send repeat `PUT`s.
- Deleting without the in-use check: leaves snapshots naming a repository that cannot be read.
- A second switch: no downside to separate.
