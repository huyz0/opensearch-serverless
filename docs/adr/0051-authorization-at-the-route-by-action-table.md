# 0051: Authorization is decided at the route, from an action table, by the names in the path

**Status:** Accepted after independent review, 2026-11-24 (its findings are folded into the text above)

## Context

[ADR 0043](0043-security-configuration-as-document-sets.md) puts authentication in front of every request and left authorization to a later slice, sketched as a trait in the coordinator's index resolution, after aliases and wildcards are resolved to concrete indices. The stock plugin decides on resolved names: a request through an alias, or a wildcard, is allowed when every index it resolves to is allowed.

Resolution here is per index and sits behind the coordinator's reads (descriptor lookups that cost store requests). Putting the decision there would make an allowed or refused answer depend on store reads, put the check in every handler, and make the table of which handler checks what impossible to enumerate. The forces are the same as for authentication: no store request on the request path for the check, deny by default, and a rule that can be a predicate over files is a check, not a sentence.

## Decision

- The router knows each route's action. A route is registered with the stock action name (`indices:data/read/search`, `cluster:admin/settings/update`, ...) and where its indices come from (a path parameter, or nowhere). After the route is found and before its handler runs, an `Authorizer` on the router decides from the principal, the action and the index names in the path, and may refuse with its own answer. The decision is a read of the node's snapshot and nothing else: no store request.
- The decision is pure and lives in `oss-coordinator` (`security/authz`): a user's permissions are the union over its roles of `cluster_permissions` and `index_permissions`, with action groups expanded to any depth (a cycle ends; a name that is not a group is an action), built-in action groups and roles shipped as data from the stock plugin's static configuration, and the plugin's wildcard rule (`*` any run, `?` one character, `${user.name}` substituted).
- **Names are matched as written, not resolved, after one decode.** The index path parameter is percent-decoded once, by the decode the handler uses, split on `,`, and each element must be covered by a pattern of a permission that grants the action: an empty element, or one starting with `-` or `+`, is refused, `_all` is read as `*`, and a `*` of a pattern never spans a comma because the list is split first. A wildcard in a request element (`*`, `?`) is a wildcard of the request: a pattern covers it only if it matches every string the request stands for, so `a?` does not cover `a*` and only `*` covers `*`. A user name holding `*` or `?` voids a `${user.name}` pattern.
- **A request through an alias needs a permission on the alias name, and that permission then reaches whatever the alias points at.** This is looser than the plugin in one direction (a name granted by pattern can be made an alias of an index the user was not granted, by a user who may write aliases) and stricter in the other (an alias or wildcard that would resolve to allowed indices only is refused). Aliases are made by `indices:admin/aliases`, which has no row and so needs `all_access`; a role granting alias management on a pattern is a role granting everything the pattern's names can come to point at, and is documented as such.
- **Routes whose indices are in the body, or that touch two index sets, are `all_access` only**: `_bulk`, `_msearch`, `_mget` and their `/{index}/` forms (the path index is only a default), `_search` without an index, scroll and point-in-time ids in use, `_reindex`, restore, `_delete_by_query`, aliases, templates, ingest pipelines, `_cat`, `_cluster/state` and every route that lists index names, and every prefix (plugin) route. A `_bulk` also needs the cluster permission `indices:data/write/bulk`. A search body that reads another index (a `terms` lookup) is not checked; it is the plugin's own gap and is documented.
- **The check sits immediately after the route is found**, before the content-type, parameter and body checks, so a refused request spends no body buffer and learns nothing from a parameter error; a refused request that carries a body closes the connection, as a guard refusal does. Methods answered without a handler (`OPTIONS`, 404, 405) are covered by authentication only.
- **The table is complete by test and everything it does not hold is `all_access` only.** `Router::routes()` lists every registered method and pattern (a prefix route as any method), and a test fails if one has no row; a row is `Open`, a cluster action, an index action or `AllAccess`. A missing row at run time is `AllAccess`, so the test guards usability and the default guards safety. `all_access` here means the cluster permission `*` and an index permission over `*` granting `*`.
- The refusal is the recorded 403 `security_exception`: `no permissions for [<action>] and User [name=..., backend_roles=[...], requestedTenant=null]`.
- No separate switch: authorization is on whenever `serverless.security.enabled` is. A node that authenticates and does not authorize is the open door this closes.

## Consequences

- This replaces the sketch in ADR 0043 (a trait in the coordinator's index resolution): the decision is at the route and reads no store. A request the plugin allows through an alias or wildcard may be refused here until the user is granted the name; an alias made onto an index reaches it for whoever holds the alias's name (above). Resolving names later would need its own ADR and its own request budget.
- Limited users cannot use `_bulk`, `_msearch` or `_mget`; per-item checks need the body parsed before the decision and are not done. They can search, count, read and write single documents, and create, delete and read the indices their patterns name.
- Tenants, document-level and field-level security, and `/regex/` patterns are not enforced; a role using them is read for its actions and indices only.
- Adds a data file (the stock static action groups and roles) and a router API (`routes()`, an action on a route, an `Authorizer`).
