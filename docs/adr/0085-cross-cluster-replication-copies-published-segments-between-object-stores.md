# 0085: Cross-cluster replication copies published segments from the leader's object store; it does not pull operations

**Status:** Proposed. Design only: no code, no setting, no route exists. Accepted after an independent review (rule: [ADR README](README.md)); the slices that follow are listed in "Slices" and each needs its own spec.

## Context

The stock plugin (`opensearch-project/cross-cluster-replication`, checked out as `huyz0/cross-cluster-replication`; its design is `docs/RFC.md`) replicates an index from a leader cluster to a follower in four moves: a remote-cluster connection over the transport, a retention lease on each leader shard so the translog is not trimmed, a bootstrap by snapshot restore through the leader exposed as a repository, and then per shard a long poll that fetches translog operations in sequence and replays them on the follower's primary, with `IndexReplicationTask` and `ShardReplicationTask` as persistent tasks in cluster state. The follower index is write-blocked until `_stop`.

None of those pieces exists here, and each assumes something this build does not have:

- **No translog to pull.** Writes land in one write log per node, not per shard ([principles](../principles.md#write-path)); acknowledged operations are folded into immutable segment blobs that a commit publishes. A leader node holds no per-shard operation history that a follower can ask for, and nodes own nothing, so there is no leader shard copy to long-poll.
- **No cluster state, no persistent tasks, no retention lease.** There is no master. A lease would be a lock, and the invariants forbid one for correctness.
- **A remote cluster is an object store.** The only durable tier of the leader is its bucket; a follower that can read it needs no leader node at all. That is a stronger disaster-recovery property than the stock plugin has (a stock follower needs a live leader to make progress), and it is what the design should keep.

Forces: requests scale with nodes and bytes, never with records or with elapsed time per index; LIST is priced like a PUT and is banned on read, write and startup paths; no data-dependent chain of fetches on a user path; memory is reserved before it is held ([ADR 0004](0004-bounded-memory-and-streaming.md)); a feature with a measured downside is a setting; the owner's rule that no Java is in the runtime path, so the Java plugin is a reference for the API and a test oracle for the API only.

## Decision

**Replication is segment-level and pulled by the follower.** A follower index is kept equal to the leader's last *published* state of each shard by copying the immutable segment blobs the leader's shard manifest names that the follower lacks, then landing the follower's own manifest. The same copy that bootstraps ([ADR 0045](0045-shallow-snapshot-restore.md)'s streaming ranged read into a streaming write, with the Lucene footer check of [ADR 0060](0060-stock-snapshot-restore-reads-a-source-repository.md)) is the steady state: the bootstrap is the first iteration of the loop, not a second mechanism. There is no operation stream, no sequence number to reconcile and no replay.

1. **A remote is a store location, not a transport seed.** `PUT _cluster/settings` with `cluster.remote.<alias>.store` (an `s3` bucket and prefix, or an `fs` root for a single host) names the leader's store and the read-only credentials this node already has or a named profile of them. The leader's bucket and prefix must fall under an operator allow-list (`OSS_REPLICATION_REMOTE_ROOTS`, empty by default: nothing is readable until an operator names a root), checked by the same validators as the stock-repository roots (`OSS_STOCK_REPO_ROOTS`, `OSS_STOCK_REPO_S3_ROOTS`), reused, not copied: canonical, no symlink, no overlap with this deployment's own store in either direction. The follower holds read credentials and **writes nothing to the leader's store**; the leader runs no replication code and needs no node to be up. Seeds in `cluster.remote.<alias>.seeds` are accepted and ignored with a warning in the response, so the stock `PUT _cluster/settings` body works unchanged.
2. **The unit of replication is the shard manifest.** The follower reads the leader shard's manifest register (the compare-and-swap blob that names its published files, as the snapshot take and ADR 0045's restore read it), compares its generation to the one it last applied, and for a newer one copies each file the follower does not hold, then lands the follower manifest by compare-and-swap. Files are immutable and named by their content's term directory, so a copy is idempotent, a crashed copy is a retry of the same bytes, and the order is files first, manifest last: a follower reader never sees a manifest whose files are absent. No operation is replayed, so the follower's `_seq_no` is not the leader's; `_version` and `_id` are, because they live in the segments.
3. **What is replicated is what the leader has published.** A write the leader acknowledged but has not yet published (it is in the node log and the tail overlay) is not visible on the follower until a commit publishes it. The follower's lag therefore has two parts, the leader's publish interval and the follower's poll interval, and the stock plugin's "a few seconds" is a target the design does not promise. This is the measured downside; the spec's budget states the numbers once they are measured, and they are `provisional` on an emulator ([principles](../principles.md)).
4. **Polling is per replicated shard, with a floor, a backoff and a cap, and costs nothing for an index that is not replicated.** The follower must find out a leader manifest changed, and the only read that tells it is the manifest, one GET (or a conditional GET on the etag, where the store has one, answered 304 with no body). To keep "requests do not scale with elapsed time per index" true for everything except the indices a person opted in, the poll interval for one shard starts at `serverless.replication.poll_floor` (default 5 s, lower bound 1 s), doubles after each unchanged answer up to `serverless.replication.poll_cap` (default 60 s) and returns to the floor after a change. A replicated, idle shard therefore costs about 1 GET a minute; a busy one up to 12 a minute. The cost is the product of replicated shards and polls, stated beside the setting, bounded by a per-follower-cluster cap on replicated shards (`serverless.replication.max_shards`, default 2,000, 429 `replication_limit` beyond it), and charged to the follower's tenant. Only the first owner of a shard by the placement hash polls it; the second polls only after the first's last applied time is older than three intervals, so idle cost is one GET per poll, not two. The default cap of 2,000 shards at the 60 s ceiling is about 2.9 million GETs a day, stated beside the setting. `_start` runs its bootstrap as a background task ([ADR 0063](0063-a-restore-may-run-in-the-background.md), [ADR 0072](0072-tasks-are-node-local-memory-with-no-blob-requests.md)), never in the request, and one poll copies at most `serverless.replication.max_poll_bytes` (default 1 GiB) and resumes next poll. A change feed on the leader (a per-cluster marker bumped on commit) would make the poll one GET for all indices, but it costs a PUT on every leader commit for every leader, replicated or not; that is the wrong side of the trade and is rejected below.
5. **No lease, no lock, no leader election.** Two followers of one shard owner racing is harmless: both copy the same immutable bytes and the manifest swap is a compare-and-swap from the generation each read, so one wins and the other re-reads and finds the work done. A node that is paused or partitioned is already safe by the same fencing.
6. **Retention is the leader's janitor grace, not a lease.** Nothing on the leader pins a segment a follower has not copied. A leader merge retires a segment after the janitor's grace; a follower that falls further behind than that finds a file missing, copies nothing from the stale manifest, re-reads the manifest, and if the files it needs are gone **re-bootstraps that shard** from the current manifest (a full copy of the current files, counted in `follower_stats.bootstrap_count`), at most 3 times in an hour with doubling backoff, after which the shard is `paused` with reason `cannot_keep_up` in `_status` until `_resume`, so bytes cannot scale with elapsed time unbounded. Correctness is never at risk, only the bytes copied. The length of that grace is the reclaim delay the janitor already has ([ADR 0012](0012-index-deletes-and-reclaim.md), [ADR 0020](0020-janitor-crate.md)); its minimum unreferenced age defaults to 60,000 ms (`MINIMUM_UNREFERENCED_MILLIS`, `crates/janitor/src/settings.rs`) on top of the janitor's two sightings, which is close to the 60 s poll ceiling, so slice 3's spec must either raise the follower's read-ahead or set a replication-aware reclaim age, and measure it. It is the one place the design could pin leader data, and an optional follower-written pin was considered and rejected below.
7. **Metadata follows the manifest.** The index's mappings and the settings the follower is allowed to take (`index.number_of_shards` fixed at start; analysis, mapping and dynamic settings follow the leader; `index.replication.*` and `index.blocks.*` are the follower's own) are read from the leader's index descriptor on the same poll cadence, as one GET per replicated index when any shard changed, and applied by the descriptor's compare-and-swap. A mapping the follower cannot hold is a `paused` state with a reason in `_status`, not a failure of the shards.
8. **The follower index is write-blocked by an index block**, not by a task: the descriptor carries `index.blocks.replication` and the write path refuses with 403 `cluster_block_exception` naming it, as the stock plugin does. `_stop` clears the block (the index becomes a normal writable index; replication stops, the data stays). A `_start` on an index that exists and is not empty is 400, as in the stock plugin.
9. **State is documents, per follower tenant.** A replication entry (alias, leader index, follower index, state, per-shard last applied generation and last copied time) is a document under `replication/<tenant>/`, written by compare-and-swap in the stored-scripts shape ([ADR 0073](0073-stored-painless-scripts-resolve-through-a-ttl-cache.md)): `_start` is 1 GET + 2 PUT plus the bootstrap, `_status` reads the document (2 GET), and a polled change updates the shard's generation by one swap. Auto-follow rules (`replication/<tenant>/autofollow`, same shape) are matched against the leader's index list. **The leader's index list is not discoverable without a LIST**, so auto-follow takes the leader's index registry where one exists as a key the leader already maintains and otherwise is refused 501 `autofollow_unsupported` with that reason; the spec decides which. It is not made to work by an unmarked LIST.
10. **Stats and routes** follow the stock API (`/_plugins/_replication/{index}/_start|_stop|_pause|_resume|_status|_update`, `_autofollow`, `follower_stats`, `leader_stats`, `autofollow_stats`). `leader_stats` answers `501` honestly, because the leader keeps no replication state in this design (nothing on the leader knows it is followed); the response says so. `_status` reports `bootstrap` then `syncing` with each shard's lag in generations and in seconds since the leader manifest was last seen.
11. **Security.** Start and stop need the index-level actions the stock plugin defines, mapped in the action table of [ADR 0051](0051-authorization-at-the-route-by-action-table.md); the store credentials are the node's, never a request's. Two clusters under different security configurations are different tenants of the follower; the follower copies bytes the leader's store policy already lets it read, so the leader's index-level security (document and field level) is **not** applied to the copy. That is a stated limit, refused rather than silently weakened: starting replication of an index the leader marks with document or field security is 400.
12. **Where it lives.** A new `oss-replication` crate (layer 3, peer of reader, writer and janitor, depending only on `oss-blob`, `oss-format`, `oss-meta`, `oss-cluster` and `oss-types`; it never depends on reader or writer, which the layering check enforces) holds the copier, the poll schedule and the document store; `oss-node` mounts the routes and runs the poll thread. It is first-party and linked in. [ADR 0080](0080-one-plugin-system-three-tiers.md)'s tiers are not used: the work needs the store handle and the manifest register, which a loaded plugin never has.

**Behind a setting.** `serverless.replication.enabled` (`OSS_REPLICATION`), default **off**: it adds a standing poll cost an operator should choose. The setting is cluster-wide and an index is replicated only by an explicit `_start`, so "off" is also what makes an unreplicated index's cost zero. It flips on by default only when the measurement in the spec shows a replicated, idle shard at no more than the 1 GET a minute above and the leader's write p99 unchanged (it is unchanged by construction: the leader does nothing).

## Consequences

- Easier: a follower survives a dead leader and bootstraps from a quiet bucket; no leader code path, no task state, no lease to leak; one copy loop for bootstrap and steady state; cost and failure modes are the ones of snapshot restore, which is built and measured.
- Harder: lag is bounded below by the leader's publish interval; the follower holds no leader sequence numbers, so an operation-level consumer (a stock follower of a Rust leader, `_seq_no` based reads) cannot be served; a leader's document and field security does not travel; a follower more than the janitor grace behind pays a full bootstrap; two buckets under different accounts need the operator's read grant.
- Rules out: replicating into a stock follower from a Rust leader or the reverse (a Java follower needs translog operations, which a Rust leader does not keep); bidirectional or active-active replication; replicating a single shard or a subset; a retention pin on the leader.

## Alternatives considered

- **Port the stock design: ship translog operations.** Needs a per-shard operation history that this build deliberately does not keep (one log per node, folded into segments), a leader node for every read, a retention lease (a lock), and persistent tasks. It would reintroduce all four things the architecture removes. Rejected.
- **A change feed on the leader** (a per-cluster marker bumped on every publish, followed by one GET). Makes polling one read for all indices, but each leader commit pays a PUT whether or not anything follows it: a cost on the write path of every leader, for the benefit of the replicated few. Rejected. Revisit if replicated indices become the common case.
- **A follower-written pin on the leader** (a small blob naming the generation a follower holds, honoured by the janitor). Removes the re-bootstrap case, but makes the leader's store writable by followers and makes reclaim wait on a follower's health (a stuck follower pins the leader's storage without bound). Rejected for now; the grace is bounded and its overflow is a cost, not a loss.
- **Run `copy_from`-style shallow restore on a schedule.** A restore into the same index is refused by [ADR 0045](0045-shallow-snapshot-restore.md) and rewrites every file; the incremental loop is the same code with a manifest diff in front of it, so no second mechanism is kept.
- **An in-process Java sidecar running the stock plugin.** Rejected by the owner's rule: no Java in the runtime path.

## Slices

Each is one PR with its own spec, started only after this ADR is accepted. All run in the cloud against the emulator and RustFS.

1. **Remotes and the store reader**: `cluster.remote.<alias>.store`, the allow-list, a read-only remote store handle, `GET` of a leader manifest and descriptor; no copying.
2. **Bootstrap**: `_start` creates the follower index, copies the files, lands the manifest, sets the block; `_status` and `_stop`; the budget rows.
3. **The poll loop**: schedule, backoff, cap, the manifest diff, the incremental copy, `_pause`, `_resume`, `_update`, `follower_stats`; the re-bootstrap on a retired file.
4. **Metadata**: mapping and settings following.
5. **Auto-follow**, once the leader's index registry question is settled by its spec.
6. **Measurement**: lag, idle cost and bootstrap bytes on RustFS; decides the default of `serverless.replication.enabled` and fills the numbers this ADR leaves open.

A slice that changes a shared blob format (the descriptor's block, the replication document set) is risk-tier high and waits for the owner's go.
