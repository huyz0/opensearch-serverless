# 0015: A cluster crate beside the metadata crate, and node leases on registers

**Status:** Accepted after independent review, 2026-11-16.

## Context

The roadmap's stage R4 makes a Rust node a member of a fleet, Rust or Java: it joins by a lease blob, every node computes the same shard owners (placement) and the same document routing as the Java. Membership, placement and routing are needed by the writer (who owns which shard), the reader (where to send a search), and the coordinator. The layering forbids the reader and the writer depending on each other, so the code belongs below both.

The Java shell keeps membership in `serverless/shell/.../membership/` (`BlobLeaseMembership`, `NodeLease`, `LeaseDigest`), placement in `cluster/` and routing in `routing/`, all over the same registers [ADR 0007](0007-registers.md) ported. A node writes its own lease register under `cluster/members/lease-<id>` and renews it by compare-and-swap; a members index (`cluster/members/members`) names every member, so a refresh is a read instead of a listing; and the live member with the lowest id writes every live lease into a lease digest (`cluster/members/members-digest`) each third of a lifetime, so the rest read one register instead of each lease. Measured on the emulator with a simulated clock (`crates/cluster/tests/leases/budget.rs`), an idle hour of three nodes renewing and refreshing every 10 s costs the digest writer 720 swaps (360 renewals and 360 digest writes, the Java's number) and 1,800 reads, every other node 360 swaps and 539 reads, and nobody a LIST.

## Decision

- **A new crate, `oss-cluster`, at layer 2 beside `oss-meta`**, depending on `oss-blob` and `oss-format` only. It owns membership now (`lease`), and placement and routing next (R4.2, R4.3). Not in `oss-meta`: that crate is the names namespace (descriptors, aliases, tombstones) and its rule is "no lease"; membership is a different concern with a different writer population (every node writes its own register, continuously). Placement and routing are pure computation over the leases and the index records, and need nothing from `oss-meta`.
- **The records are `oss-format`'s**, written byte for byte as the Java's `NodeLease.toBytes` and `LeaseDigest.encode` (recorded by the Java's own classes in `fixtures/node-leases/`), so Rust and Java nodes read each other's leases.
- **The protocol is the Java's, ported unchanged:** renewal by compare-and-swap against the generation last written; a revoked lease of this process is not written over (`Revoked`, which the caller treats as a lapse); another live process under the id at another address is a duplicate and refused; the same address is a fast restart and taken over; the holder trusts its own lease until its expiry less `ttl / 32`; a taker revokes a dead owner's lease before taking its shard; a refresh prunes a lease gone from the store, or dead for ten lifetimes and naming no write-log epoch. No lock, lease service or leader is added: fencing is the register's compare-and-swap, as everywhere. The `ttl / 32` margin is for liveness only (a holder stops before a taker starts); a lapsed holder's writes are fenced by the conditional creates and swaps on the write log and shard heads, which it loses to its successor, never by a clock bound.
- **No LIST, where the Java lists once.** The Java builds a missing members index from a listing of `lease-*`, for deployments from before the index. Rust creates a missing index naming the enrolling node instead. Every Java node at the ported revision writes the index when it joins, so a fleet the Rust nodes join has one.
- **Bounded:** a lease is at most 2 KiB (about twenty write-log epochs; a longer Java lease is refused, which a refresh treats as not live and a liveness check as alive, the safe answer for each), a node id at most 128 bytes, and a node's index and digest buffers are sized for `max_members` (512 by default: a fleet is hundreds of nodes, and past that another fleet), taken once: about 1 MiB of digest buffer, and at peak about 2 MiB a node with the decoded digest and the two index buffers. A digest entry past 2 KiB is skipped, not a reason to refuse the whole digest, so one long Java lease costs only its own reads.
- **Whether conditional deletes were verified is a constructor argument too**, supplied by the node from its probe of the store; this crate does not depend on `oss-meta`'s probe.
- **The lifetime is a constructor argument** (the Java's 30 s default) until a node runs a lease; a setting comes with the node wiring.

## Consequences

- Rust nodes and Java nodes on one bucket see each other in membership, and a Rust node can take part in a Java fleet's shard takeovers once the writer ports them.
- An idle node's membership costs what the Java's does, recorded in [request-budgets.md](../request-budgets.md) as exact rows, so a regression fails the gate. The digest writer pays 360 more swaps an hour than the others, the price of the rest reading one register.
- A fleet larger than `max_members` cannot be held in one node's buffers: the digest is then not written (readers fall back to reading leases) and enrolment past the index's bound fails. Raising it costs about 2 KiB a member a node.
- A Java deployment from before the members index is not joined until a Java node at the ported revision has written the index.
- Pruning never removes a lease that names write-log epochs: that lease is the only place a successor finds them. The price is that every node reads such a dead lease on every refresh until the successor that took the epochs calls `forget_node_log` (the writer, when its takeover has replayed them; ported with the writer), as the Java does.
- A Java lease longer than 2 KiB (more than about twenty epochs) is not live to a Rust refresh and is live to a Rust liveness check, so Rust nodes never take over that node's shards; a Java node still can. The Java bounds no lease; capping its epoch count is left to the Java.
- Cost grows linearly with the fleet, measured on the emulator over an idle hour (provisional): the digest writer reads `360 × (N + 2)` registers (4,320 at 10 nodes, 72,720 at 200, about 185,000 at 512) and swaps 720; every other node reads 539 and swaps 360 whatever N is. The whole fleet's requests are about 1,260 an hour a node. Each reader fetches the digest, about 300 bytes a member, once a lifetime.
- The members index is one register every joining node swaps: a co-started fleet of hundreds contends on it, and a node whose three enrol attempts all lose retries on its next renewal, 10 s later. Until it is enrolled, refreshes do not see it.
