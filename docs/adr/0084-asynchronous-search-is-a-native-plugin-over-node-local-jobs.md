# 0084: Asynchronous search is a native plugin over node-local jobs; its results are memory only

**Status:** Accepted after independent review, 2026-11-28 (two rounds; the first found ten blocking points and the second three, all folded in).

**Amends [ADR 0080](0080-one-plugin-system-three-tiers.md)**: the sentence of section 5 "There is no background-job capability in v1" and its rejected alternative "a background-job capability now" stand for open-ended jobs (a timer, a schedule, work with no request in flight: that remains the later `schedule` capability), and gain one exception, `job` below, which only runs a search a call asked for and ends with it. Pointers are added in 0080.

## Context

The stock plugin (`/_plugins/_asynchronous_search`, legacy `/_opendistro/_asynchronous_search`) submits a search that may outlive the HTTP call: the client gets an id and a state (`RUNNING`, `SUCCEEDED`, `FAILED`, `CLOSED`, and the persisted states), reads the result by id, extends or deletes it, and reads node stats. With `keep_on_completion` the stock plugin writes the response to a system index. [ADR 0046](0046-plugin-requests-are-proxied-to-java-nodes.md) proxies it to a Java node today; the owner's rule is no Java in the runtime path, so it is ported ([java-dependencies](../java-dependencies.md)). [ADR 0080](0080-one-plugin-system-three-tiers.md) is where ported plugins live.

Forces: a result write is a blob PUT and a read a GET, for something a client reads once or never; requests scale with nodes and bytes, idle indices make zero; memory is reserved before it is held; no lock or lease; the plugin system gives a plugin no thread, no timer, no transport and no blob handle.

## Decision

1. **A native plugin, `plugins/async-search`, on the `rest` point**, routes claimed under the stock prefixes (`/_plugins/_asynchronous_search`, `/_opendistro/_asynchronous_search`, with and without `/{index}`) by the policy's `claim`. It holds no state of its own and starts nothing.
2. **Two host capabilities.** `search` (ADR 0080 section 4) runs the search as the calling tenant. `job` is new and is **data, not a closure**: `job.submit(search_request) -> id`, `job.get(id, wait_ms)`, `job.cancel(id)`, `job.stats()`. The host runs that one search on its own thread through its ordinary search entry and keeps the outcome; a plugin runs no code on that thread, so "a plugin gets no thread" holds. `job` and `identity` are for native plugins (the `rest` point), granted by the policy (`grants: ["job", "identity"]`, with ceilings `max_running` and `max_kept`), and each submit is charged as **one `searches` unit of the submitting call's budget**. A job is not a timer: it starts only because a call asked, ends when its search ends, is cancelled, or passes `max_running_time` (default 10 minutes, the deadline is passed to the search entry at submit and the search's stages compare against it with the cancel flag, so the bound holds with no access and no timer; a hung search's thread cannot be killed, so its slot is held until the thread exits and counts toward the running cap). The registry is ADR 0072's mechanism extended in its own namespace (jobs do not appear in `GET /_tasks`, and `GET /_tasks/{id}` does not answer a job id, nor the reverse; by-query task tests are unchanged): ids `<node_id>:<n>`, a read or cancel of another node's id is relayed over `internal:serverless/tasks/call` to a lease already held (no store request, and the relay carries the verified tenant and user), the drop guard frees a slot on panic, nothing is listed, no timer, limits checked on access (every add or read sweeps the at most 72 entries).
   A waiting call (`wait_for_completion_timeout`, at most 10 s here) is a condvar wait in the host, never a poll. The plugin's `rest` ceiling is 15 s and its policy bulkhead is raised to 16 and 6 per tenant, so two waiting submits (the per-tenant running cap) leave room for a get, a delete and a stats call (5 of 6). A relayed waiting read holds a call on both nodes for its wait.
3. **Results are node memory, never a blob, and are the submitter's.** A job records the submitter's tenant and user (the `identity` capability); a read by another tenant or user is 404, not 403.  No `.asynchronous-search-response` index and no PUT: `keep_on_completion` keeps the result in the registry until `keep_alive` ends, the entry is deleted, it is evicted, or the node restarts. A result is therefore readable only through the node that ran it (its id names it, and other nodes relay) and is lost with that node. The persisted states (`PERSISTING`, `PERSIST_SUCCEEDED`, `PERSIST_FAILED`, `STORE_RESIDENT`) are never reported.
4. **Bounds** (settings with these defaults; each a limit, not a switch): at most 8 running and 2 per tenant (a further submit is 429 `es_rejected_execution_exception`), at most 64 kept results and 32 MiB of them, oldest finished evicted first; a response over `max_response_bytes` (1 MiB) is cut off by a counting writer that aborts at the cap, so it is never held whole: the job ends `FAILED` with `response_too_large`, on a submit that waited as on a later read; a running job holds a reservation of `max_response_bytes` and a kept one its actual size, both from the `Extensions` pool, and each entry adds 1 KiB for its id and state, so the registry is at most 8 MiB running + 32 MiB kept + 72 KiB. Every plugin call also reserves its body and its response ceiling (ADR 0080 section 7), so with the plugin's bulkhead of 16, a request body of at most 1 MiB (`max_request_bytes`) and the 4 MiB response ceiling, the calls add up to 16 x (1 + 4) = 80 MiB on top (waiting calls hold theirs for the wait); the total worst case is 80 + 8 + 32 MiB + 72 KiB; the `Extensions` pool must be sized for both, it is 0% by default so every call is refused until `OSS_EXTENSIONS_PERCENT` is set, and the plugin needs `serverless.plugins.enabled`. A refused reservation is a 429. A running or kept entry's reservation is released by the thread's drop guard when the thread exits (delete and `max_running_time` only mark the job cancelled), never earlier, so the pool never understates what a still-running search holds. A tenant at its own kept cap whose entries are all running gets 429 on submit. One tenant may hold at most half of the kept results (32) and bytes, so eviction oldest-first is within a tenant first. `keep_alive` is at most `max_keep_alive` (default 1 hour, a 400 above it, as stock refuses above its 5 days), and the default is the smaller of 12 hours and that maximum. Expiry is checked on access, never by a timer.
5. **The search is the ordinary search.** Its requests are the reader's: a cold index is 3 GET at depth 3, a warm one 0 ([request-budgets](../request-budgets.md)). Submit, get, delete and stats add none of their own. A running job that is cancelled stops at the next point the search checks its flag (the search's own stages), and a dropped client connection does not cancel a job that has an id.
6. **Switch:** `serverless.async_search.enabled`, default off until the spec's measurements are recorded; with it off the prefixes go to a plugin upstream when one is configured. Not a switch per limit.

## Consequences

- Easier: zero added requests, no durable format, no fencing question, idle nodes spend nothing, and the `job` capability serves any later plugin that needs background work without a thread of its own (ISM's and alerting's native ports do not use it).
- Harder: a result is lost on restart or node loss and read through one node; `keep_alive` is capped far below stock; a client that submitted, restarted nothing and polls another node pays a relay hop. Each is listed in `docs/compatibility.md`.
- Rules out: persisting results (a later ADR would weigh one PUT per kept result against the benefit), cluster-wide stats (this node's only), and a plugin starting its own work.
- The `job` capability is a change to the plugin contract (ADR 0080's catalogue); it is added by its own slice with a golden layout test where the ABI shows it.
