# 0053: The analyzer point: an index pins a WASM module as a named analyzer, in its settings, at creation, and every node that opens the index runs it or refuses

**Status:** Accepted after independent review (three rounds), 2026-11-24

## Context

[ADR 0052](0052-extension-modules-on-a-wasm-abi.md) built the runtime (ABI, host, store, upload route) and wired no point. Its "Not decided here" list is this ADR's checklist. The roadmap expects `analyzer` first because it is the one point whose output is stored: a term built from a document is in a segment for good, so the module that built it must be the module that builds the query's terms, on every node, for the life of the index.

What the Rust nodes do today:

- Only the built-in `standard` analyzer is admitted on a text field (`keyword` exists for `_analyze` and keyword fields only). A mapping naming any other analyzer is refused when it is parsed (`crates/doc/src/mapping/field.rs`, "analyzer [x] on field [y]" as `unsupported`), so there is no silent fallback to remove.
- Analysis runs at these places: the writer's indexing (`oss_doc::lucene`, `Inverted::text`, called from `Shard::index`), the reader's tail overlay (`crates/reader/src/overlay`, which indexes pushed, unpublished documents with `Indexer` and `FastIngest`), the query builders (`match`, `match_phrase`, `multi_match`, `query_string`, `simple_query_string`, and the node's `search`, `count`, `msearch`, `frozen`, `shard` and `validate` paths, each of which builds `Analyzer::standard(None)` today), the highlighter and `_analyze`. A merge and a publish never analyse. The lucene-rust fast ingest plan (`oss_doc::fast`) is built for the built-in analyzers only.
- The node log records the source document, after any ingest pipeline ([ADR 0044](0044-ingest-pipelines-in-the-write-path.md)); replay indexes it again through `Shard::index`. A bulk item is applied to the engine, and so analysed, **before** its record is staged ([ADR 0050](0050-writes-to-one-shard-share-a-commit-window.md), rule 2), so an item whose analysis fails is refused before anything reaches the log.
- The descriptor's `settings` are kept as raw bytes; the Java shell builds an index's analyzers from `index.analysis.*` in those settings (`SharedAnalysis`, `AnalysisRegistry`).

Forces: [add-an-extension-point](../how-to/add-an-extension-point.md) says a point that builds terms is deterministic and imports nothing, an index pins `{module, point, version, sha256}`, and a node without the module refuses the index. Blob requests scale with nodes and bytes, never with documents or queries. Memory is reserved before use. A feature with a downside is a setting.

## Decision

### 1. The point

The point is named `analyzer`, version 1. A call carries **a block of texts** and returns **the tokens of each**. The module analyses each text on its own; the host joins the texts of a multi-valued field with the position and offset gaps exactly as `Inverted::text` does for the built-in analyzer, so a module never sees a gap.

Input (little endian): `u32 count` (1 to 64), then per text `u32 byte length` and its UTF-8 bytes. Output: per text `u32 token count`, then per token `u32 term length`, the term bytes, `u32 start`, `u32 end` (**byte** offsets into that text, which the host converts to the UTF-16 units Lucene's offsets use), `u32 position increment`. The ceilings are per point and below the ABI's: 1 MiB in, 4 MiB out, 100,000 tokens a call.

The host **validates every output** and a violation is a `502 extension_malformed`, never repaired: a term is non-empty, valid UTF-8 and at most 32,766 bytes (Lucene's immense-term bound); `start <= end <= text length` on character boundaries and starts do not decrease; the first token's increment is at least 1; the counts fit the output. There is no position length and no token type: a module cannot make a graph, and `_analyze` reports every token as type `word`.

The module is **deterministic and imports nothing**. At pin time the host refuses a module whose imports are not empty (so neither `log` nor `cancelled`, which would make output depend on the clock), a module that exports the analyzer point without declaring `analyzer` version 1 in its descriptor, and a descriptor `io_bytes` smaller than the ceilings above.

Multi-term queries (prefix, wildcard, regexp, fuzzy) on a pinned field are **refused as unsupported** in v1, because a Lucene analyzer's `normalize` has no module equivalent and a silent verbatim match would miss for a module that changes case; `normalizer`, `explain`, `char_filter`, `tokenizer` and `filter` in `_analyze` against a pinned name stay refused, as they are for the built-ins. This is stated in `docs/compatibility.md`, not silent.

### 2. How an index pins it: in its settings, in the Java's own spelling, at creation only

A pin is three settings under the key the Java reads for a custom analyzer:

```
index.analysis.analyzer.<name>.type    = "serverless_module"
index.analysis.analyzer.<name>.module  = "<64 hex sha256>"
index.analysis.analyzer.<name>.version = "1"
```

`version` is the point version and must equal the one the module's descriptor declares for `analyzer` (an exact match; v1 hosts accept only 1). The coordinator also writes the resolved limits (below) beside them as `index.analysis.analyzer.<name>.limits.{fuel,memory_bytes,deadline_ms}`; rewriting the settings object is covered by a byte round-trip test, since the descriptor keeps settings as raw bytes. A mapping field then says `"analyzer": "<name>"` as stock OpenSearch does; `search_analyzer` and `search_quote_analyzer` may name the same pin or `standard`/`default`, and when unset they default to `analyzer` as today. A name that is not pinned by the same index and is not `default` or `standard` is refused as today. A pin's name is `ext_` followed by 1 to 60 characters of `[a-z0-9_]`; the prefix keeps it from colliding with any built-in analyzer name or the Java's `default` key. At most 4 pins an index, at most 16 KiB of pin settings.

Why this spelling: the Java builds analyzers from exactly these keys, and `serverless_module` is a type it does not have, so a Java node that opens the index fails to build the analyzers and refuses it ("Unknown analyzer type"). That refusal is a property of the Java code and is **proven by a fixture before anything depends on it**: `fixtures/extensions/CheckPin.java` opens a Rust-written descriptor with a pin on the Java shell and must see the open refused. Until that run is recorded in `docs/specs/extension-analyzer/VERIFIED.md` the pin switch (section 7) stays off, as the take switch of [ADR 0042](0042-snapshots-taken-shallow-first.md) did.

A pin exists **only in the create request** and is part of the descriptor from then on. There is no index settings update in the Rust nodes, so a pin cannot change; the coordinator refuses `index.analysis.*` in any later settings or mapping request with the Java's "final setting" message. A mapping update may add a field that uses an existing pin, never a pin. Adding a pin to an existing index would leave segments built by one analyzer and queried by another, so it is not offered; a client reindexes.

**Authority.** ADR 0051 decides at the route from the path, before the body is read, and that is unchanged. A pin is authorised by a **second check inside the handler**, after the body is parsed and the settings normalised, against the identity already authenticated: any `index.analysis` key (flat or nested spelling) in a create, template, rollover or restore body needs `all_access` in v1, and a client-supplied `limits.*` key is refused (only the coordinator writes them). The route's own action-table row is unchanged; a test holds the handler check for each spelling.

**Every path that builds a descriptor** (create, index template PUT and its resolution at create, rollover, snapshot restore ([ADR 0045](0045-shallow-snapshot-restore.md)), clone and resize where they exist) runs the same pin validation, probe, limit resolution and cluster-setting check at the moment the descriptor is built, or refuses a pin with a 400 where it does not (restore and a rollover that is not resolved through a template refuse a pin in v1; a rollover through a pinned template runs the create's validation). A template with a pin is validated when stored, and again when it resolves, since the module or the setting may have changed.

**Create-time validation.** The coordinator reads the module once (a GET into a buffer reserved from the `Extensions` pool, hash verified, compiled by ADR 0052's rule, single-flight per hash) and refuses the create with a 400 naming the key if the module is absent (`ext/modules/<sha256>.wasm`), its descriptor does not declare point `analyzer` at the pinned version, the ABI refuses it, or it fails section 1's import rule. The validation also **runs the module once** on a fixed one-word text under the host defaults, so a module that traps on every input is refused at create rather than at the first bulk. The module's own descriptor `limits` and the host defaults are **resolved and written into the pin's settings** (`fuel`, `memory_bytes`, `deadline_ms`, the lower of the two for each) at that moment; replay and every later node read the pin, never live configuration.

### 3. Where the point runs

- **Index time.** `Shard::index` takes the field's analyzer from a small `oss_doc` trait, `Tokens` (text in, tokens out, `Result`), whose implementations are the built-in `Analyzer` and the module's `ModuleTokens`, the second injected by the node (the writer and `oss_doc` never depend on the host, the layering of ADR 0052). A field analysed by a module takes the **complete path** of `oss-doc`, never the lucene-rust fast plan, which stays built-in only. A document's values for a field go in calls of at most 64 texts **and** at most 1 MiB, split in order and never inside a text (the gap arithmetic is the host's and is identical across a split); a single text over 1 MiB, or one that yields over 100,000 tokens, is refused `400 extension_failed`, a difference from the built-in listed in `docs/compatibility.md`. Module time runs under the shard's slot lock like any apply: it is bounded **per item** by a cumulative cap of ten times one call's deadline across all of the item's calls (a document with many pinned fields or values is refused `400 extension_failed` past it) and counted in the write p99 measurement of section 7, not bounded per group; a bulk's items are not batched together, so an item's failure is its own. Cost is CPU in the caller's thread, behind the per-module and per-tenant gate of ADR 0052; a full gate answers the item `429 extension_busy`, a limit or malformed output answers it `400 extension_failed` / `502 extension_malformed`. The item is refused **before staging**, so nothing of it reaches the log.
- **Replay and takeover.** The log holds the source; replay runs `Shard::index` and so the module again, with the pin's recorded `fuel` and `memory_bytes`. Replay is a recovery path and is never refused for capacity: it **bypasses the per-tenant cap and the 429 gate** (one replay runs at a time a shard, so the node's concurrency is bounded by the shards it replays) and waits, up to 60 s, for the `Extensions` reservation; a reservation that is still refused fails the open as retryable `extension_unavailable` (the open's existing back-off, never a skipped record). The **deadline is wall time and not a correctness limit on replay**: it is ten times the recorded value and only guards a hang. Fuel is deterministic for a pinned wasmtime build; a wasmtime upgrade reruns the golden vectors of ADR 0052. If a record that once succeeded now exceeds its recorded fuel, fails the output validation or hits even the stretched deadline, the shard **fails closed**: it does not open, answers 503 `extension_replay_failed` naming the sequence number and module, and counts it on a metric. The write is never skipped or indexed without its terms. **Recovery without data loss:** the number of concurrent replays is the number of shards opening at once, bounded by the `Extensions` pool and the 60 s wait. The replay's limits are the pin's recorded `fuel` and `memory_bytes`, **each times `OSS_EXTENSIONS_REPLAY_FUEL_FACTOR`** (a node setting, default 16, 1 to 1024; it is the only live input, the recorded values never change) and the failure threshold is exactly that product. The log is intact, so an operator raises the factor and restarts the node, and the shard opens and replays. A record that fails output validation (a module that is no longer deterministic) is not helped by the knob: the remedy is to roll the binary back, which the 503 says; this is stated, not hidden. A new index and reindex is not needed, and is not offered as the remedy because the unpublished tail would not be readable.
- **Tail overlay.** The reader's overlay indexes pushed documents; for a pinned field it **calls the module** through the same `Tokens` the node injects into the reader, under the overlay's byte budget and the call reservation, **without the per-tenant cap** (an overlay build is a recovery of state, one at a time a shard) but waiting for the reservation only up to the search's own timeout. The lucene-rust fast plan **declines** any field whose analyzer is not built in, so a pinned field is never indexed with `standard`. A build that fails (a refusal, a reservation not granted in time, a malformed output) fails retryably and the search answers a typed 503 `extension_unavailable` (429 for capacity); the reader never serves the published commit without the tail it was asked to include. Each build re-analyses its kept records as it does for built-ins, so module CPU repeats per build and is counted in section 7's measurements.
- **Query time.** Readers (and a coordinator that analyses) call the module for the texts of a query, one call a field per query, input bounded by the query's own size limits and the 1 MiB ceiling. Highlighting analyses a hit's text in blocks of at most 64 values. A module's result for a text is **not cached** in v1 (a cache keyed by hash, text and fuel is a later optimisation, measured first).
- **`_analyze` and `_validate/query`** with `index` in the path and `analyzer: <pinned name>` call it too; with no index, a pinned name is "failed to find global analyzer", as today.
- **Merge and publish** never analyse; a published segment carries no module reference and a reader of the segment needs the module only to **query** it, never to open it.

**One resolver, checked.** The reader's own mapping parser (`crates/reader/src/mapping.rs`, which marks an analyzer field unsupported today) admits a pinned name only when the descriptor's settings pin it. An older Rust node meets the pin as an unknown analyzer type and marks the field unsupported or refuses the index; that is stated here, not verified until the fixture work covers Rust nodes of the previous release. Every site above gets its analyzer for a field from one function, `analyzer_for(index, field)`, which returns the built-in or the pinned module's `Tokens` and cannot return the built-in for a pinned field. A tree check fails when a `lucene_analysis::Analyzer` is constructed, by any constructor or alias, in the request-path crates (`oss-node`, `oss-reader`, `oss-doc`) outside the resolver module; it has a planted violation in `scripts/selftest-checks.py` and a row in `docs/mechanical-gates.md` (slice 2, before the sites are changed). The sites are listed in the spec so nothing is found by luck: the other analysing queries (`match_phrase_prefix`, `match_bool_prefix`, `more_like_this`, `intervals`, suggesters, `_explain`, term vectors) are refused today on a pinned field with `unsupported` until each is made to call the resolver.

### 4. Opening an index with a pin

A node that opens an index (shard open on a writer, index open on a reader or coordinator) reads the pin from the descriptor it already read, and **loads each pinned module in the second round of the cold open (the descriptor, which carries the pin, is round 1), beside the commit-register GETs**, one GET per distinct module per node, single-flight per hash, never per shard, query or document. The open's depth does not grow, and the compile runs concurrently with round 3 so it adds latency to a cold open but no round; `search.cold.round_trips` stays 3 (the module's key is derived from the pin, not from anything read in that round; slice 3 verifies it against the open path and the budget row is `exact`) and the budget row in `request-budgets.md` arrives with the code, as rows are spent by tests. A module already loaded costs nothing, and an evicted one is refetched at most once per open and at most once per 30 s per hash (an index that is not open holds nothing).

A pinned module of an **open index is resident and non-evictable**, charged to `Extensions` for as long as the index is open; the pool that cannot hold it at open refuses the open with a 429, and a module is never fetched or compiled at call time, so no call adds a GET or a round. A node that cannot run a pin **refuses the open and never falls back to the built-in analyzer**: no `extensions` feature, `OSS_EXTENSIONS_PERCENT` at 0, the module absent from the store, an ABI or hash mismatch, or the `Extensions` pool unable to hold the compile reservation (that one is a 429, the others a 503 `extension_unavailable`). **The pin check and the module load complete before any fencing write**: a node that cannot run a pin never claims the shard head, so a capable node can still take it, and a refused takeover leaves the head as it was. A refused open is cached negatively for 30 seconds per hash on that node so a query storm does not become a GET storm (a bounded count, no per-document cost). **Takeover** by a node that cannot run the pin is the same refusal: the shard stays unserved under the existing back-off with one unserved-shard metric, no log is written, and the request cost of the retry is the capped GET above; placement does not yet prefer a capable node (section 5).

### 5. A mixed fleet

The refusal is held by the things below, none of them a lease capability. The failure of a mis-deployed fleet is loud by construction: an unserved shard, the `extension_unavailable` 503 and a metric.

1. A **Java node** (and the cluster-config key, which the fixture also feeds to a Java node to see it ignored or refused) cannot build the `serverless_module` analyzer type and refuses the index (the fixture of section 2; this is the property that must be proven, not assumed).
2. A **Rust node without the runtime** refuses the open (section 4), and a refused shard open on a writer leaves the shard unserved with the existing back-off, no log entry written for it.
3. The **cluster setting `serverless.extensions.pins.allowed`** (default `false`, dynamic) must be `true` for a create to carry a pin. An operator sets it only when every node that can hold a shard of the index runs the runtime. It is a deployment decision, as the byte-compat rules of the Java shell are for the rest of the fleet; the ADR does not claim the fleet is checked.

A lease capability (a node announcing what it can run) would change `oss-format`'s lease record and make placement avoid a node that cannot open an index. It is **not built**: it costs a format change with a fixture and a read of every member's lease at placement, and the two refusals above already make a wrongly placed shard fail to open instead of serving wrong results. The price is that a mis-deployed fleet shows as unserved shards until the setting is corrected, which is loud. A later ADR can add the capability if mis-deployments happen.

### 6. Counters, bounds and memory

A call reserves ADR 0052's `linear memory + 2 x io_bytes + stack` from `Extensions`; with the point's ceilings that is 64 MiB + 10 MiB + 1 MiB at most, and the per-module concurrency of 8 (2 for one tenant) bounds the worst case. Each call adds to per-tenant counters (`calls`, `fuel`, `input_bytes`, `output_bytes`), bounded in cardinality by the usage ledger's `max_indices` and its `_other` row, kept beside the usage ledger of [ADR 0037](0037-per-index-store-usage.md) and reported with it on `GET /_serverless/usage` when that is on; they feed the non-store counters R13.4 needs and change no guardrail by themselves. No request is made per call, document, query or highlighted hit.

### 7. Switch

Turning the setting back to `false` refuses new pins only; existing pins keep working. A tree check holds that no shipped configuration sets the pin setting to `true`. Two gates, both off by default: the node's `extensions` Cargo feature with `OSS_EXTENSIONS_PERCENT` above 0 (ADR 0052), which builds and sizes the runtime, and the cluster setting `serverless.extensions.pins.allowed` (section 5), which lets a create carry a pin. With either off, **nothing changes for any index without a pin**: the existing tests pin the built-in behaviour unchanged and new tests cover the pinned one, both run in CI. The pin setting stays `false` in every shipped configuration until, with a module present, (a) the Java fixture run is recorded, (b) a soak with hostile modules (spin, memory growth, trap, oversized and malformed output, a module that is valid at create and exceeds its fuel on a long text) leaves the node serving within its memory budget, (c) a replay of a log of pinned writes after a crash and a takeover reproduces the same terms byte for byte, and (d) a measured write p99, per-query call cost and the saturation point of the 8-call cap are recorded as provisional. The measured downside is expected to be CPU and a tail of the write path; that is why this is a setting and not a default.

## Docs that change with the slices

`docs/how-to/add-an-extension-point.md` is corrected (a limit is 400 `extension_failed`, capacity 429; the replay-limits and no-fallback rules; the two tree checks), `docs/compatibility.md` lists the differences (multi-term queries, token limits, `_analyze` refusals), `docs/mechanical-gates.md` gets a row and `scripts/selftest-checks.py` a planted violation for each of the two tree checks (the analyzer sites; the pin setting in shipped configurations), and `request-budgets.md` the exact row once a test spends it.

## Consequences

- An index can use an analyzer written outside this repository without a build of the node, at one GET a node a module and no request a call.
- A pin is for the life of the index; changing an analyzer is a reindex. This matches stock OpenSearch, where `index.analysis.*` is final on an open index.
- A document's analysis cost moves into the write's tail; the pipeline of ADR 0050 hides it from a window's wait only up to the depth, not from the client's latency.
- A replay can fail closed after a wasmtime upgrade; that is a visible 503 on one shard, never a wrong term.
- Harder: a Java node cannot serve a pinned index. A cluster that mixes the two for a pinned index is out of scope; the fixture proves the refusal and the setting keeps pins from being created before the fleet is ready.
- Rules out here: pins added to an existing index, token graphs and token types, module imports, a result cache, a lease capability, a native or non-WASM module, a normalizer for multi-term queries, and a pin shared across indices by name.

## Slices

The pin setting is not registered, and a create with a pin is refused, until slice 4 has landed, so no build indexes a pinned field with a built-in analyzer in between.

1. The point's codec and `Tokens` validation in `oss-ext`, `analyze_block` in `oss-ext-wasm`, hostile and golden vectors, a test module builder for the point.
2. Pin parsing and create-time validation (coordinator, the setting, the action row, `index.analysis.*` finality), the mapping admitting pinned names, `Tokens` in `oss-doc`.
3. The write path and replay with recorded limits, the node's `ModuleTokens`, the fail-closed replay event, the open-time load and its budget row.
4. The reader's query builders, highlight, `_analyze`, `_validate/query`.
5. The Java refusal fixture, the hostile soak, the replay-equality test, the p99 and per-query measurements, and the compatibility notes. The switch is not flipped here.
