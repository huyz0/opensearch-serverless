# 0022. Nested bucket aggregations: one engine tree, a total bucket bound, a product-aware reservation

**Status:** Accepted after independent review, 2026-11-20 (two rounds; the owner accepted the 400 `too_many_buckets_exception` over the bucket limit for a nested terms, where OpenSearch would run it).

## Context

The sub-aggregation series serves metrics and a keyword `terms` under every bucket aggregation. A bucket aggregation under a bucket (a `date_histogram` of `terms`, a `terms` under a `histogram`, ...) is refused. OpenSearch serves it, and the product of bucket counts is its classic memory risk: it bounds it with `search.max_buckets` (65,535), counted over every bucket at every level, and fails the request with `too_many_buckets_exception`.

lucene-aggs (rev 0a46c83) already holds the nesting: `AggNode::{Histogram, DateHistogram, NumericTerms, Range, Filters}` carry `subs: Vec<AggNode>` recursively, and a sub's result lists its buckets per *owning bucket*, the parent's buckets flattened in order, so a grandchild's owners are all of the child's buckets. `Globals::with_bucket_limit(BUCKET_LIMIT)` makes the pass count the buckets of the **whole node tree** (`buckets_made`) before every window of 1,024 documents and once more before results are built, and stop with `TooManyBuckets`; the reader already sets it.

## Decision

1. **One tree, no second engine.** A parent's sub-aggregation may itself be a `histogram`, `date_histogram`, `range`, `filters`, `filter` or numeric `terms` (a keyword `terms` as a *parent* of a bucket aggregation, and `top_hits`-style or pipeline kinds, stay refused). `keyword_subs::sub_nodes` builds its node recursively; depth stays under the parser's existing `MAX_NESTING` (3 levels of sub-aggregations under a top-level aggregation), which the first PR re-checks against the reservation.
2. **The hard bound is a key cap in the engine.** The engine's total-bucket count is a lower bound (a terms level counts `min(keys, shard_size)`) and is checked once a window of 1,024 documents, so it is not a memory bound by itself. lucene-rust now caps each *nested* key table at the request's bucket limit (`KeyOrds::cap`, lucene-rust#567): at the cap a new key is not added, the table is marked over, and the pass fails with `TooManyBuckets` at its next check. A pass therefore holds at most `BUCKET_LIMIT` keys per nested level however many documents a window holds, at most (the number of nested aggregation nodes in the request, itself bounded by the request body) tables of that size, `Fixed` levels (`range`, `filters`) of owners x width entries with at most one window of new owners past a check, and the top-level aggregation's keys, bounded by its field's values as today. A request over the cap fails with the existing 400 `too_many_buckets_exception`, which is stricter than OpenSearch for a nested `terms` of very high cardinality (which OpenSearch serves with large memory); that is the bounded-memory principle taking precedence, stated in the compatibility document.
3. **Results by slicing, not by new types.** A sub-aggregation's engine result is sliced per owning bucket (a function over `AggResult` that takes the owner's range of buckets and, recursively, the matching range of the children's `subs`), and each slice goes through the same `value()` that serves the aggregation at the top level, giving a `Value::Histogram`, `Value::Terms`, ... held in the parent bucket's list. No second result type exists, and the slice is linear in the total buckets.
4. **Reduce counts as it goes.** `reduce_sub` today falls back to the first shard's value when a nested reducer fails, and a gap-filled histogram (`min_doc_count: 0`, `extended_bounds`) or a zero-count terms level builds up to the limit per parent bucket, so a total counted after the reduce is too late. The nested reduce takes one running bucket counter for the whole tree: every bucket a level merges or fills is counted as it is made, over `BUCKET_LIMIT` fails the reduce with `too_many_buckets_exception` (as OpenSearch's `MultiBucketConsumer` does, over every level), and a nested reducer's failure is an error, never the fallback. The reduce holds the shards' partials, each bounded as in 2, so its memory is linear in the shards that answered.
5. **The reservation is per slice and counts copies.** The reader runs one slice a segment set today; the reservation is made per slice, so a change to more slices multiplies it, and the merge of slices (up to slices x cap keys) is reserved with them. For each nested level, a segment's metadata gives `B_k = min(V_k x F_k, BUCKET_LIMIT)`: `V_k` the level's field value count; `F_k` the product of the fanouts above it: 1 for a single-valued numeric entry, the bucket count for a `range` or `filters`, and `BUCKET_LIMIT` for a multi-valued (sorted-numeric) field. The search reserves the sum of the levels' `B_k` at the per-bucket bytes of the sub-aggregation reservation, times `SUB_COPIES` for the values built while the engine result is alive, with its hits. The engine's cap makes this an admission estimate, not the safety bound: a multi-valued parent reserves the worst case (and a small pool may refuse it), never more than the cap allows.

## Consequences

- The product of bucket counts is bounded twice: before the pass by the reservation, during it by the engine's key cap (the bucket limit, OpenSearch's own number, per nested level).
- Requests: a nested aggregation reads the same doc values through the same ranged reads as it would at the top level, so the request count is not expected to grow; plan item 4 measures it against the budget rows before it is claimed.
- A `date_histogram` of `terms` of a high-cardinality field fails with `too_many_buckets_exception` instead of exhausting memory.
- A multi-valued parent field reserves the full cap, which can refuse a search in a small pool; metadata of a per-document maximum would tighten it and is deferred.
- A nested `terms` over more than `BUCKET_LIMIT` distinct (parent bucket, value) pairs fails with 400 where OpenSearch would run it with large memory; a request over the cap names `too_many_buckets_exception` and `search.max_buckets`.
- The guarantee depends on the reader passing `with_bucket_limit` (it does), and on nested keyed tables outside `significant_terms`/`composite`, which the reader refuses. The engine's segment cache never stores a block whose table hit its bound (lucene-rust#567).
- Rules out here: a keyword `terms` as a parent of a bucket aggregation, `composite`, `nested`/`reverse_nested`/`global`, and pipeline aggregations.

## Plan

Small PRs, each with its spec under `docs/specs/nested-bucket-aggs/`: (1) the slice function and a bucket aggregation under a `range`/`filters`/`filter` (fixed owners, no key alignment); (2) under `histogram`/`date_histogram`; (3) under a numeric `terms`; (4) the multi-level reservation and the limit tests (a product over the limit fails with 400, under it passes, a reduce over the total fails), measured against the budget rows. Before (1): lucene-rust#567 (the key cap) and the pin bump here.
