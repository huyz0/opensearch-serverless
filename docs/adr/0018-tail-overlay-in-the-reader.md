# 0018: The reader searches pushed, unpublished writes through one small in-memory segment beside the commit

**Status:** Accepted after independent review, 2026-11-18.

## Context

A reader serves a published commit, so a write is searchable on it only after its writer publishes: a refresh interval at the soonest, and every publish costs PUTs ([request budgets](../request-budgets.md)). The writer holds every write it acknowledged and, since the tail work ([writer-tail-keep](../specs/writer-tail-keep/SPEC.md), [writer-tail-push](../specs/writer-tail-push/SPEC.md), [reader-tail-held](../specs/reader-tail-held/SPEC.md)), pushes it node to node to the readers subscribed to the shard. What is missing is how the reader makes those held writes searchable. The Java shell's `OverlayReadOnlyEngine` indexes them into a small in-memory index and searches it with the commit, hiding every commit document the overlay replaces or deletes.

The Rust reader searches with `IndexSearcher::new(segments, norms)` over the segments `shard.reader.open_segments()` gives (`crates/reader/src/search.rs`); aggregations, top hits and fetch take the same segment list. `oss-reader` already depends on `lucene-index`, `lucene-store` and `lucene-codecs`.

Principles this must keep: no request on the push or search path (pushes are node to node); the one place the build reads the object store is bounded below, bounded memory ([ADR 0004](0004-bounded-memory-and-streaming.md)), idle shards free, and a reader never answers with a version older than its commit's.

## Decision

- **One overlay segment per open shard, beside the commit's segments.** The records [`TailHeld`](../specs/reader-tail-held/SPEC.md) holds are applied in ordinal order to a small in-memory segment built with the same mapping and analyzers as the commit, and the searcher is given the commit's segments followed by that one. Aggregations, top hits and fetch see it through the same segment list, so no query path is special-cased.
- **The overlay holds the latest pushed version of each document id only.** An operation at or below the commit's local checkpoint, or older than what the commit holds for the id, is dropped; a later version replaces an earlier one; a deletion is a mask, not a document.
- **Commit documents the overlay replaces or deletes are hidden** by a per-segment live-documents mask over the commit's segments, built from the overlay's ids; the commit's files are never rewritten.
- **A new overlay is built in the background when records arrive and `next_ordinal` has moved since the last one**, and is rebuilt from the records held, not patched, so a search sees one consistent pair of commit and overlay; the old one lives until the searches holding it end. A search never starts a build. The cost is bounded by `MAX_RECORDS` (100,000) records a shard.
- **The overlay is charged to the `open_indexes` pool** ([ADR 0014](0014-open-indexes-pool.md)) by an estimate from the record bytes held, before it is built; a refused charge leaves the reader on its commit (the shell's "skipped"), never a failed search.
- **A record the overlay cannot take** (a field the reader's mapping lacks, no sequence number, past the cap) marks the shard `refusing` (or `skipped`, set by the engine), so it grants nothing until a newer commit, and the search serves the commit. A reader is never older than its commit, only as fresh as before.
- **Home and input.** The builder lives in `oss-reader` (layer 3) and takes an owned slice of a neutral record type it defines (id, sequence number, operation, source); `oss-node`, which holds `TailHeld`, converts its records and passes them in. The seam is a trait `OverlaySource` owned by `oss-reader` and implemented in `oss-node` over `TailHeld`: `overlay(uuid, shard, now) -> Option<Arc<Overlay>>`. It is called per search; `overlay()` only returns an already finished `Arc<Overlay>` or `None`, and never builds; the build is started by record arrival. The freshness gate (`granted`, 500 ms) is evaluated inside it at search time and never cached across the grant. `search`, `top_hits` and `collect_top` take the returned overlay and mask beside `open_segments()`. `oss-reader` gains no dependency on `oss-node` or `oss-transport`; any new edge goes through the `architecture` skill first.
- **Hiding commit documents is done off the search path, never in a search.** Finding the commit's copy of an overlay id (and its sequence number, for the version comparison above, which is kept: an overlay entry not newer than the commit's copy is dropped) reads the `_id` term dictionary and the sequence-number doc values, which are paged lazily through `CachedBlobDirectory` (ADR 0014). That work runs in the background when records arrive for an open commit, as at most two dependent rounds (the `_id` dictionary gives a document number, which locates its sequence number), each a parallel fan-out; it is off the user path, so the three-round ranking budget is untouched, and produces a complete overlay and mask. A search only picks up a *finished* overlay; until one is ready, or when the grant has lapsed, the search serves the commit alone and adds no round, so the ranking budget of three rounds is untouched. Lookups are kept per commit and extended for new ids only, at most 10,000 distinct ids an overlay (more leaves the shard `skipped`). The reads are capped per commit and shard by the number of blocks of those two structures (their size in bytes), not by the id count, and are cached per commit, so a commit costs at most that many reads once however many writes arrive; the first implementation PR adds the path to `docs/request-budgets.md`. Tests, on a cold multi-page index with many overlay ids: the background build issues at most two rounds and no more requests than the blocks of the `_id` dictionary and sequence-number structures, and none on a second build for the same commit; a search never starts a build, issues zero requests and the same number of rounds with an overlay as without; a search before the overlay is ready returns the commit's result; a commit holding a newer version of an id than a held record is never masked.
- **Searching both sides must score as one index.** The overlay segment has its own norms; document frequency and total document count are summed across the commit's segments and the overlay the way the shell does, so ranking matches one index. Whether document frequency counts masked documents is confirmed against the shell (Lucene counts deleted documents in it) and matched. The oracle is the shell's `OverlayReadOnlyEngine` on the same data, compared in the usable-cluster suite.
- **The overlay is dropped when it cannot be trusted.** When the commit's checkpoint passes the held records they are released and the overlay goes with them; when the writer's grant lapses (`GRANT_MILLIS`) or the shard is `skipped`, the search serves the commit alone.
- **The mask is a sparse set, bounded and charged.** It holds at most 10,000 commit document numbers a segment (the id cap), never a bitset sized by the commit's maxDoc; it and the per-commit id lookup cache are charged with the overlay in the same non-evicting reservation and released with it, and a limit test covers them.
- **Held records are reserved at receipt.** Each record's bytes are reserved from the `open_indexes` pool by a non-evicting try-reserve before `TailHeld` stores it, for a tracked shard (one an engine tracked, or closed under 30 s ago); a refusal sets `refusing` and drops the shard's held records, and a reservation is released when the commit's checkpoint passes the record. The build then reserves only the overlay and mask. A limit test: a refused receipt allocates nothing and sets `refusing`.
- **Freshness guarantee.** An overlay is *usable* while the grant holds and the commit has not passed it; a search uses the newest finished overlay even if a rebuild is under way, so the guarantee is never older than the commit and as fresh as the last finished build, not read-your-writes. A test pins that a search during a rebuild uses the previous overlay, and one after the grant lapses uses none.
- **Held and overlay bytes get a share of the pool, not all of it.** Non-evicting reserves are an extension of ADR 0014, which the first implementation PR amends: held and overlay bytes together may take at most a stated fraction of the pool, so an unrelated index's open is not refused for them.
- **Held bytes are bounded and charged.** `TailHeld` gains a per-shard byte cap (16 MiB, as the writer's keep) beside `MAX_RECORDS`; a record past either cap sets `refusing`, so nothing is granted until a newer commit. The held records and every live overlay (the old one while its searches run, and the new one) are charged together to the `open_indexes` pool by a non-evicting try-reserve made before the build; a refusal serves the commit alone, never evicts another index and never fails the search. A charge is released when the last holder drops. Limit tests cover bytes as well as count.
- **The charge has a formula and a limit test.** The estimate is a fixed cost plus a per-byte factor on the record bytes held; a test asserts it is at least the measured heap of the built overlay, as ADR 0014 did for commit segments.
- **Everything is behind a new tail-overlay setting**, added to the settings registry by the first implementation PR (cluster default, overridable per index), default off until the usable-cluster suite measures it ([principles](../principles.md#switches-and-defaults)); the default is flipped only when write p99 is within 5%, no request is added, searches do not regress and the crash tests pass.

## Consequences

- A write is searchable a network hop after its acknowledgement with no request on the push or search path (the background build's bounded reads of the commit aside), for shards whose readers subscribed; shards nobody searches stay free.
- Memory a shard is bounded by the 100,000 records held plus one overlay segment built from them, charged to the pool by a non-evicting reserve, so a refusal serves the commit and never evicts another index.
- A rebuild per changed `next_ordinal` is simple and consistent; its price is CPU that grows with the write rate, up to 100,000 records a rebuild (unmeasured; the bound is on memory, not time). The first implementation measures it and adds a minimum rebuild interval if searches slow; the existing tests pin the setting off, new tests pin it on. If measured too slow, the next step is appending to the overlay in sequence order instead of rebuilding, which this decision does not forbid.
- Unverified until the first implementation PR: that the overlay's heap fits the pool estimate (ADR 0014's constants were measured on commit segments), and that `IndexSearcher` and `open_segments` take a per-segment live-documents mask (the reader has only `soft_deletes_wrapper` today).
- The engine is the first thing to need an in-memory segment writer in the reader build; if `lucene-index` cannot write a segment to an in-memory directory, or `open_segments` cannot take an extra segment with a live-documents mask, that is found in the first implementation PR and this ADR is amended, not worked around.
- Rules out: indexing pushed writes into the commit's files, a second searcher merged by hits (which could not mask replaced documents or sort and aggregate across both), and any object-store request on the push or search path.
