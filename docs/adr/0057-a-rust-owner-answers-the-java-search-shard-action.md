# 0057: A Rust owner answers the Java search-shard action

**Status:** Accepted after independent review (three rounds), 2026-11-25; the lease-age bound was accepted by the owner

## Context

A Java coordinator searches a shard by `SearchShardCalls.askOneShard`: a local copy, then up to two placement readers, and the shard's owner last. A Java reader that is asked checks that its open commit covers every write the owner has answered as refreshed; when it does not (a Rust owner acknowledges a bulk with `forced_refresh` and publishes its commit lazily, so for up to a refresh interval the commit is behind), it refuses with `shard_behind_log_exception`. The coordinator then asks the owner, with `internal:serverless/search/shard` (`ForwardedSearchRequest`, answered by `ForwardedWorkHandlers.handleSearch`). A Rust node registers no handler, so that last attempt fails with `action_not_found_transport_exception`, every attempt's failure is kept, the last is reported, and the coordinator answers a partial result (`_shards.failed` above 0). The Java coordinator does not re-resolve and retry: a refusal from the owner is a shard failure too.

The mixed-fleet wide soak shows it. After a Java node is killed, both Java nodes answer partially for the shards a Rust node owns, for longer than the judge waits, while both Rust nodes hold every acknowledged document ([mixed-fleet-wide-soak](../specs/mixed-fleet-wide-soak/VERIFIED.md)). Pushing every commit to the Java readers ([mixed-fleet-push](../specs/mixed-fleet-push/SPEC.md)) does not cure it: 107 of 131 commits had no Java reader among the two ranked readers, and the 24 that reached one found it had the shard closed. A commit cannot carry writes that are not yet in one.

The owner decided (2026-11-25): the Rust node serves the action.

Forces: no Java change; requests scale with nodes and bytes; bounded memory; a paused or deposed owner must not answer as if it were current; the request is the Java wire format of a `SearchSourceBuilder` (versioned, with named writeable queries) and the answer holds `SearchHit`s, both Java wire formats; the transport MAC covers the request bytes ([ADR 0016](0016-native-transport-and-early-revoke.md)).

## Decision

**A Rust node answers `internal:serverless/search/shard` for a shard it currently writes, from its own view of the shard, for the subset of the request it can decode; it refuses everything else by name.**

1. **Order of work on a request.** (a) The MAC is verified over the received bytes, as for every forwarded action, before anything is decoded; a wrong MAC decodes nothing. (b) The request is read under the limits of item 5, from the raw bytes; the request is not re-serialized, so a field the decoder does not model cannot break the MAC. (c) The shard is checked (item 2). (d) The query runs. (e) The shard is checked again, as the Java handler does, and an answer is sent only if both checks held.
2. **Where it answers, and what is guaranteed.** Only a shard this node holds as writer, whose uuid equals the request's uuid (a local comparison: a recreated index has a new uuid, and the node releases the shards of a deleted one), while this node's own lease is unexpired and not revoked by its own clock. The checks are made before and after the query, from the node's own state, with no blob request. A shard that is not held, a uuid that differs, or a lease the node knows it has lost is refused with the typed not-owner refusal, and the handler never opens a shard as a reader. **This is not write fencing.** A read has no compare-and-swap, so a paused node, or one whose lease was taken and which has not yet learned it, can still answer from its view. The lease is 30 s, renewed every 10 s ([ADR 0016](0016-native-transport-and-early-revoke.md)), so a deposed holder can answer for up to about one renewal interval after a revoke it has not seen, and up to the lease lifetime if it was paused or partitioned. During that window its answer can miss writes the successor acknowledged. The Java coordinator names the owner from the shard head, which names the successor once it has taken the shard, so the old owner is asked only by a coordinator whose view of the head is also stale. **This trades read-your-writes during a deposition window for an answer where today there is a partial one.** Java's own forwarded get refuses instead; this action does not, because a refusal here is the partial answer the ADR exists to remove. The window is narrowed: the node answers only if its last successful lease renewal is no older than `serverless.search.shard_action.max_lease_age_millis` (`OSS_SEARCH_SHARD_ACTION_MAX_LEASE_AGE_MILLIS`, default 10,000, the renewal interval), so a node that has missed a renewal refuses, and a deposed holder answers for about 10 s at most after its last renewal. The owner accepted this bound on 2026-11-25 ("Require a renewal in the last 10 s"); a different bound is a setting change.
3. **What it searches.** The owner's own current view, including writes acknowledged and not yet published: the view a `_search?refresh=true` on this node reads. Hits come back in the shard's own order, ranked by score and, on a tie, by `_id` ascending, and the shard's cut-off at `from` plus `size` is made under the same rule (the Lucene doc id depends on segment layout, which differs between the two builds, so which tied hits fall at the cut-off can differ from a Java shard's; the page is a valid page and a fixture with tied scores pins it); the merge and the fetch phase of a multi-shard search stay with the coordinator. `now` in date math (`range` on `now-1h`) is the request's `nowInMillis`, not this node's clock.
4. **What it decodes (first slice).** Java's wire format has no length prefix per field or per named query, so after the first thing the decoder cannot read, nothing later can be read. The rule is therefore: read in field order and refuse at the first item that is not decodable, naming that item with a typed `illegal_argument_exception`; a field outside the subset at its default value is read and ignored. The subset is `query` of `match_all`, `term`, `terms`, `range` (with `time_zone`, `relation` and bounds), `bool` (`must`, `filter`, `should`, `must_not`, `minimum_should_match`), `ids`, `exists`, each with `boost`; `size`, `from`, `track_total_hits`, `_source` fetch filtering, `min_score`, `timeout`, `terminate_after`. A query parameter the decoder does not model refuses the request at that query; it is never read past. Sort other than score, aggregations, highlight, rescore, `search_after`, collapse, suggest, script fields and PIT are later slices, each with its own spec row and Java fixture. The response is written at the pinned Java stream version (3.10.0): total, hits, a `false` aggregations flag, the relation flag, max score, timed out, terminated early; which `SearchHit` fields are written is part of the fixture and the spec.
5. **Limits.** Enforced while reading, before allocating: request bytes 1 MiB; query nesting depth 16; clauses 1,024; `from` plus `size` 10,000; a string or list length from the wire is checked against the bytes left. The answer is bounded at 16 MiB: bytes are reserved against the node's memory pool as each hit is added, and a shard whose answer would pass the bound is refused whole (a partial page would be a wrong page). The answer is written at the stream version the connection negotiated; a version below 3.10.0 is refused, not written in a layout the peer may read differently.
6. **Load.** A forwarded search takes a permit from a bounded pool of search slots ([ADR 0047](0047-search-slots.md)), separate from the writer's workers, so searches cannot starve the writes the owner serves; the REST-edge queue of [ADR 0056](0056-over-share-searches-wait-off-the-workers-in-a-bounded-queue.md) does not apply to a transport handler, and a forwarded request names an index, not an authenticated tenant, so the pool is shared by all forwarded searches. A full pool refuses the shard with a typed transport exception, which a Java coordinator reports as a failed shard (not a 429). The load lands on the owner only while a Java reader is behind.
7. **Cost.** No S3 request in steady state. None: the handler makes no blob request, and none for an idle index. The answer's bytes and the decoded request are charged to the node's memory pool (item 5). A test counts the node's blob requests across a forwarded search and a row in `docs/request-budgets.md` pins it at zero. The Java side's own two reader attempts before the owner are unchanged and are not this ADR's cost.
8. **Refusals stay partial answers on Java.** A not-owner, an unsupported query, an over-limit request and a full queue each fail that shard on the Java coordinator (`_shards.failed` above 0), exactly as `action_not_found` does today. This ADR removes the failure only for requests inside the subset on a shard the node writes.
9. **Switch.** `serverless.search.shard_action.enabled` (`OSS_SEARCH_SHARD_ACTION`). It ships default on only if the measurements the principles ask for hold: write p99 within 5% under forwarded-search load (AC-11, provisional on an emulator), no extra S3 request beyond the budget row, and no search regression; if AC-11 does not hold the default is off and the soak sets it. The off state is a partial answer in a mixed fleet, a correctness failure and not a performance one, which is why on is the intended default. Both modes are tested, and the existing tests that pin the old behaviour (`action_not_found` for an unknown action) stay.

## Consequences

- A mixed fleet answers complete results for in-subset searches while a Java reader is behind a Rust owner, so the wide soak can pass its first cycle.
- The Rust node holds a decoder for part of the Java `SearchSourceBuilder` wire format and an encoder for `SearchHit`; it grows slice by slice, and a request outside the subset is a visible refusal in `_shards.failures`, not a wrong answer.
- A Java coordinator that sends a query outside the subset still gets a partial answer until its slice lands.
- It rules out a shortcut: publishing a commit for every refresh-acknowledged bulk, which would make lazy publish eager and add a PUT per refresh.
- `docs/compatibility.md`, the transport crate README and ADR 0016's list of Java actions Rust does not serve change with it.

## Built slice (2026-11-25)

The handler runs a decoded request through the reader's own search parser, as the JSON a REST search would carry, so a query means here what it means on a REST search. Two things the decoder reads are therefore refused at that step, by name, because the reader does not run them: a query with `_name` (a named query's hits carry `matched_queries`, and the forwarded answer writes none, so serving it would be a wrong answer) and a `range` with `format`. `now` and `timeout` are read and not applied; ties on score keep the shard's document order. Each is a later slice with its own row.
