# 0064: A routine publish stages its commit, and the register is written as a checkpoint

**Status:** Accepted after independent review, 2026-11-26

## Context

Every publish of a shard uploads its new segment files and then swaps the shard's commit register: one conditional PUT a publish a shard. At the target scale (10M tenants, 10 indices each, a refresh interval of a second or five) the register swap is the largest request class left once segments ride node packs and the write log is one blob a window. The Java shell measured it (`serverless-log-commits`, 1,000 shards, 150 s): staging the manifest and writing the register once a minute took PUT+LIST per publish from 2.09 (blob segments, no staging) to 1.44 (staged commits), and to 0.68 with node packs. Its cost was a longer takeover: a successor replays the log from the register's older commit (+4% to +23% over the unstaged one at 1,000 shards, bounded by the checkpoint age).

The shell stages the commit in memory (`CommitStaging`), writes the register at a checkpoint (the first publish of a term, any non-routine publish, and once the oldest staged commit is as old as the checkpoint age), and also logs each staged commit in the node log under a key of its own so a successor can open from it (`LoggedCommits`). This ADR ports both, in three slices, each behind a setting.

## Decision

1. **Staging.** `ShardPublisher::publish_routine` uploads a commit's new files as `publish` does, then, when staging is on, keeps the commit's manifest instead of swapping the register, as long as (a) the publisher holds the register it last wrote (same term, same writer: the first publish of a term is the fence and always writes), (b) the oldest staged commit is younger than the checkpoint age, and (c) no pack a staged commit names is older than the pack deadline. `publish` is unchanged: a release, hand-off, hibernation, eviction, an open's replay or a requested refresh writes the register and clears what was staged. A checkpoint (`flush_staged`) swaps the newest staged manifest over the generation the publisher last wrote, with no new upload. A staged commit carries a stage sequence in its manifest (`stage_seq`, the field the shell reads) so a later reader can tell which of two commits is newer.
2. **Only a register write counts as published.** The log trim and the tail overlay's `published` (which lets the overlay drop what a commit holds) happen only when a register write lands, never at a stage. The lazy policy's due clock moves on at a stage (or the shard would be due at every pass), but a shard with a staged commit still counts as unpublished for every other question the node asks: hibernation, eviction, hand-off, retire and a requested refresh take the full path (`publish`, which writes the register), and a refresh of a sleeping shard is never answered "published" on a staged commit. The tail overlay keeps its records until then, inside its own bounds. A pushed staged commit is a hint to readers; a reader that cannot use it falls back to the register.
3. **The log is trimmed behind the register, never behind a staged commit.** The node records the log position a staged commit covers and calls `on_published` only when a register write lands: a checkpoint, or any full publish. A staged commit is therefore never the only home of a record. A crash, a lost lease or a dropped publisher loses the staged commit and nothing else: a successor opens from the register and replays the log, as it does after any crash between two publishes. Files uploaded for a dropped staged commit are uploaded again by the next publish (names are taken with `create_if_absent`, as now).
4. **What reads the register keeps working.** Readers read the register and are pushed the staged commit by the writer (the push already exists, [`node-commit-push`](../specs/node-commit-push/SPEC.md)); the janitor judges a dead node's log by the register's checkpoint, so a lagging register keeps a log longer, never shorter. Shard collection deletes only blobs of terms older than the register's, and a staged commit is of the register's term. Node pack collection deletes a pack no manifest names once it is old; the checkpoint age is bounded by half the pack deadline, and a staged commit older than the deadline is dropped, so a register never names a pack that may be gone.
5. **Switch.** `serverless.wal.node_log.commits.staging` (node scope for this slice, default `false`; the cluster-wide runtime override the shell has comes with slice 2, which reads the cluster config register already on that path, so this slice adds no register read) and `serverless.wal.node_log.commits.checkpoint_millis` (default 60,000; at least 1,000 and two commit periods, at most half the pack deadline, as the shell's `CommitStaging.check`). Off, the publisher is byte for byte what it is today, and every existing test pins that. The default flips only on the measurements the build rule names: write p99 within 5%, no extra S3 requests, no search regression, the crash tests green. Staging adds none: it removes requests.
6. **Logged commits (slice 2) and opening from them (slice 3)** are the shell's `LoggedCommits` and `NewestCommits`: each staged commit joins the node log under the key `<uuid>#commit`, newest only, so a successor reads one slice a shard and opens from it while its oldest pack is younger than the swap deadline, adopting it into the register by compare-and-swap before it lets go of the predecessor's log. They have their own spec and a separate switch; this ADR fixes only that the key is never a shard's, and that a logged commit is a hint a successor may ignore: opening from the register is always correct. The janitor's dead-log loop must skip that key (it has no index name), and the bytes logged commits add to a window are bounded by the newest-commit bound (`MAX_NEWEST_BYTES`), both in slice 2's spec.

## Consequences

- One conditional PUT fewer on all but one routine publish in `checkpoint_millis / publish spacing` (twelve at the defaults) for every busy shard; an idle shard with a staged commit writes it once, at the checkpoint.
- A register-only reader is at most the checkpoint age behind the writer's newest commit; readers the writer pushes to are not. A successor replays up to a checkpoint age more of the log unless it opens from the newest logged commit (slice 3, `open_from_logged`).
- The log is kept up to a checkpoint age longer.
- Fencing is unchanged: every register write is a compare-and-swap over the generation this publisher last wrote, and the first publish of a term writes. No lock, lease or leader election is added; no request scales with records, documents or indexes; no LIST; memory per shard grows by one manifest's bytes.
- A staged commit is not durable. Nothing acknowledged depends on it: acknowledgement means the write log holds the record, and the log is trimmed only behind the register.

- A fenced or zombie writer learns it is fenced at its next register write, up to a checkpoint age, instead of at each publish. It can push commits to readers meanwhile. Acknowledgements are fenced by the log, so no write is lost. Bucket members swap their member entry at their own checkpoint through the same register seam, one conditional swap of the bucket manifest per checkpoint of the members that land together.

## Tests that hold it

Request counts: a routine publish inside the checkpoint age makes one PUT with staging on and two with it off (`publish_staging.rs`, both values). Bounds: checkpoint age and pack deadline boundaries (unit tests of the pure functions), the settings' bounds, and the staged manifest's size, which is a manifest the register already holds. Hibernate and evict with a staged commit and no checkpoint publish in full (node suite). Crash: a staged commit dropped with its node loses no acknowledged write.

Staged bytes: one manifest a shard with a staged commit (the register already holds a manifest that size), held until the next register write or drop. Bucket members stage and flush through the same register seam; the pack-deadline bound applies to their staged commits as to any, and they are off with the buckets switch.

The checkpoint pass takes what a flush covered while it still holds the publish gate, so a publish staging a newer commit meanwhile keeps its own entry (found by the second review).

## Review

Independent review 2026-11-26, three rounds by a reviewer given the ADR, the principles and the diff, not the author's reasoning. Round one found the lazy policy's published mark and the missing count tests; round two found a race in the checkpoint pass (the pending log position was taken after the publish gate was released); round three cleared the fixed text and code. Slices 2 and 3 (logged commits, opening from them) each get their own spec and review before they are built.
