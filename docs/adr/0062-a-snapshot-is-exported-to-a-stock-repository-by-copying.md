# 0062: A snapshot is exported to a stock repository by copying the shard files

**Status:** Accepted after independent review, 2026-11-26

## Context

[ADR 0060](0060-stock-snapshot-restore-reads-a-source-repository.md) lets a tenant move data in from a stock OpenSearch repository. The way out is the other half of R14.8: a repository a stock 3.10 cluster can restore. The native snapshot cannot be that. It is shallow ([ADR 0042](0042-snapshots-taken-shallow-first.md)): it names the published blobs and copies none, so its repository holds nothing a stock node could read. A stock restore needs the bytes of every Lucene file, the SMILE metadata blobs and the `index-N` generation.

The owner decided stock interop is wanted, opt-in, restore first. Export has no Java counterpart in the shell, so there is nothing to port; the target is the layout the recorded 3.10 repository shows (`fixtures/snapshots/stock/`).

## Decision

**Which request.** `PUT /_snapshot/{repo}/{name}` where `{repo}` is a repository registered with `format: "stock"` and not `readonly` takes a standard, copying snapshot of the named indices into that repository. A stock repository registered `readonly` stays restore-only. A native repository is untouched, and its rows in the request-budget table do not change.

**The target store.** Writing is a stronger permission than reading, so it has its own allow-lists, `OSS_STOCK_EXPORT_FS_ROOTS` and `OSS_STOCK_EXPORT_S3_ROOTS`, empty by default: nothing is writable until an operator names a root. The checks of the read-side allow-lists apply unchanged (canonical path under a root, no symlink, an `s3` target that overlaps this deployment's own bucket and prefix in either direction refused). The target store is a wrapper that allows reads, creates and puts under the repository prefix and answers every delete with an error; a failed take leaves orphan blobs, as a stock take does; they are named in no `index-N`, so only a stock cleanup collects them.

**What is written, in this order.**

1. For each shard, each file of its published commit, copied as a whole-file blob `__<id>` (no chunking, so `part_size` is absent; a file above the store's single-object limit is refused 501 before any write), streamed through two pooled buffers as the native restore's copy is. The Lucene footer CRC is computed as the bytes pass and compared with the file's own footer; it is the `checksum` the shard snapshot records, since the native manifest does not carry one. `written_by` is the Lucene version the file's own header or its segment's `.si` records, read as the bytes pass (the restore's file check already reads the footer; the version comes from the `.si` for segment files and from `segments_N` for itself). Stock writes `.si` files and `segments_N` inline (`v__` entries with a `meta_hash`) and no blob; the export writes a blob for every file, which a stock restore reads the same, so the shard snapshot's file list is compared to the recorded one by name, length and checksum, not by blob name. `number_of_files` and `total_size` are the sums over the list.
2. Each shard's `snap-<snapshot uuid>.dat` and a new `index-<generation>` blob of shard files. When the index is already in the repository the new generation keeps every earlier snapshot's file entries (read from the previous generation, one GET a shard), because without dedupe the earlier snapshots' blobs must stay named.
3. Each index's metadata blob (`indices/<index id>/meta-<identifier>.dat`, the identifier a fresh 22-character id, recorded under `index_metadata_identifiers` and `index_metadata_lookup` of `index-N`), its mapping and settings as stock `IndexMetadata`.
4. The snapshot's `snap-<uuid>.dat` and the global `meta-<uuid>.dat`, whose content is the recorded empty global metadata (`include_global_state` is refused). Snapshot uuids and index ids are 22-character URL-safe base64 (`oss_meta::new_id`), the shape the recorded repository shows; the version written is the constant `3.10.0` (stock refuses a snapshot newer than the node), and every field of the recorded `index-0` (`index_metadata_lookup`, `index_metadata_identifiers`, `shard_generations`, `version`) is written and tested against it.
5. `index-N+1`, by **conditional create**: the generation is the fence. A second writer at the same generation gets a conflict. On a conflict the take reads `index-N+1`, adopts it as the base and tries again, at most 16 times, then answers 409 `snapshot_conflict`. A retry rebuilds each shard's new generation from the adopted base's previous generation, so a concurrent take's entries are kept, and reuses the blobs already copied instead of copying them again; its extra reads (the adopted `index-N+1`, the previous generations) are bounded by the 16 tries and are not in the happy path's budget row; this also moves a repository past a crash that created `index-N+1` and died before the `index.latest` put, which would otherwise wedge every later take. Never a lock or lease.
6. `index.latest`, an unconditional put of the new generation, as stock does. A reader that sees the old value reads the old, still valid `index-N`. Two concurrent takes can write it out of order, leaving it one generation behind; a stock reader sees that older, valid generation until the next take, which finds the newer one by the 409 adoption and rewrites `index.latest`.

The generation to extend is read from `index.latest` and `index-N` (two GETs, no LIST). A repository with neither is a new one and starts at generation 0.

**Formats.** An encoder for SMILE in `oss-format` (the decoder's counterpart, same bounds), the Lucene header and footer writer, and the `RepositoryData`, `SnapshotInfo`, `IndexMetadata` and `BlobStoreIndexShardSnapshot` writers. Blobs are written uncompressed: a stock reader detects compression, so the repository's `compress` setting only governs what stock writes. Every writer is tested against bytes the server's own `*_FORMAT` classes wrote, and against the recorded repository: what the Rust node decodes from a Rust-written blob equals what it decodes from the stock-written one for the same index.

**Consistency, with no pin.** A shard is copied from one published commit, which is immutable, so the copy is consistent without a quiesce. The take takes no native register or marker: that pin ([ADR 0042](0042-snapshots-taken-shallow-first.md)) is released only by a snapshot delete, which a stock repository does not have, so a crash would pin the index's blobs for good. The take is optimistic instead. It reads each commit, copies, and verifies every file's length and CRC as it streams; a blob the janitor reclaimed mid-copy (its two-sweep grace and minimum age make this rare) fails the take with 409 `snapshot_conflict` before `index-N+1` names anything, and a retry reads the new commit. A crash leaves orphan blobs in the target and no state in the deployment. The index's incarnation is checked before the copy and again before `index-N+1`, as the native take does (409 on a change).

**No dedupe in the first version.** Stock reuses a file already in the repository when its name, length and checksum match the previous shard generation. The first version copies every file of every snapshot. The cost is bytes, not requests, and it is the opt-in's stated price; a later spec may carry the previous generation. Restoring on stock works either way.

**Refused 501, before any write.** A bucketed or shared-pack index (its files are not whole published blobs of one shard), `include_global_state`, `partial`, a file above the single-object limit, a delete of a stock snapshot (so a deployment can never release an export, and the snapshot a stock cluster deletes is the stock cluster's act), an index whose settings or mapping stock cannot restore.

**No LIST, and request scaling.** Requests scale with files and bytes: per shard one commit read, a ranged read for each buffer of each file, one put for each file, one for the shard's snapshot blob, one for its generation, and one read of the previous generation when the index is already in the repository; per index two describe reads and one put; per snapshot four puts and the two generation reads. Nothing scales with indices that are idle, and nothing is a LIST. The rows are measured and pinned in the budget table.

**Bounds.** The same numbers as the restore: 100 indices, 4,096 shards, 10,000 files a shard, 100,000 file entries in all, 128-byte names, blobs of 16 MiB. The copy reserves two buffers from the memory pool before the first read and answers 429 when it cannot.

**Switch.** `serverless.snapshots.stock.export.enabled` (`OSS_SNAPSHOTS_STOCK_EXPORT_ENABLED`), default off: it copies the tenant's bytes out of the deployment. It is independent of `serverless.snapshots.stock.enabled`, which governs only restoring. Both sides are tested: off answers 501 with no request to either store; on exports. A stock repository registered without `readonly` can be exported to and restored from, each under its own switch.

**The proof that it works.** A repository the Rust node wrote is restored by a stock 3.10 node (the `opensearch-min` build) and answers the searches the source index answered. That run is by hand, like the Java mixed-fleet proof, and is recorded in `VERIFIED.md` with the version and result; until it is run the criterion says NOT-RUN.

## Consequences

- Easier: a tenant takes its data out as a stock-restorable repository, from an operator-named directory or bucket.
- Harder: a SMILE encoder and stock writers to keep against OpenSearch 3.x; every snapshot copies all bytes until dedupe lands.
- Rules out for now: dedupe against earlier snapshots, a delete of a stock snapshot, bucketed and shared-pack indices, and global state. It sharpens [ADR 0042](0042-snapshots-taken-shallow-first.md)'s consequence that Rust has no snapshot delete: that is why export takes no pin. Superseded `index-N` blobs accumulate, since stock deletes the previous generation after a take and export cannot; they are safe.
