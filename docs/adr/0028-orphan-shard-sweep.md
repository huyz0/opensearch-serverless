# 0028: The orphan-shard sweep is an opt-in backstop, resumable and bounded

**Status:** Accepted after independent review, 2026-11-23 (four rounds by a separate subagent given the ADR, the principles and the Java; the first three found the pin order, the capture rule, the shared cursor format and the cost table, all answered above).

## Context

A writer that lost its shard head can still finish a publish it had begun, because publishing is fenced by the manifest register's term and not by the head. The bytes it lands after the delete of an index are under the dead index's uuid: `segments/<index>#<uuid>#<shard>/...`. Nothing reads them and nothing reuses that path. The reclaim queue ([ADR 0012](0012-index-deletes-and-reclaim.md)) purges a deleted index's shards once its intent falls due; it cannot see a blob written after the purge. The shell's `GarbageCollector.collectOrphanedShards` is the backstop: it walks every shard container under `segments/` and deletes those whose index is gone, or exists under another uuid, unless a snapshot or a point in time pins it.

That walk visits every container of the deployment. [ADR 0020](0020-janitor-crate.md) refuses a timer sweep over every index because its cost grows with indexes, and the owner's rule is that requests scale with nodes and bytes and an idle index makes none. The shell runs it anyway, 100 containers a slice. This ADR decides how the Rust janitor offers the same backstop without breaking that rule. It shares the cursor register with the shell: a Java node sweeps whatever the Rust setting says.

## Decision

- **Off by default, and off means no request.** `serverless.janitor.orphan_slice_budget` is a per-node setting read from local configuration (never from a cluster-settings register), default 0. At 0 no timer is registered, no `gc/` register is created or read, and nothing is sent at startup; the node-side test asserts the meter reads zero. A deployment that sees leaked bytes (a billed prefix under a uuid no descriptor names) turns it on. The default flips only when a measurement shows the leak is common enough to pay for the scan, in a PR of its own (the switch rule).
- **One slice an interval, on one node, at most `budget` containers.** Like the tombstone sweep ([node-tombstone-sweep](../specs/node-tombstone-sweep/SPEC.md)), the slice runs only on the live member that ranks first by rendezvous on the fixed name `orphan-sweep`, once every `serverless.janitor.orphan_slice_interval` (default one hour); every other node makes no request for it, so a fleet of any size makes one slice an interval. The three settings are fleet-wide, like the tombstone sweep's interval: if the node that ranks first has a budget of 0 it makes no request and no other node takes over, so a deployment with mixed values has the sweep off until they agree (a test asserts both halves: the first-ranked node with budget 0 sweeps nothing, and a node with a budget that does not rank first makes no request). A slice reads the cursor register `<base>gc/orphan-sweep-cursor`, then lists the next `budget` shard containers strictly after it. The register's value is the shell's, byte for byte, with nothing added: the last container name, UTF-8, empty meaning start over (a test advances it alternately from Rust and from a recorded Java value). Java nodes sweep from the same register whatever the Rust settings say, so a Rust slice that loses its swap to a Java node stops and counts it. If the page is empty the slice writes the empty cursor and ends, which makes a cycle whose last page was exactly full cost one empty slice more.
- **Judge before claiming, claim before deleting.** In this order: (1) read the descriptors of the distinct indexes among the page's containers (a direct, uncached register read each; a read that fails fails the slice, and "absent" means the register read succeeded and found nothing, never a timeout or an error); (2) if any container is a candidate (its index is absent or has another uuid), read the pins (below), and if they cannot be read completely, or exceed the reservation, stop here with the cursor unmoved: the page counts as a failure (see "A page that keeps failing"); (3) claim the page by moving the cursor past it with one conditional swap, and stop if the swap loses; (4) delete the candidates not pinned. A slice whose page has no candidate never reads a pin.
- **Why the order is safe.** A dead uuid never revives: an index is created under a fresh uuid, and creating one writes only its descriptor register (`IndexLifecycle.createIndex`, one put-if-absent, no storage) so no blob exists under a uuid before its descriptor does, so a container with no descriptor naming its uuid at step 1 was either never live or is dead. What can make a dead container needed again is a pin made after it died: a point in time or snapshot freezing the index while it is still live. Creating either publishes a capture record (naming the index and no shards yet) before it reads any manifest (`MetadataPlane`: "records that a freeze has begun, before any manifest is read" for a point in time, and "publishes its provisional pin before capture reads any manifests" for a snapshot; the freeze then calls `verifyCaptureIncarnation` to check the index's uuid after its pin is published and before it reads any captured file), so a freeze that reads files under a uuid has its pin published before the first read, and the sweep sees it at step 2 or the freeze fails its incarnation check against a descriptor that no longer names the uuid. Both are Java code the Java creators run in a mixed fleet; the fixture is the recorded capture record of a Java run. A slice that stalls between steps stays safe for the same reason: a pin created after the descriptor read could only name a live index, and the uuid is dead. A test registers a capture record between the descriptor read and the pins' read, and one between the pins' read and the delete.
- **Pins, in full.** A container is left alone when a point in time or a snapshot names its shard's blobs, and when a capture is in progress that names its index (a view or snapshot entry with a shard count and no shards pins every shard of that index below the count: otherwise deleting an index mid-freeze purges the files the freeze is reading). The slice pages through all point-in-time and snapshot records; a record that cannot be read, or more pins than `serverless.janitor.orphan_max_pins` (default 100,000 `(uuid, shard)` pairs, about 5 MiB) stops the slice with nothing deleted and the cursor unmoved; so do more than `serverless.janitor.orphan_max_pin_records` live point-in-time and snapshot records (default 10,000), counted before they are read, and a record larger than the pooled read buffer (the point-in-time record limit the existing pins use), which reads as unreadable. Pin caps are enforced where a pin is created, never by dropping records at read; a Java-made snapshot has no Rust creation cap, so a deployment whose live pins exceed the setting raises it or keeps the sweep off, and the slice says so in its log and its counter. The slice keeps only each record's `(uuid, shard)` pins, not the records.
- **Snapshots have no "none".** `Sweeper::slice` takes a snapshot-pin source and a point-in-time-pin source and has no constructor that answers "no pins" ([ADR 0020](0020-janitor-crate.md)). Until the snapshot source exists (R14.2) the only snapshot source is one that reads the Java's snapshot records in the Java's format, since the Java shares the bucket and leaves the shards a live shallow snapshot references. A source that cannot read says everything is pinned. A mixed-fleet fixture with a Java snapshot is part of the acceptance criteria.
- **A container is judged only if its name is one this system wrote:** `<index>#<uuid>#<shard>` where the index passes the index-name validation, the uuid is a well-formed uuid, and the shard is an integer in `0..MAX_SHARDS`; anything else is left (a sweep that deletes what it cannot parse deletes somebody else's data). A live manifest never names blobs outside its own container: the Rust writer's manifests are tested for it, and for the Java's restore, clone and shallow-snapshot paths the sweep relies on the snapshot pins above (a shard a live shallow snapshot references is pinned), the only cross-container reference the Java makes; a fixture from a recorded Java run holds one.
- **The deletion** lists the container's blobs under its derived path and deletes them in batches ([ADR 0012](0012-index-deletes-and-reclaim.md)'s purge), the `manifest` register last, so an interrupted deletion is judged again by the next cycle. A blob that is already gone counts as deleted (a racing slice's work). A straggling writer that recreates the register afterwards leaves a container the next cycle collects.
- **A page that keeps failing** (an unreadable descriptor or pin, or pins over the cap) does not stall the cycle for ever. The sweeping node counts consecutive failures of the same cursor in memory; at the third it logs the page's first and last container at warn, adds one to `orphan_pages_skipped`, claims the page and moves on, as the Java does. The count is lost on a restart or when the role moves, which delays a skip and never causes a deletion; under a role that moves more often than every three intervals the skip is best-effort, a liveness limit and not a safety one. A skipped page is collected by a later cycle once its cause is fixed.
- **Dry run applies.** Under `serverless.janitor.dry_run` (default on) a slice makes every request above, lists each orphan's blobs to count them, and deletes nothing.

## What a slice costs

LIST is priced like a PUT, so the listing is the number that matters. A flat listing returns every blob of every container, so a cycle would cost the deployment's blob count over 1,000: a bucket inventory. The slice lists children, not keys.

| Form | Requests to list a page of `budget` containers | Ships |
|---|---|---|
| Portable (`BlobStore::list_children`'s default): one LIST of one key per child, each next LIST starting strictly after the child's prefix (the prefix with its last byte raised, so the child is not returned again) | `budget` LISTs | First, with the sweep |
| S3 delimiter (`CommonPrefixes`, up to 1,000 a LIST) | `ceil(budget / 1000)` LISTs | A second PR, high-risk, with its own budget row |

The rest of a slice, for a page of `c` containers over `i` distinct indexes, `o` orphans holding `b` blobs in all:

- Always: 1 GET of the cursor, the listing, `i` GETs of descriptors, and 1 conditional PUT of the cursor (a create on the first slice ever, a swap after). A slice that loses the swap (only to a Java node, since one Rust node sweeps) paid all of that plus the pins below if it needed them, and stops.
- Only when a page has a candidate (`k > 0` containers whose index is absent or has another uuid): the pins, one LIST page per 1,000 views and per 1,000 snapshots (at least 2 LISTs) plus 1 GET per live record, read before the swap. These scale with the live views and snapshots, up to `orphan_max_pin_records`, not with the budget; a page that fails pays them up to three times.
- Per orphan deleted, unless dry run: `max(1, ceil(b / 1000))` LISTs, `ceil(b / 1000)` DELETE batches, 1 DELETE of the register. In dry run the listing is made to count the blobs and nothing is deleted. A pinned candidate costs none of this.

A slice with no candidate on the S3 form is `i + 3` requests (`i <= budget`), and on the portable form `budget + 1 + i + 2` (one more LIST finds the end of the children when the page is short); with a candidate it adds 2 LISTs and a GET per live pin record. The role being on one node is what keeps the fleet at one slice an interval: the other nodes make no request at all, and the interval is a setting (default an hour), so the cycle takes `ceil(N / budget)` intervals.

The cycle length, not the cost per slice, is what grows: 100 containers a slice and an hourly interval is 10 hours for 1,000 containers and over a century for 100 million, so a large deployment raises the budget, and a failed slice is retried at the next interval, and a page that fails three times in a row is skipped and counted, so one corrupt record delays the cycle by three intervals and not for ever. The listing and descriptor reads are capped per slice by the budget, the pin reads by `orphan_max_pin_records`; together they are the only cost that scales with indexes, and it is zero when off.

## Memory

A slice holds one page of container names (at most `budget`, capped at 1,000), one descriptor per distinct index among them, the pins' `(uuid, shard)` set and one batch of keys to delete. The slice reserves its worst case from the node's pool before it starts, with the pin set fixed at the reservation; a slice whose pins exceed it stops with nothing deleted and counts as a failure of its page (three in a row skip it), never refused to a client.

## Consequences

- A leak the reclaim queue cannot see is eventually reclaimed, at a cost the operator chooses.
- The blob store gains `list_children`, a default method over `list_prefix`, with an S3 delimiter override later; that override is a request-pattern change, so its PR is high-risk and carries its own budget row.
- Rules out: sweeping on a timer by default, judging a container whose index could not be read, a "no pins" source, and deleting a shard a capture in progress may be reading.
