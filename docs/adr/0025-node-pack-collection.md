# 0025: Node pack collection

**Status:** Proposed (revision 2). A second independent review (2026-11-26) found the first revision sound in design but leaving costs that grow with elapsed time or churn, and one claim the merged code contradicts; this revision answers each. Until it is Accepted and built, `serverless.segments.node_pack.enabled` ([ADR 0024](0024-node-packs-in-the-writer.md)) is for bounded measurement runs only: packs are written and never deleted.

## Context

A pack is deleted only when nothing names it. The Java's `NodePackCollector` does this with in-memory state: it tracks each pack from when it first saw it, judges it 15 minutes later, deletes it after two unreferenced sightings 60 seconds apart, and rechecks a pack found referenced on a backoff capped at 6 hours. Four properties of that design break the owner's rules ([principles](../principles.md#cost-s3-requests-are-the-bill)) or do not carry over to nodes that own nothing:

1. **A capped recheck costs `n` manifest GETs every 6 hours per pack for as long as the pack lives.** With no cap it is `O(log lifetime)` per pack per shard (about 19 a year: provisional arithmetic), at the price of garbage found at most twice as late as it died, and per-pack space amplification that is not bounded: one idle shard's small blob pins a pack of up to 64 MiB holding other shards' dead blocks.
2. **A long-lived pack at ordinal `k` stops the ledger's `collectedBelow` prefix.** After any restart, or in a reaper pass, the epoch is re-read from `collectedBelow` to `high`: one header GET per ordinal, including the 404s of deleted slots, about 86,000 a day at one pack a second. That is the elapsed-time cost, and the Java's recheck cap hides it.
3. **The state is in memory.** A restart, or a reaper that runs once, starts from nothing: it cannot judge a pack until 15 minutes after it first saw it, and it forgets the schedule. The ledger holds only `(epoch, collectedBelow, high)` per epoch and the Java reads exactly that (version 1).
4. **Referenced-ness is judged from the pack's header,** by the manifests of the shards named in it, plus views and snapshots. A shard not named in the header that nonetheless names the pack by location (a clone, a restore, a split) is invisible to it.

## Decision

Numbers below are arithmetic from the stated rates, provisional until the R11 measurement.

- **Rotate the epoch every 1,024 ordinals, and reserve the high ahead.** As before: a new epoch is one ledger swap per 1,024 packs; before spending ordinals `base..base+7` the writer raises the recorded `high` to `base+8` by a monotone-max compare-and-swap (at most 8 attempts, then the publish fails and retries), so no pack lands at or above the recorded `high`. About 12% more PUTs on the pack path, counted in the R11 measurement. A crash leaves 404 slots, not leaks.
- **Collection progress is held per ordinal, not per prefix (bounds the re-read).** A rotated epoch pinned by one long-lived pack would otherwise be re-read, 1,024 headers, per live epoch at every restart: about 84 new epochs a day at one pack a second, so cost would grow with elapsed time. Each node's collected ordinals are kept in a Rust-only sidecar register `packs/<node>/collected`: per live epoch, a 128-byte bitmap of the ordinals already deleted or never written, plus the epoch's `high`. The Java's ledger (version 1) is untouched and still advanced as far as its contiguous prefix goes; the Java does not read the sidecar. After a restart the collector reads the sidecar (1 GET) and re-reads only the headers of ordinals not marked: the **live packs**, which scale with bytes, never with elapsed time. The sidecar is written once per pass that collected something (a pass is at most every 10 minutes, so at most 144 PUTs a day per node with garbage, 0 when idle); an epoch whose bitmap is full is dropped from it and from the ledger, and the newest epoch is never dropped. Size: 128 bytes an epoch, with 8 bytes each for the epoch and its `high`, that is 144 bytes an epoch, so the 256 KiB register cap holds about 1,800 live epochs, which is about 1.8 million live packs of one node; a node reaching 1,500 live epochs stops rotating and says so in the log (a stated bound, not a silent one).
- **One reference-source abstraction, and the check is over persistence, not construction.** `PackReferences` answers "does anything name this pack" over every place that persists a manifest or a file location, and like `Pinned` in the janitor ([`crates/janitor/src/gc/pins.rs`](../../crates/janitor/src/gc/pins.rs)) it has no "none" implementation. The sources, by home today: commit manifests and the register (`crates/format/src/manifest.rs`, `crates/writer/src/publish/upload.rs`); a bucketed member's entry (`crates/format/src/bucket_manifest/compact_write.rs`); frozen views and points in time (`crates/reader/src/frozen.rs`, `crates/meta/src/pit/capture.rs`, `crates/janitor/src/gc/point_in_time.rs`); snapshots and stock restores/exports (`crates/format/src/snapshot_restore.rs`, `crates/meta/src/snapshot_restore.rs`, `crates/meta/src/stock_restore.rs`, `crates/meta/src/stock_export.rs`). A clone, restore or split reaches a pack by **copying a manifest or location string**, never by calling the constructor (`crates/writer/src/pack/store.rs`, the parser in `crates/format/src/location.rs`), so a rule over constructors would pass while a copier is missing. The mechanical rule is therefore over files: every source file that persists a manifest, a bucket manifest or a location (it names `CommitManifest`, `BucketManifest` or `FileLocation` and writes a register or blob) is listed in an allow-list file that `PackReferences` also names, so a new persister fails the check until it is registered. A planted violation goes in `scripts/selftest-checks.py` and a row in [mechanical-gates](../mechanical-gates.md) with the collector's first slice. A cluster whose snapshots cannot be read (a Java node made them) is never judged: collection stops there, and says so.
- **One collector per window, a LIST per window, a floor on passes.** The points-in-time inventory is a LIST ([`crates/meta/src/pit/sweep.rs`](../../crates/meta/src/pit/sweep.rs)), priced like a PUT, and it scales with the number of views, so it is paged by 1,000 and a pass is bounded by `ceil(views / 1,000)` LISTs. If every node ran a pass, 10,000 nodes at one pass per 10 minutes would issue 1.44 million of them a day, all returning one answer. So the window (`floor(now / 10 min)`) names its collector: the member at `hash(window) mod n` of the live membership sorted by node id. There is no lease: a node that disagrees about membership also collects, which costs duplicate HEADs and a lost compare-and-swap, never a wrong deletion. That is **144 inventory LISTs a day per cluster (plus paging), independent of node count**, and no LIST at all when no pack is due. A pass with nothing due makes no request beyond the sidecar GETs of ledgers with live epochs. A view being captured halts judgement; a capture placeholder older than its keep-alive is treated as dead.
- **Which ledgers a collector reads is bounded by nodes with live packs.** A writer adds its node id to one of 16 index registers `packs/index/<hash(node) mod 16>` when it first records an epoch (once a process start, not per pack) and the collector removes the id when the node's sidecar (a Java node: its version-1 ledger) shows no live epoch and the node's lease is gone. **The add happens before the writer's first pack, and always writes**: each new epoch from a process start rewrites the node's entry (a fresh timestamp), so the register's generation moves even when the id is already listed and a removal made against an older read fails, as `add_epoch` does for the ledger, and fails the publish if it cannot be made, so a pack is never written that the index cannot find. **The removal is a compare-and-swap** on the index register's generation read *before* the collector reads the node's sidecar and ledger: a writer's add in between moves the generation and the removal fails, to be retried at the next pass. Both sides retry at most 16 times with jitter. A register holds about 625 ids of at most 40 bytes (about 25 KB, far under the cap), so a fleet restart is hundreds of contending swaps per register, bounded by that retry count; the interleaving and the bound each have a test. The collector reads the 16 registers (16 GETs a pass) and then only the listed ledgers, so the set grows with nodes that hold live packs, never with every id the membership ever listed, and a scaled-in node's packs are found without its lease. A fully collected dead node's ledger and sidecar are deleted. **Scope:** a Rust writer adds itself, and the window's collector adds Java members (decision 1). A Java node's ledger is found only while it is a member (the members index, `crates/format/src/members.rs`); after it leaves, nothing names it. Decision 1 (chosen: option b) closes that: one marked LIST of the children of `packs/` seeds the index registers once per cluster, and one LIST of a dead Java node's `packs/<node>/` prefix retires it.
- **One clock for each question, stated.** *The writer's swap deadline* is the age since the pack landed, on `CLOCK_BOOTTIME`, which keeps counting across a suspend or VM freeze. The merged check ([`crates/writer/src/publish/publisher.rs`](../../crates/writer/src/publish/publisher.rs), [`crates/writer/src/publish/packed.rs`](../../crates/writer/src/publish/packed.rs)) reads `Instant`, which is `CLOCK_MONOTONIC` and stops across a freeze: it can under-count exactly the paused-writer case. The collector's first slice replaces it with a boot-time clock read through `rustix` (already a dependency of `oss-blob` for its file I/O; the first slice adds its `time` feature, a feature change on a pinned crate, and no `unsafe`), and the register swap call carries its own time limit of 60 seconds, so the check plus the call is at most 5 minutes plus 60 seconds. *The collector's judgement age* is the object's server-side age: `LastModified` and the `Date` of the same HEAD response, both stamped by the store, so no node's clock enters it; a pack is judged at 15 minutes. Writer and collector never compare clocks: the 9-minute margin between the 6-minute worst case and 15 must exceed any pause between the check and the swap, a stated bound that every timeout in the system already assumes. No lease is claimed to fence a paused writer.
- **Memory.** A tracked pack is its key and its shard keys, not its header (a header may be 4 MiB), capped per entry and in total; tracked bytes are reserved from the node's pool ([ADR 0004](0004-bounded-memory-and-streaming.md)); at the cap the collector stops adding and says so.
- **Dead nodes' packs** are collected by the window's collector from the index registers above, by a Rust ledger and sidecar. A dead **Java** node's epoch is read from its version-1 ledger by its probe of 16 slots past `high`; see decision 1 for how a departed one is found.

## Decisions for the owner

1. **Packs of Java nodes that have left.** Two gaps: a departed Java node is in no index register, so its ledger is not found; and a run of 16 or more ordinals spent without a pack in a Java node's epoch hides the packs behind it from the Java's 16-slot probe (Rust writers cannot leave that gap, they reserve ahead). Options: (a) collect Rust nodes' packs only; a departed Java node's packs are left to the Java's own collector, or leak; (b) one `// LIST:` of the children of `packs/` once per cluster, to seed the index registers with every node id that has a ledger, and one LIST of a dead Java node's `packs/<node>/` prefix when the collector retires it. "Once" is enforced, not assumed: the seed is resumable: `packs/index/seeded` holds `{state, cursor}`, created in-progress by the first collector, advanced by one compare-and-swap per LIST page (a racing collector loses the swap and stops, so duplicate seeding is bounded to one page), and set `done` after the last page; a crash resumes from the cursor, and every collector and restart that reads `done` skips. The seed finds only nodes that left before the first Rust collector ran: afterwards the window's collector, while it reads the members index (`crates/format/src/members.rs`), adds each Java member to its index register with the same always-write add, so a Java node that joins after `done` and then leaves is already listed, and the retirement LIST of a dead Java node's `packs/<node>/` runs once, when the collector first sees its lease gone, and its result (the pack keys) is written once to its own blob `packs/index/retired/<node>`, capped at 10,000 keys (a node over the cap is left unretired and logged), with the index entry holding only a state flag and that blob's key so the 40-byte entry bound holds; later passes judge those keys without another LIST even while a long-lived referenced pack keeps the node listed; the ledger and sidecar are deleted with the last pack. At most 4 retirement LISTs run in a pass. `packs/` children come back 1,000 to a page, so seeding costs `ceil(node ids ever seen / 1,000)` LISTs, once; only ids whose ledger shows a live epoch enter an index register, so the register cap holds the live fleet, not history. **Chosen (2026-11-26, by the writing thread under the owner's "decide for me"; binding once this ADR is Accepted): (b)**, against storage that is otherwise never freed. The LISTs carry `// LIST:` and never run on a read or write path. The collector's first slice owes a test of the seeding LIST and of the 16-spent-ordinal gap.
2. **A recorded exception to "never elapsed time per index".** With the sidecar this is no longer needed for the epoch re-read; it is needed only if the owner wants the Java's logarithmic recheck of a long-lived referenced pack (about 19 manifest GETs a year per pack per shard, provisional). Recommended: do not build the recheck; a referenced pack is re-judged only when a source it named changes (a manifest swap or a view deleted), which costs nothing while idle.
3. **Pack space amplification.** One long-lived blob pins its pack (up to 64 MiB of other shards' dead blocks). Recommended: accept, measure in the R11 run; a repack is its own decision.
4. **The 12% PUT cost of reserving the high ahead,** against a leaked pack per gap. Recommended: accept, include it in the R11 measurement.
5. **Whether to build this before the R11 measurement** shows what packs save. Recommended: measure first with packs on and no collector in a bounded run, then build; the design above is what the build would follow.

## Consequences

- Nothing here is built; ADR 0024's switch stays for bounded measurement runs.
- Steady-state cost, all provisional: 144 inventory LISTs a day per cluster plus paging; at most 144 sidecar PUTs a day per node that collected something; 16 index GETs per pass; a HEAD per due pack once; a node holding a live pack costs one sidecar GET per pass (144 a day a node, so 1.44 million a day if all 10,000 nodes hold one), and each sidecar PUT is at most the 256 KiB cap; seeding is `ceil(node ids ever seen / 1,000)` LISTs once, and retiring a Java node is one LIST, a cost that follows node churn, not time, and a cluster with no live packs makes none beyond the window's LIST. Nothing scales with documents, indexes or time per index.
- Tests the collector's first slice owes: a second collector and a restart after seeding issue zero seeding LISTs; two simultaneous first collectors seed at most one extra page; a crash mid-seed resumes from the cursor; a Java node that joins after `done`, leaves and is retired; a dead node with a live pack causes no second LIST across N passes; a retirement over the key cap is left unretired and logged; a rotation stop at 1,500 live epochs; a restart re-reads only live packs' headers, not 1,024 an epoch; the index add/remove interleaving and its retry bound; a mixed-version case (a Java-written version-1 ledger, a Rust prefix advance and a dropped epoch, then a Java read); the file-persister allow-list check with its planted violation. The `ledger.rs` header's "never per pack" is false once `high` is reserved ahead (a ledger swap every 8 packs, about 10,800 a day per node at one pack a second, a cost that scales with bytes) and is corrected with it; the 144-a-day inventory figure is steady state and is exceeded while membership churns.
- Rules out: a capped recheck, a LIST of any live node's pack prefix, every node collecting, collection by the owner only, judging while a reference source cannot be read, any claim that a lease fences a paused publisher, and an allow-list of constructors as the reference check.
