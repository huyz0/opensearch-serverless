# 0058: HTTP/2, HTTP/3 and gRPC are served by an in-process front that bridges to the HTTP/1.1 server

**Status:** Accepted after independent review, 2026-11-25 (accept with changes, all folded in below: connection bounds, worker accounting, a forgery-proof client address, smuggling rules, flow control, HTTP/3 and gRPC limits). Amends [ADR 0006](0006-http-stack.md): the async runtime and inbound TLS it ruled out are allowed, in the front only.

## Context

[ADR 0006](0006-http-stack.md) chose a blocking HTTP/1.1 server of our own and ruled out HTTP/2, TLS at the node and an async runtime "for now", naming the trigger for revisiting it. The owner has since asked that the Java shell and the Rust node both serve HTTP/2, HTTP/3 and gRPC. [docs/protocols.md](../protocols.md) records what each side serves today: the Rust node speaks HTTP/1.1 in clear text and nothing else; the Java shell's Netty transports already speak HTTP/2 and HTTP/3, and upstream's gRPC transport exists, but the shell does not start it.

Forces:

- **The handlers and the limits are the product of ADR 0006.** Head limits, 413 and 429 admission before a body is read, the slow-peer rule, the parked-search queue ([ADR 0056](0056-over-share-searches-wait-off-the-workers-in-a-bounded-queue.md)), the error shapes and authorisation at the route all live in `oss-rest`'s connection loop, which is written against a `TcpStream`. A second implementation of those rules for HTTP/2 would drift from the first.
- **HTTP/2 and HTTP/3 multiplex many requests on one connection**, so the one-worker-per-connection model does not carry over, and neither protocol has a blocking server crate. `h2` and `quinn` are async on tokio.
- **HTTP/3 is QUIC, and QUIC is TLS 1.3 only.** There is no clear-text HTTP/3, so a certificate is a precondition, and the node has no inbound TLS today (outbound TLS exists only in the S3 and plugin-proxy clients, through `ureq` and `rustls`).
- **Memory is bounded by construction** ([ADR 0004](0004-bounded-memory-and-streaming.md)): a stream must not buffer a body, and every buffer is charged to the node budget at start.
- **Connections per node are hundreds** ([ADR 0006](0006-http-stack.md)); a multiplexed client needs far fewer connections, not more.

| Option | For | Against |
|---|---|---|
| **A protocol front in its own crate: tokio, `h2`, `quinn` and `h3`, `rustls`; each request stream is bridged to the existing HTTP/1.1 server over a loopback connection** (chosen) | The server, its limits, its error shapes, its admission and its tests are reused unchanged; the front is a translator, as the buffering proxy ADR 0006 already recommends, but in the process; every protocol difference lives in one crate behind one switch | A loopback socket and a second head parse per stream; the async runtime and its dependency tree are in the build when the front is |
| Move `oss-rest`'s connection loop to a stream abstraction and serve HTTP/2 straight into it | No loopback hop | `conn.rs`, `timed.rs`, `linger.rs` and the parked-search queue all use `TcpStream` directly (socket timeouts, `peek`, `shutdown`); the refactor touches every limit, is far larger than the protocols are, and has no way to carry QUIC streams without the same async runtime |
| Replace the server with `hyper` | One stack for HTTP/1.1, 2 and 3 | ADR 0006's reasons stand: pooled-buffer reads, exact reserve-before-read and the slow-peer rule would all be re-derived on `hyper`'s body types |
| Tell operators to put an HTTP/2 and HTTP/3 proxy in front | No code | The ask is that the node serves them; gRPC needs more than a proxy can do, which is to speak the protobuf messages |
| Hand-roll HTTP/2 and QUIC | No dependency | HPACK, flow control and QUIC loss recovery are thousands of lines each, with security history; not our product |

## Decision

1. **A new crate, `oss-edge`, is the protocol front.** It is linked into the node binary and runs in the node process: the node itself translates HTTP/2, HTTP/3 and gRPC down to its HTTP/1.1 handling, with no external proxy or sidecar (owner's direction, 2026-11-25). It owns one small tokio runtime (`edge.threads`, default 2) and no handler logic. It is built only with the node's `edge` cargo feature; a build without it has no tokio, `h2`, `quinn` or `h3` in its tree, and the node behaves as today.
2. **Every listener is explicit and off by default.** Each is an address that is empty unless set, so nothing opens a port until an operator names it:
   - `h2c`: HTTP/2 over clear text with prior knowledge, for a trusted network or a TLS-terminating load balancer.
   - `tls`: TCP with TLS 1.2 and 1.3 and ALPN `h2` then `http/1.1`, so one port serves both versions to a browser, `curl` or an SDK.
   - `h3`: UDP, QUIC with ALPN `h3`. The UDP port is its own setting. QUIC 0-RTT is off (a replayed bulk or index POST is not idempotent) and address validation is on. A client learns it from `Alt-Svc: h3=":<port>"`, which the `tls` listener adds to its responses when `h3` is configured.
   - `grpc`: HTTP/2 with ALPN `h2` over TLS when a certificate is configured, clear text when not, serving the gRPC services of decision 6.
   The certificate chain and private key are PEM files named by `edge.tls.cert` and `edge.tls.key`; `tls`, `h3` and a TLS `grpc` refuse to start without them, and the node refuses to start with a listener set and no certificate where one is required. They are read at start; a reload is a restart.
3. **A request stream becomes one HTTP/1.1 request on a loopback connection to the node's own listener.** The front checks the pseudo-headers, drops hop-by-hop headers, maps `:authority` to `Host`, writes the head, streams the body, parses the response head with `httparse`, and streams the response back. The server's limits answer as they would to an HTTP/1.1 client: 413, 429 and 400 reach the client as the same status and body. `oss-rest` is unchanged: no handler, `Request` or `Response` sees the protocol. Translation rules, each held by a spec criterion: exactly one `:method`, `:path` and `:scheme`; `:path` origin-form only (no whitespace, control characters, `#` or bytes above 0x7F; `*` only for `OPTIONS`); CR, LF and NUL in a name or value, and uppercase names, reset the stream; `te` other than `trailers` is refused; multiple `cookie` headers are joined with `; `; `:authority` wins over `Host`; a declared `content-length` must equal the DATA bytes received or the stream is reset; with none, the body goes chunked; the response's `connection`, `keep-alive` and `transfer-encoding` are dropped and its chunking removed under a bound; `1xx` answers from the loopback (`100 Continue`) are swallowed, never sent as the final response; request and response trailers are dropped; a `HEAD` answer ends the stream on its `HEADERS` frame. The rewritten head must fit ADR 0006's 4 KiB line and 16 KiB header limits after expansion, else 431. Each stream uses its own loopback connection with `Connection: close`, so ADR 0006's idle-yield rule never applies to it. A loopback 503 or 429 reaches the client as that status and body, as it would over HTTP/1.1 (the handler's `429 circuit_breaking_exception` carries a body clients read, so it is never turned into a retryable reset); only the front's own `max_streams` refusal is `REFUSED_STREAM` (HTTP/3: `H3_REQUEST_REJECTED`). The slow-peer rule of ADR 0006 still holds: the worker's blocking read on the loopback counts against it, and the front's own flow control is what makes a slow client slow the loopback, so a slow direct client costs a stream, not a worker's idle time.
4. **Streaming in every protocol (owner's direction, 2026-11-25).** No protocol holds a whole body: an HTTP/2 or HTTP/3 request body flows from DATA frames to the loopback socket and a response flows back chunk by chunk, each stream bounded by its own flow-control window; a body larger than the node's memory budget passes through each protocol in a test. gRPC decodes one message at a time (bounded by `max_message`), and streaming RPCs are served message by message.
4. **Bounded by construction, streams and connections both.** `edge.max_streams` in flight across all listeners (default `workers / 4`, and a larger value is a start error, because the loopback connections are served by the same `workers` and count against `max_connections`; the quarter leaves the rest to HTTP/1.1 clients and is a setting, not a measurement). `edge.max_connections` bounds edge connections (default 256), with `edge.handshake_timeout` (10 s) and `edge.idle_timeout` (60 s); a connection past the bound is closed before the handshake. The initial h2 stream window is `edge.stream_buffer` (default 64 KiB) and the connection window is `max_concurrent_streams x stream window`, so one stalled stream cannot stall its siblings; `max_concurrent_streams` per connection is 16. The charge to `Pool::RequestBodies`, taken at start, is `max_streams x 2 x stream_buffer + max_connections x edge.connection_overhead` (default 128 KiB, covering HPACK tables, TLS buffers and h2's received-data window; QUIC state and UDP socket buffers are counted the same way), so the front does not start if the pool cannot hold it. A stream past `max_streams` is refused with `REFUSED_STREAM`. Flow-control credit returns to the client only as the loopback socket accepts the bytes, so a slow server slows the client instead of growing a buffer. Header-list size and frame sizes follow the HTTP/1.1 head limits; a connection is closed on rapid reset, continuation, settings and ping floods.
5. **A request costs the same S3 requests as over HTTP/1.1**: the front makes none, and a stream reaches the same handler. The front takes no lock and holds no state shared between nodes.
6. **gRPC (its own spec, before it starts) serves the services upstream OpenSearch's gRPC transport serves**, so existing clients work unchanged: `DocumentService/Bulk`, `SearchService/Search`, `SearchService/CreatePit` and `SearchService/DeletePit` of `opensearch-protobufs`, plus `grpc.health.v1.Health`. A unary message is decoded, mapped to the equivalent REST request, bridged as in decision 3, and its JSON answer mapped back to the response message; gRPC status codes follow the table upstream uses for REST statuses. `edge.grpc.max_message` (at most `max_content_length`) is charged to the request-body pool per call, because a protobuf message is decoded whole; compressed messages are refused with `UNIMPLEMENTED`; `grpc-timeout` is honoured; `grpc-status` and `grpc-message` (percent-encoded) go in trailers. The REST-to-gRPC status table is written in that spec. The messages are mapped from the published `.proto` files with a generated mapping, not hand-written for each query type. Only the services above are served; any other is `UNIMPLEMENTED`. This is the least certain part of the decision: the mapping from protobuf to REST JSON is only as faithful as the schema, and the first slice states how much is covered. If it is not covered, the call is refused with `UNIMPLEMENTED` and a message, never approximated.
7. **Each protocol is a setting, a slice and a test of its own.** HTTP/2 over `h2c` and `tls` lands first, then gRPC on it, then HTTP/3. Each is gated by its listener address being set. No further switch is needed: a feature that is off opens no port and costs no memory, and one that is on has no downside to the HTTP/1.1 path, whose tests are untouched.

## Consequences

- HTTP/1.1 behaviour is unchanged and its tests pin it. The new code is exercised by new tests against a real server, with `h2` and `quinn` clients in the tests and `curl --http2-prior-knowledge` and `--http3` for the evidence a person can rerun.
- Every stream costs a loopback connection and a worker for its duration, so HTTP/2 concurrency is bounded by the same workers as HTTP/1.1. Multiplexing saves connections and handshakes; it does not add worker capacity. A deployment that wants thousands of concurrent slow streams per node needs the event-loop revisit ADR 0006 names, and this ADR does not remove that need.
- The node gains inbound TLS, which the security work ([ADR 0043](0043-security-configuration-as-document-sets.md)) can use: with a TLS listener, a node can serve security on without a TLS-terminating proxy, and `allow_plain_http` is no longer the only way to start it. That change is not made here.
- The client address is the loopback address's to the handlers, and no handler or rule (including [ADR 0043](0043-security-configuration-as-document-sets.md)) treats a loopback peer as privileged; the spec holds that by a search of the tree. The front does not set `X-Forwarded-For`: the main listener is reachable by any client, so the header could not be told from a forgery. If the peer address is needed later, it travels in an internal header carrying a per-process secret that the main listener strips from every request that lacks it. Authentication headers pass through untouched.
- The tokio dependency tree enters `Cargo.lock` (`cargo deny` and the licence check cover it) and the `edge` build is larger; a deployment that does not want it builds without the feature.
- What it rules out: HTTP/3 without TLS, HTTP/2 server push, request compression ([ADR 0006](0006-http-stack.md) still holds for it), gRPC reflection in the first gRPC slice (gRPC streaming calls follow once the unary services stand, for the services that offer them, under the same bounds), and a certificate reload without a restart.
- The Java shell is a separate decision in [docs/protocols.md](../protocols.md): its transports already speak HTTP/2 and HTTP/3, and the gap there is configuration and a missing start of the gRPC transport.
