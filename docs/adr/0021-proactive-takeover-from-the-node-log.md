# 0021: Proactive takeover reads the dead node's log, not a registry of its shards

**Status:** Accepted after independent review, 2026-11-20 (two rounds; the first found the O(fleet) fence cost, the missing recovery of an absent reaper, the missing refresh surface, the shard pre-checks and the unbounded header, all answered below; the second found specification gaps only, answered below).

## Context

R8.2 asks what happens to a dead node's shards. Today a shard is taken **lazily**: the first write routed to a shard whose head names a dead owner acquires it, replays the predecessors' logs and publishes ([writer takeover](../specs/writer-takeover/SPEC.md), [node takeover](../specs/node-takeover/SPEC.md)). Nothing takes a shard nobody writes to.

The Java shell also takes shards proactively, finding the dead node's shards by LISTing a per-node assignments (claims) folder, written with one PUT per shard acquired (as described by the R7 thread; not re-read from the Java here). That is a PUT per acquire and a LIST per death, both of which [principles](../principles.md#cost-s3-requests-are-the-bill) rule out: requests scale with nodes and bytes, never with indices or shards held.

What a dead node's shards need is not symmetric:

- **A shard whose commit holds everything the node logged** (almost every idle shard) needs nothing. Its published commit is durable, readers read it whatever the head says, and the next write takes it lazily at no extra cost.
- **A shard the dead node logged records for and did not publish** is the only one with work outstanding: those acked writes are in the dead node's log only, readers must read that log until someone replays it, and the janitor cannot free the log ([janitor-node-log](../specs/janitor-node-log/SPEC.md): StillNeeded until every shard is published past).

The second set is exactly the shards the node's write log names. The log's header names each shard once with its records (`NodeLogTakeover::named`, which the janitor already reads), and its size is bounded by publishing, not by how many shards the node holds: lazy publish bounds a shard's unpublished age (default 1 s, or the index's refresh interval) and count, so the set is the shards written since each last published.

Cost of doing nothing for that set, per [ADR 0015](0015-cluster-crate-and-node-leases.md): a dead lease that still names epochs is never pruned and every live node reads it on every refresh. At 200 nodes refreshing every 10 s that is about 72,000 GETs an hour for each dead node until its shards are taken and its log collected, roughly $250 a year at $0.40 per million GETs (provisional arithmetic, not measured). Fleet churn makes that recur.

## Options

1. **Per-node claims registry (the Java's).** One PUT per shard acquire, one LIST (or a register) per death. Rejected: the PUT scales with shards held, and a node that crashes between acquiring a head and writing the claim leaves a shard the registry misses, so it needs the lazy path anyway.
2. **Per-node summary object rewritten at publish or acquire time.** Same PUT problem at a lower constant (one per change of the held set), plus a window of loss between the head CAS and the summary write. Rejected for the same reasons; it adds a durable index of a fact the head already holds.
3. **Lazy only.** Zero new requests, but the dead lease and log stay until every named shard is written again, the recurring read above is paid, and the first write to a hot shard pays the revoke, acquire, restore and replay inside its request.
4. **Derive the set from the log's header (chosen), lazy for everything else.** No new object, no LIST, no PUT beyond what a lazy take already does.

## Decision

- **Only designated reapers act.** For a dead node, the reapers are the first `reapers` (default 2) live ingest writers in rendezvous order of the dead node's id (a new `reapers_for(dead_id, live, n)` in `oss-cluster`, hashing `("reap", dead_id, node_id)`; capacity is ignored, and a reaper without pool room defers, leaving the lazy path). Only a reaper fences the dead node's epochs (as the successor), reads the headers and takes shards, so the cost of a death is O(reapers), not O(fleet). The first reaper starts at once; the second starts when the first refresh at or after the dead lease's expiry plus one refresh interval still sees the lease naming epochs, and skips shards whose head already moved. Worst case is therefore two reapers each paying the fence, headers and per-shard pre-checks (2x a death, not O(fleet)); no node shares a clock with the first, only the lease's own expiry. If both reapers die the set is recomputed over the live view on the next refresh and another node becomes a reaper.
- **The trigger is a new surface of the membership refresh,** not something it offers today: it must report a dead (expired or revoked) member whose lease names log epochs, whether or not the node saw it live. This is an `oss-cluster` API change, made from data the refresh already reads (the digest or the lease). The refresh already GETs and decodes every listed expired lease each refresh (the digest holds live leases only), so surfacing a dead member with its epochs, and whether it is revoked or expired, costs no extra read; there is no timer over nodes, shards or indices.
- **Each named shard is checked before it is taken**, as the janitor judges it: a name the header does not know is skipped (taken lazily, and the janitor's rule for it is unchanged); the descriptor is read and an index deleted or recreated under another uuid is skipped; the head is read and a head owned by a live node, or already at a term past the dead node's, is skipped. Cost: one descriptor GET and one head GET a named shard, paid by the reaper only.
- **A take is the existing take.** Acquire the head, restore the commit, replay, publish, settle ([writer takeover](../specs/writer-takeover/SPEC.md)). No new write path and no new fencing; the cost per shard is what a lazy take costs, paid earlier. The janitor's collector then finds every shard published past and frees the log, and the lease stops naming epochs.
- **Bounded.** A pass takes at most `max_concurrent` shards at once (default 16; it was 4 until the opens that serialized them were fixed and a 1,000-shard take measured 2.3 times the Java's time, [takeover-scale](../specs/takeover-scale/SPEC.md)), each reserving the engine's worst case from the node's pool first (ADR 0004); a shard without room stays for the next pass or the lazy path and is never refused to a client. A pass has a deadline. Every shard a node takes proactively enters the open-indexes pool ([ADR 0014](0014-open-indexes-pool.md)) like any other and is closed least recently used first.
- **Hot shards first, for free.** The header names the recently written shards, so the shards most likely to be written next are the ones taken before the first write.
- **Lazy takeover stays the fallback and the correctness path.** A pass is an optimisation: a node that died, restarted, never saw the death, or lost the winner computation costs nothing but a lazy take later. Nothing relies on the pass having run.
- **Not taken proactively:** shards the log does not name (nothing outstanding), and shards of a Java node that keeps per-shard logs (no node log to read).
- **A switch, `serverless.takeover.proactive.enabled`, default on** (flipped from off after the R8.6 fault suites, [proactive-takeover-faults](../specs/proactive-takeover-faults/VERIFIED.md)). Under the switch rule it flips on when the fault suites (R8.6) show write p99 within 5%, no extra requests on any path that exists today, no search regression and the crash tests passing, recorded in a PR of its own. Existing lazy-takeover tests pin the off behaviour unchanged; new tests cover the on behaviour; both run in CI.
- **Measured cost of the default.** A single reaper adds one descriptor GET per death over lazy takes, but with two reapers (kept for redundancy) the end-to-end three-node, six-shard test makes about 24 more requests per death (514 to 538, +4.7%) on the emulator, because each reaper makes its own checks; no LIST. It is paid once per death and ends the recurring read of the dead lease. `OSS_PROACTIVE_TAKEOVER=false` is the revert switch. Follow-ups: measure the requests per hour of that old recurring dead-lease read to confirm the break-even; embedding RustFS as a crate in the tests (optional).
- **Mixed fleets.** Rust nodes write no claims and read none. A Java node's proactive takeover of a Rust node's shards finds no claims and falls back to the lazy path, which reads the head and works. A Rust node proactively takes a Java node's shards when that node logs to a node log, which is the Java's default.

## Cost, memory, fencing and scale

- **Requests.** Per dead node, per reaper: the fence (a conditional create per epoch plus the HEAD probes that find the free slot, as `NodeLogTakeover::fenced` does), the header GET per epoch, and per named shard a descriptor GET and a head GET; per shard taken a lazy take's requests, exactly. 0 LIST, no PUT beyond the fence and the publish. A zone loss costs deaths times reapers, not deaths times nodes. The fence also fences a node that was only partitioned, so its other shards lose the epoch and it opens a new one: the same price the takeover and the janitor already put on an expired node, now paid by a reaper only. The janitor's collector reuses the reaper's fence through an adapter in `oss-node` (the janitor never depends on the writer), so a death is fenced once on a node, not twice.
- **Duplicate work.** A shard is taken by one reaper; the head's CAS refuses the other. Stale digests can make the two reapers' choices differ: the loser's checks and acquire are refused before any restore, so the waste is one descriptor read, one head read and one refused CAS. With no live writer there is no reaper and nothing happens; the lazy path remains.
- **Memory.** The pass reserves from the pool for the headers it reads and the set `named()` builds from a hard cap, `max_header_bytes` (8 MiB, a constant): the header's length is known from its prefix (`header_end`) before the body is read, so a header over the cap is refused and the shards left to the lazy path, and one under it reserves its length first; a header that cannot reserve defers the pass. A take restores a shard into memory today. The pass bounds concurrency and reserves before it allocates; a take that cannot reserve is deferred, not failed.
- **Fencing and durability.** Unchanged: the head's CAS, the log's conditional creates and the register's term fence decide ownership; no lock, lease or leader is added.
- **Availability and latency.** Writes to a shard whose owner died fail or stall until it is taken. Lazy: the first write pays revoke, acquire, restore and replay. Proactive: the take starts at the first refresh that sees the lease expired (up to one lease lifetime after the crash, then one refresh interval; early revoke by a refused transport connection, [ADR 0016](0016-native-transport-and-early-revoke.md), shortens the first part), and the first write finds the shard held. The crash stall stays what ADR 0015 states; this changes who pays the take, not when the death is detected.

## Consequences

- A dead node's log is freed after its hot shards are published rather than when each is written again; the recurring dead-lease read ends.
- The pass is a new consumer of the membership refresh, of `NodeLogTakeover::named` and of the writer's take. It touches `oss-node` (wiring), so it follows the R7.6 node assembly, and adds a setting and a budget row.
- A fleet that loses many nodes at once (a zone) has every winner take its share at once, bounded per node by `max_concurrent` and the pool.
- A shard taken by a reaper is not necessarily the shard's placement writer; the next write is routed by placement and must reach the holder or hand it off at a bounded cost, which AC-18 holds before the switch can flip. A shard whose head names a third dead node is left to that node's own pass or a lazy take.
- Rules out: any per-shard claims or per-node summary object; a timer that enumerates indices to find shards to take.
