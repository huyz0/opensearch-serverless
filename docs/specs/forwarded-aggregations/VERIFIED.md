Recorded on 2026-11-27 against the 3.10.0 jars from Maven Central: `AggRecordings.java` wrote `java-aggs-3.10.0.txt`, and the bytes written for slices 1 and 2 from the source matched them at the first run, so no expectation changed. The recorded shard results carry null metadata, as a shard's do; the `stats` code was written before its test and the test was not seen to fail first.

Cardinality slice: `CardRecordings.java` wrote `java-cardinality-3.10.0.txt` (builders with and without `precision_threshold`; answers for no sketch, four hashes at precision 14, and 100 hashes at precision 4). Linear-counting hashes are written in table-slot order, which `Hll::to_bytes` matches; the tests were written after the code and not seen red first.

Percentiles slice: `PctRecordings.java` wrote `java-percentiles-3.10.0.txt` (builders with the defaults, with keys and a compression, and for ranks; answers over ten values, five hundred, none, and ranks). The Rust digest of the values 1 to 10 and an empty one write the same bytes as Java's; the 500-value digest is recorded only for the wire around it, since Java's random values are not reproduced here. The tests were written after the code and not seen red first.

Terms slice: `TermsRecordings.java` wrote `java-terms-3.10.0.txt` (builders with the defaults and with options; answers as `StringTerms` and `LongTerms`, with and without a sub-aggregation, and with no buckets). The recordings with a sub-aggregation back the sub-aggregation slice. A shard-level `shard_min_doc_count` with an order other than count descending is refused by the reader's parser, so that request fails as a bad request. The tests were written after the code and not seen red first.

Sub-aggregation slice: the recordings above (`request.terms_subs`, `response.string_terms_subs`, `response.long_terms_subs`) matched the Rust bytes at the first run. A terms nested in a terms is read and written by the same code, but no recording of one exists yet, so its answer is not Java-verified. Tests written after the code and not seen red first.

Date histogram slice: `DateHistoRecordings.java` wrote `java-date-histogram-3.10.0.txt` (builders with a calendar and a fixed interval, with an offset and a descending order, with a sub-aggregation; answers with a day and a 30-second rounding, with and without sub-aggregations, with a minimum count of 1, and an empty histogram for each of the eight calendar units). The Rust bytes matched at the first run. The node tests were written after the code and not seen red first.
