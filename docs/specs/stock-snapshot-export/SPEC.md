# Export to a stock OpenSearch snapshot repository

## Serves

Parity plan R14.8, [ADR 0062](../../adr/0062-a-snapshot-is-exported-to-a-stock-repository-by-copying.md): `PUT /_snapshot/{repo}/{name}` where `{repo}` is registered with `format: "stock"`, not `readonly`, over an `fs` or `s3` target takes a copying snapshot of the named indices that a stock OpenSearch 3.10 node restores. The restore half is [stock-snapshot-restore](../stock-snapshot-restore/SPEC.md).

## Acceptance criteria

- AC-1: A SMILE encoder in `oss-format` writes the JSON subset the stock blobs use (objects, arrays, strings, integers, longs, booleans, null, doubles, shared keys, binary), with the decoder's bounds (depth 64, 1,024 shared keys, 64 MiB of output). Every document it writes decodes, with the existing decoder, to the JSON it was given, and Jackson's own Smile reader (a Java check over the same bytes, `fixtures/snapshots/stock-smile/`) reads it to the same tree. Tests: round trip at every value type, at each bound and one past it; the Java check by hand.
- AC-2: The Lucene header and footer writer produces a blob the envelope reader accepts (codec name, version 1, SMILE body, footer CRC), and `CodecUtil.checksumEntireFile` and `retrieveChecksum` accept (Java check over the same bytes). Tests: the reader over writer output at every body length, and the Java check.
- AC-3: The `RepositoryData` writer produces an `index-N` the existing reader parses to the same snapshots and indices, and that the server's own `RepositoryData.snapshotsFromXContent` parses (Java check); the next generation extends the previous with the new snapshot, keeps every earlier snapshot and index id, and a repository with neither `index.latest` nor `index-N` starts at generation 0. Tests: extend the recorded repository's `index-0` and read it back; the Java check.
- AC-4: (`written_by` of each file is the Lucene version its `.si`, or `segments_N`, records, and is part of the comparison.) The shard snapshot, snapshot info, index metadata and global metadata writers produce blobs the existing readers decode to the source index's mapping, settings (with `index.number_of_shards`, `index.number_of_replicas` 0 and a uuid and creation date, which stock requires) and files. The shard snapshot's file list equals the recorded one by name, length and checksum (not by blob name: the export writes `.si` and `segments_N` as blobs, stock inlines them), `number_of_files` and `total_size` are the sums, and the checksum is the file's own footer CRC. The global metadata equals the recorded `meta-<uuid>.dat` (`cluster_uuid` `_na_`, the empty coordination and templates). Each `index-N` field of the recorded `index-0` (`index_metadata_lookup`, `index_metadata_identifiers`, `shard_generations`, snapshot `version`) is written and compared. Tests: each writer over the recorded index decodes equal to the recorded blob's decoding, named per blob; the Java check parses each with the server's own `*_FORMAT`.
- AC-5: The take copies each file of a shard's published commit as a whole-file blob, streaming through two buffers, with the Lucene footer CRC and length checked as the bytes pass; a file whose bytes do not match the manifest's length and its own footer CRC fails the take before any blob names it in `index-N`. The take writes no native snapshot register and no protective marker, so a crash pins nothing; a blob reclaimed mid-copy fails the take with 409 `snapshot_conflict` and nothing names its files. The index's incarnation is checked before the copy and before `index-N+1` (409 on a change). Tests: a taken index's repository holds each file's bytes exactly, every file as a blob; a planted truncated and a planted flipped file fail the take; a file deleted from the source store mid-copy fails it with 409 and leaves `index.latest` unchanged; after any failure the node's store holds no register or marker for the name; a changed incarnation is 409.
- AC-6: Order and fencing: shard files, shard snapshots, index metadata, snapshot info and global metadata are written before `index-N+1`; `index-N+1` is a conditional create and `index.latest` the last put. On a conflict the take adopts the existing `index-N+1` as its base and retries, at most 16 times, then 409; a retry rebuilds each shard generation from the adopted base's (keeping a concurrent take's entries) and reuses the blobs already copied. Two takes into one repository at once: both end in the repository, or one fails with 409, and every state restores. A take that dies after creating `index-N+1` and before the `index.latest` put leaves a repository the next take extends, not one it wedges on. A failure at every store call leaves a repository whose `index.latest` still names a restorable generation. Tests: a store that records the order; two concurrent takes; a fault at each call; the take after a fault at the `index.latest` put.
- AC-7: Refused 501 before any write: an index in a bucket or shared packs, `include_global_state`, `partial`, a file above the store's single-object limit, a delete of a stock snapshot, a mapping or settings stock cannot restore; 400 for a name over 128 bytes or outside `[A-Za-z0-9._-]`; 404 for an unknown index; a repository registered `readonly` is 400. Tests: one request each, each asserting no write reached the target.
- AC-8: A target outside the export allow-lists (`OSS_STOCK_EXPORT_FS_ROOTS`, `OSS_STOCK_EXPORT_S3_ROOTS`, empty by default) is refused 400 and nothing is written; an `fs` location reached by `..` or a symlink, and an `s3` target overlapping this deployment's own bucket and prefix, are refused. The target store answers every delete with an error (a test calls each method) and writes only under the repository prefix. Registering the repository as anyone but a cluster admin is 403. Tests as the restore's AC-7.
- AC-9: With `serverless.snapshots.stock.export.enabled` off (the default) the take answers 501 and makes no request to either store; with it on, the take passes, whether or not `serverless.snapshots.stock.enabled` is. The native take's rows are unchanged. A second take into the same repository, of the same index, keeps the first snapshot restorable (the new shard generation keeps its file entries) and reuses the index's id. Tests: both modes; the second take restored on the Rust node, both snapshots.
- AC-10: Requests: per shard one commit read, a ranged read for each buffer of each file, one put for each file, one put for its snapshot blob and one for its generation, and one read of the previous generation when the index is already in the repository; per index two describe reads and one put; per snapshot four puts and the two generation reads; no register or marker request; no LIST on `fs` and on the RustFS leg alike; requests scale with files and bytes and not with indices that are idle. Budget rows `snapshot.stock_export.requests` (one index, one shard, the recorded fixture's four files, each a blob) and `snapshot.stock_export_cleanup.requests` (a failed take), exact, recorded in `docs/request-budgets.md` when measured. A 429 when the pool cannot hold the buffers, writing nothing.
- AC-11: The repository the Rust node wrote restores on a stock 3.10 node and the restored index answers what the source answered. By hand: a stock node (`opensearch-min`) registers the exported directory read-only, restores, and returns the three searches of `fixtures/snapshots/stock/README.md`. Recorded in `VERIFIED.md` with the build and result; NOT-RUN until run.

## Test plan

AC-1 to AC-4: unit and round-trip tests in the format crate, plus a Java check beside `fixtures/snapshots/stock-smile/` for Jackson and the server's `*_FORMAT` classes. AC-5 to AC-10: server tests over an emulator store and an `fs` store, the recorded repository as the template, with a RustFS leg for AC-6 and AC-10 over `s3`. AC-11: the stock node, by hand.

## S3 request budget

See AC-10.

## Bounds

The restore's numbers (ADR 0062): 100 indices, 4,096 shards, 10,000 files a shard, 100,000 file entries, 128-byte names, 16 MiB blobs; two copy buffers reserved before the first read.

## Switch

`serverless.snapshots.stock.export.enabled`, default off: it copies the tenant's bytes out of the deployment.

## Risks

A stock layout detail the recorded repository does not show (found only by AC-11, which is why it is a gate); every snapshot copies all bytes, so a nightly export costs its whole size in requests and bytes; a crash leaves orphan blobs in the target (only a stock cleanup collects them) and nothing in the deployment; superseded `index-N` blobs accumulate; a merge that reclaims a blob mid-copy fails the take, so a heavily written index may need a retry.

## Build order

1. SMILE encoder (AC-1). 2. Header and footer writer, `RepositoryData` writer with every `index-N` field the recording holds (AC-2, AC-3). 3. The metadata and shard snapshot writers (AC-4). 4. The copy and the target store (AC-5, AC-8). 5. The take, fencing, route and switch (AC-6, AC-7, AC-9, AC-10). 6. The stock-node proof (AC-11). Each step updates `docs/compatibility.md` and the budget rows it spends.
