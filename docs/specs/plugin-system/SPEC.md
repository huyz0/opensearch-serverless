# Plugin system: native, WASM and gRPC tiers

## Serves

[ADR 0080](../../adr/0080-one-plugin-system-three-tiers.md), the owner's request of 2026-11-28 for plugins in the manner of Envoy and Chrome. Builds on [extension-abi](../extension-abi/SPEC.md) and [extension-analyzer](../extension-analyzer/SPEC.md); changes none of their behaviour.

## Change

Eight slices, one PR each. The plugin system has no master switch: the deployer's policy (`OSS_PLUGINS`) is the opt-in, an empty or absent policy loads nothing, and the native library loader sits behind the Cargo feature `plugins-native`, with `serverless.plugins.native.enabled` as an opt-out that defaults on. Slices 1 and 2 add no tier a deployer can reach; the first plugin that runs is slice 2's linked-in one.

1. **Contract** (`oss-ext`, no runtime): the manifest and its strict parser (the descriptor parser grown by the `plugin`, `routes`, `events`, `capabilities`, `budget` sections), the point catalogue as data (name, version, determinism class, ceilings, allowed tiers), the capability and budget types, the plugin API version (`1.0`) and its accept rule, the circuit breaker with an injected clock, and (added with the dynamic native tier) the C ABI as `#[repr(C)]` types and symbol names, with a golden layout test and the version rule both ways. The `rest` and `lifecycle` codecs and their golden vectors move to slice 2, where the first caller is.
2. **Registry, the linked-in native form, REST routes, lifecycle** (`oss-node` `plugins/`, `plugins/` for third-party native crates): the `NativeInstance` trait, the policy reader (`OSS_PLUGINS`), registration with collision and claim rules, route mounting with the action-table row, dispatch with `catch_unwind`, the breaker and bulkhead on every call, lifecycle delivery from a bounded queue, the status route, counters, the setting. A reference plugin `plugins/echo` used by the tests, linked in here and built as a library in slice 5.
3. **WASM plugins:** the `rest` and `lifecycle` points on ADR 0052's host (an effectful point is allowed host imports, linked only when granted; a pure point still refuses any import), deadline accounting across host imports, the module's manifest, the load-time grant check.
4. **State, search and egress capabilities** for native and WASM: the `state` host API over document sets, the call budget and its 429, the `search` and `egress` imports with alerting's egress rules, tenant attribution of every request, rows in [request-budgets](../../request-budgets.md).
5. **Dynamic native libraries** (`oss-ext-native`, `oss-plugin-sdk`, feature `plugins-native`): the loader, the SHA-256 allow-list and Ed25519 signature check, the verified private copy, the manifest-against-policy check, the `OssHost` table with granted capabilities and `denied` stubs, the host allocator and the unmetered refusal, the watchdog with `stuck_action`, the crash-loop guard, the no-replace rule, and the SDK with the panic wrapper. `plugins/echo` is built as a `cdylib` and loaded by the tests.
6. **gRPC tier** (`oss-ext-grpc`, feature `plugins-grpc`): the client, the `Describe` and `Call` messages, unix socket and mutual TLS, deadline, message bound reserved before read, connection reuse, breaker, `serverless.plugins.grpc.enabled` (opt-out, default on). A test server in Rust in `testkit` stands in for a plugin.
7. **Conformance, hostile soak, measurement, docs:** one suite run against every form of the tiers (the same plugin behaviour linked in, as a library, as WASM and as a gRPC service), hostile plugins per tier, the idle-zero and empty-registry measurements, `compatibility.md` (the status route, plugin routes, and that `_cat/plugins` does not list these plugins), the update of [add-an-extension-point](../../how-to/add-an-extension-point.md), the flip decision recorded.
8. **First adopter:** learning to rank's routes and rescore register through the system with its existing tests unchanged (the reference port other ports follow). Optional for the others; none is scheduled.

Not here: a `SIGHUP` that adds a plugin id (a later slice, after the route table is swappable), unloading or replacing a loaded library (refused by design), a Windows loader, signing WASM modules, the capabilities the ported plugins would need to become libraries (`schedule`, `index_admin`, `rescore`; each its own spec), the other points (`ingest`, `query`, `pipeline_agg`, `script`, collecting `agg`), each wired by its own spec; a `schedule` capability; dynamic enablement; supervising out-of-process plugins; any edit to the in-progress native ports.

File ownership: new files under `crates/ext`, `crates/ext-wasm`, `crates/ext-grpc`, `crates/node/src/plugins/`, `plugins/`, `docs/specs/plugin-system/`, plus an assembly hook in `crates/node` and the generated tables. Nothing in the files of index state management, alerting, anomaly detection or ML Commons.

## Acceptance criteria

- AC-1: the manifest is parsed by one strict parser whatever the tier delivers it: unknown, duplicate and mistyped keys are refused naming the key, depth, size and every length are bounded before allocation, a plugin id outside `[a-z][a-z0-9_-]{1,40}` is refused, and the same bytes give the same answer from a WASM descriptor, a `Describe` answer and a native `manifest()`.
- AC-2: the plugin API version rule is the ABI's: the same major and a minor at most the host's is accepted, another major or a newer minor is refused before anything else is called; golden fixtures built against `1.0` (a recorded WASM module and a recorded gRPC transcript) are accepted, and a change that breaks one fails a test.
- AC-3: the point catalogue is data and is enforced at load: each (point, tier) pair the catalogue forbids (`analyzer` on `grpc`, `script` on `grpc`, collecting `agg` on `wasm` or `grpc`) is refused naming both, and each pair it allows loads. A `pure` point with any host import or any capability is refused.
- AC-4: capabilities are granted by the node: a manifest asking for a capability the policy does not grant is refused at load and the plugin is `refused` in the status route; a granted capability the manifest did not ask for is not linked; a WASM module importing a host function it was not granted fails to load, not at call time; `grpc` plugins get no host capability and a manifest asking for one is refused.
- AC-5: routes: a plugin route is served with the method, path parameters, query, selected headers and body the `rest` codec carries, and answers with the plugin's status, headers and body within the point's ceilings. A plugin cannot mount a path outside `/_plugins/<id>/` without a `claim` in the policy; a route that collides with a built-in route is refused at load naming both; precedence is built-in, then plugin, then the proxy prefixes of ADR 0046. Authorization, `Authorization` and cookie headers are never passed, and `identity` passes the user name and roles only when granted.
- AC-6: a plugin route needs `all_access` unless the policy maps it to an action, and the action-table completeness test covers every mounted route (`crates/node/tests/server/security_authz.rs`).
- AC-7: native failures are one call, and no profile in any `Cargo.toml` sets `panic = "abort"` (a predicate in `scripts/check-layering.py` with a planted violation): a plugin, linked in or loaded, whose handler panics (through the SDK wrapper) answers 500 `plugin_failed`, the node keeps serving the next request on the same worker, the counter and the status route show it, and no node lock is held across a plugin call, asserted by running the next request after a panic inside a call made while the dispatch edge's own state is in use.
- AC-8: WASM failures are one call: modules that spin, grow memory, trap, recurse, return an oversized or malformed output, or call a host import past its budget each answer their typed status ([ADR 0080](../../adr/0080-one-plugin-system-three-tiers.md) failure table) and the next call is served, on the `rest` point as ADR 0052's hostile tests are on the test point.
- AC-9: gRPC failures are one call: against a test server that answers, is slow, hangs, drops the connection, answers a malformed message, answers more than the ceiling, answers a plugin 4xx and is absent, the host answers 200, 504, 504, 503, 502, 502, 400 and 503, never waits past the call's deadline, never holds a response buffer it did not reserve first, and the node keeps serving.
- AC-10: the circuit breaker is exactly the ADR's state machine under an injected clock: closed to open at 5 consecutive counted failures, or at half of the last 20 once 10 are seen; open for 30 s with 20% jitter; half-open admits one probe at a time; a probe's success closes it and its failure reopens it with the time doubled to 5 minutes. A 4xx and a 429 never count. While open a call makes **no call to the plugin and no store request**, and the answer is 503 at once.
- AC-11: the bulkhead holds: at most 8 calls to a plugin at once and 2 for one tenant, the ninth and the third answer 429 immediately and nothing queues, for each tier.
- AC-12: **an idle plugin makes no request** (and the gRPC runtime starts at the first connect, spawns no timer, has h2 keepalive off, and a connection dropped while idle is reopened only by the next call, not by the host): with a native, a WASM and a gRPC plugin loaded and an hour of mocked time with no call, the request meter reads exactly the startup reads (1 GET a WASM module per node) and nothing else, and the gRPC test server sees one `Describe` and no other call; no timer or health poll is started for any plugin.
- AC-13: **state costs what the table says**: `get` cold is 2 GET at depth 2, warm 0; `put` is at most 1 GET and 2 PUT; `delete` 1 GET and 1 PUT; a lost swap adds one more attempt up to 3 then 409; the meter shows no LIST for any of them; every request is attributed to the calling tenant and the plugin id. Each count is a row in [request-budgets](../../request-budgets.md) that the test pins.
- AC-14: **a call has a budget**, in the units of requests the tests count (a `searches` unit is one search whatever its requests), and a put loop past `state_ops_per_second` is 429: with a manifest budget of 2 state operations, the third in one call is 429 `plugin_budget_exceeded` and costs no request; the default budget is zero of each; the policy's ceiling lowers a manifest's budget; a `search` or `egress` over its budget is refused the same way.
- AC-15: isolation of state: a key outside the plugin's set cannot be named (`..`, a separator, an overlong key, another plugin's id are refused), a call for tenant A never reads or writes tenant B's set, and a plugin that is not granted `state.*` has no state API at all.
- AC-16: memory: a plugin route's request body is reserved from the `Extensions` pool before it is read and its response ceiling before the call, so a body larger than `max_request_bytes` is a 413 before anything is read and an exhausted pool is a 429; the peak reservation of each tier equals the literal sum the ADR states in section 7 (native `body + response ceiling + the plugin's declared memory_bytes`, wasm ADR 0052's formula plus body and response, grpc `body + response ceiling + 64 KiB window and frame pair per connection`) and is held to it by a test; a native plugin's host allocation refusal is the memory-limit status; with the pool at 0 no WASM or gRPC plugin loads and the start log says so.
- AC-17: lifecycle events are delivered to a plugin in the order they happened, from a bounded queue of 256 with drop-newest and a counter; a plugin that blocks forever delays no index create, delete or node start (the operation completes within its normal time with the plugin stuck); an event is delivered with no request to the store.
- AC-18: the status route answers from memory with id, tier, version, state, counters and last failure, makes no store request, and requires `all_access`; the counters are in `/_prometheus/metrics`.
- AC-19: no policy, no cost (the numbers are provisional, measured on RustFS): with no `OSS_PLUGINS` policy, or an empty one, nothing loads and the only route added is the status route, answered from memory; every existing test (proxy prefixes, ported routes, the analyzer pin and its switch) passes unchanged, search and write latency and the request counts of the budget tests are unchanged (within the bar of the build rule: write p99 within 5%, no extra requests, no search regression), and a policy that does not parse is refused whole with the node not starting.
- AC-20: the layering and `unsafe` predicates: `unsafe` for loading appears only in `oss-ext-native`, each block with a local allow and a `// SAFETY:` comment (`scripts/check-unsafe.py`, with a planted violation in `scripts/selftest-checks.py`); a crate under `plugins/` depends on `oss-plugin-sdk` and nothing else in the workspace; only `oss-node` depends on `oss-ext-grpc` and `oss-ext-native`; and a build without `plugins-native` has neither `oss-ext-native` nor `libloading` in its dependency tree (`cargo tree`).
- AC-21: conformance: one suite whose plugin is written linked in, as a library, as a WASM module and as a gRPC service gives the same answers for the same requests for `rest` and `lifecycle`, including every status in the failure table, on every form.
- AC-22: the first adopter: learning to rank's routes and rescore, registered through the system, pass their existing tests unchanged and make the same store requests as before (`docs/specs/ltr`).
- AC-23: egress is safe: a target resolving to a private, loopback or link-local address, a redirect, a DNS answer that changes between resolve and connect, a body over 1 MiB and an unverified certificate are each refused, with a planted target for each.
- AC-24: state is bounded: a put past 1,000 keys or 4 MiB for one (plugin, tenant) is 413, content orphaned by a lost swap is at most one blob per lost swap, and the named collector removes it.
- AC-25: a tenant cannot open a breaker for others: one tenant's calls that trap open that tenant's breaker only, another tenant is served; connection refused opens the plugin's.
- AC-26: the C ABI is versioned both ways: a library whose `oss_plugin_abi` is another major or a newer minor is refused before its manifest is read; a library built for a larger `OssHost` than the node's is refused at `init`; an older library on a newer node sees only the fields it knows; the layout of every `#[repr(C)]` type is held by a golden test (size, alignment and field offsets), and a recorded library built against `1.0`, one fixture per supported target (`.so` per architecture, `.dylib`), loads on every later node.
- AC-27: trust: a library whose SHA-256 is not in the allow-list and whose signature does not verify against a trusted key is not loaded and its bytes are never executed; one whose hash is listed loads; a signature by an untrusted key, a malformed signature and a signature over other bytes are each refused; the node loads the verified private copy (a test replaces the original after verification and sees the copy run), the copy's directory is mode 0700 and the file 0500; and the manifest's id and version must equal the policy entry; the signed message is `sha256(library) || id || version` (a signature over another version is refused) and `min_version` refuses an older signed build; on Linux the verified bytes load from a sealed memory file, elsewhere from a copy created 0700 and set to 0500 whose hash is checked at each load.
- AC-28: no unload and no replace: a loaded library is never closed, a policy whose hash or version for a loaded id changed is refused with the change applied only at the next start, removing an id holds its breaker open and drains its bulkhead, and a test counts that the library stays mapped.
- AC-29: a hung native call is contained: a plugin that never returns is marked `stuck` by the watchdog after its deadline, further calls answer 503 at once, the node keeps serving every other route, `quarantine` leaks and counts the thread and turns into `exit` after `max_stuck`, and `exit` drains and ends the process with its distinct status; with no native call in flight the watchdog thread does not run.
- AC-30: the crash-loop guard: a process killed (SIGKILL, in a test) with a native plugin active leaves the marker, a start that finds it twice in a row for the same plugin and hash refuses that plugin as `crashed twice` and serves without it, a changed policy entry clears it, a clean shutdown removes it, and none of it makes a store request.
- AC-31: native memory: a plugin whose manifest says `allocator: host` has its allocations charged to the `Extensions` pool and an allocation past the pool fails into the memory-limit status; a plugin that declares `host` and shows zero `host_allocs` after its first calls is flagged unmetered like one that declares nothing, and an unmetered plugin is refused unless the policy names `allow_unmetered`; the status route shows `host_allocs` and the flag; the declared `memory_bytes` is reserved at load; the spec states that this metering is cooperative.
- AC-32: the native opt-out: with `serverless.plugins.native.enabled` set false no library file is read, and a policy naming a library is logged and ignored; unset, it is on.
- AC-33: the native ABI at the boundary: an `OssBuf` returned with `len` above `cap` is `plugin_malformed`; a manifest without `threading` or declaring `panic: abort` is refused; a `serial` plugin never has two calls at once while a `concurrent` one may have eight; the table never returns host memory (`state_get` fills the plugin's buffer and reports the length needed); a host panic in a table function does not unwind into the plugin (a test panics in a stub).
- AC-34: a plugin's call that enters a plugin route or point (through `search`) is 400 `plugin_recursion`, at depth 1, and costs no further request.

## S3 request budget

Per operation, worst case; the numbers are the ADR's table and each is a row in [request-budgets](../../request-budgets.md) with its enforcing test.

| Operation | PUT-class | GET-class | LIST | Sequential depth |
|---|---|---|---|---|
| Idle plugin, any tier | 0 | 0 | 0 | 0 |
| Load a native plugin, load a gRPC plugin | 0 | 0 | 0 | 0 (one `Describe` call to the process) |
| Load a WASM plugin | 0 | 1 per node per module, none per call | 0 | 1 |
| A `rest` call with a zero budget | 0 | 0 | 0 | 0 |
| `state.get` of a missing / a present key | 0 | 1 / 2 | 0 | 1 / 2 |
| `state.put` | 0 | 3 | 0 | 3 |
| `state.delete` | 0 | 3 | 0 | 3 |
| A lifecycle event, the status route, an open breaker | 0 | 0 | 0 | 0 |
| `search` capability | as the search | as the search | 0 | as the search |
| `egress` capability | 0 | 0 | 0 | 0 (an HTTP call, not a store request) |

No request scales with documents, indexes, plugins loaded or elapsed time. A call's requests are at most its budget, which is declared, capped and counted.

## Switch

There is no `serverless.plugins.enabled`: with no downside to hide behind a switch, the policy is the opt-in. `serverless.plugins.native.enabled` and `serverless.plugins.grpc.enabled` stay only as opt-outs, each default true (owner's decision: plugins are on by default). A deployer who does not want foreign code in the node's process, or outbound plugin connections, sets one false; the policy still has to name the plugin before anything loads.

## Risks

- **A loaded library is the node's own fault domain, and loading it is `unsafe` that no guarantee covers.** The allow-list or signature, the verified private copy, the watchdog and the crash-loop guard limit what a fault costs and who can introduce one; a segfault still ends the process. The exception to ADR 0009 is the owner's to accept, and a second independent review of the amended ADR is open.
- **Three transports can drift.** AC-21's suite and the golden fixtures are the answer; if one tier needs a rule the others lack, the point's spec says so.
- **A synchronous host import inside a WASM call blocks the caller's thread for a store read.** The deadline covers it and the call budget bounds the count; measured in slice 7 before any default moves.
- **gRPC adds an outbound connection surface.** Off by default, endpoints named by the deployer in the policy, no redirects, no discovery; TLS verification is not optional for TCP.
- **The policy file must match across nodes.** A node with a different policy answers differently; the status route makes it visible, and a mixed policy is a deployment error this does not detect (the same as ADR 0052's node switch).
- **ADR number.** 0080 leaves room for the numbers other threads have taken; renumber before merge if one is taken.

## Host API 1.0

A plugin that holds a capability asks the host through one call, `Host::call(op, bytes) -> bytes` (`oss_ext::host`), whose operation names are versioned data, so a new operation is an additive change. The node supplies a `Backend`; `CallHost` stands between them and judges every operation the same way for every tier (AC-4, AC-14): the operation's capability must be granted (else 403), the call's budget for that kind must not be spent (else 429; a `state.*` op spends `state_ops`, `search` and `job.submit` spend `searches`, `egress` spends `egress`, the rest spend nothing), and the answer must fit the ceiling the plugin gave (else 413). A refused operation never reaches the backend. With no backend an operation is 503.

| Operation | Needs | Spends |
|---|---|---|
| `state.get` | `state.read` | state op |
| `state.put`, `state.delete` | `state.write` | state op |
| `search` | `search` | search |
| `job.submit` | `job` | search |
| `job.get`, `job.delete`, `job.stats` | `job` | none |
| `index.docs` | `index.write` | index op |
| `egress` | `egress:<host>` (the backend checks the host) | egress |

State is a document set under `plugins/<id>/<sha256 of the tenant>/state/` (`_node` for a call with no tenant), served by `StateBackend`. As built: a key is a document name of at most 128 bytes, a value at most 256 KiB, a set at most 1000 keys (413 past it); `state.put` takes `if_absent` (the answer is `[1]` written, `[0]` the key was there) and has no per-key version; there is no 4 MiB total per plugin and tenant, no `state_ops_per_second` limit and no warm cache yet. Working buffers are charged to the request-bodies pool, so a node with no extensions memory still serves state.
| `identity` | `identity` | none |
| `log`, `metrics` | `log`, `metrics` | none |

A native plugin reaches it by overriding `NativeInstance::call_host`; a plugin that asks for nothing implements `call` only. The backend's operations are bytes in and bytes out, and a port that wants one (asynchronous search's submit, get, delete and stats) implements the `job.*` operations behind `Backend` and keeps its own module a function of bytes.

`job.*` run a search as a job on a thread of the node's, never code of the plugin's: `job.submit` takes an index expression (at most 1,024 bytes) and a search body (at most 1 MiB) and answers the job's id; `job.get` takes the id and a wait in milliseconds (at most 10,000) and answers the state (running, succeeded, failed) with the result or the error body (at most 4 MiB, else 413); `job.delete` cancels a running job and forgets a finished one; `job.stats` answers this node's `running`, `submitted`, `cancelled` and `rejected`. A job belongs to the plugin that started it, in the tenant of the call: another plugin or tenant reading it gets 400, as for an id that does not exist. A job is kept until the plugin deletes it or its keep-alive passes, its result is reserved from the `Extensions` pool (so a node with that pool at 0% refuses every submit with 429) and a search that stops between shards when the job is cancelled or times out. `JobSink` is the node's side and `JobBackend` serves the operations from it ([ADR 0084](../../adr/0084-asynchronous-search-is-a-native-plugin-over-node-local-jobs.md)).

`index.docs` indexes up to 1,000 documents (each at most 1 MiB, 8 MiB in all) into one named index through the service `_bulk` uses, so a plugin's writes take the writer path, the bulk budget and the same refusals; a document that fails fails alone with its `_bulk` status, a source that is not a JSON object refuses the call (400). `DocSink::index(index, docs)` is the node's side, `DocSinkBackend` serves the operation from it, and the manifest's `budget.index_ops` bounds the calls of one invocation.
