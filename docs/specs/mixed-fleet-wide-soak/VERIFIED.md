# Verified

RustFS 1.0.6 on localhost (the vendor's prebuilt zip, SHA-256 `a4d109a0…1398f`), the Java shell at e71d4233, lease TTL 4 s, 2 Java and 2 Rust nodes, a four-shard index, four writers, a 6 s window, a 4-core container. Provisional.

Run: `OSS_SOAK_CYCLES=6 OSS_SOAK_WINDOW_SECONDS=6 RUSTFS_BIN=<rustfs> OSS_JAVA_BIN=$(which java) OSS_JAVA_CP=<classpath> cargo test -p oss-node --features reader,writer,coordinator --test mixed_fleet several_live -- --ignored --nocapture`.

- AC-1: `several_live_nodes_take_concurrent_writes_while_one_is_killed_each_cycle` in crates/node/tests/mixed_fleet/soak_wide.rs. **It fails**, in four runs out of four, after a Rust node is killed (cycle 2, the first Rust kill; cycle 1 killed a Java node and every node found everything): the Java nodes find about 74% of the acknowledged documents (747 of 1,020, 1,069 of 1,440, 1,252 of 1,700), always the documents of one shard (the same ids missing run after run), for the whole 60 s the judge waits. The Rust nodes find all of them. After the test writes to every shard, so that a node takes each one over, the same Java node finds every document. So the acknowledged writes of a Rust owner that was killed are visible to the Rust nodes (they read its node log) but not to a Java node that only reads, until a node takes the shard over by a write.
- AC-2: `several_live_nodes_take_concurrent_writes_while_one_is_killed_each_cycle` again: every bulk was acknowledged within the bound in the cycles that ran, the slowest of a cycle 4.5 to 11.4 s.
- AC-3: `several_live_nodes_take_concurrent_writes_while_one_is_killed_each_cycle` again: bulks sent first to a Java node were acknowledged first time 12 of 16 (and 38 of 43, 30 of 33 in other runs); bulks sent first to a Rust node 0 of 7 (8 of 16, 8 of 15 in other runs): a Rust node acknowledged few writes itself, so most of a Rust-aimed writer's acknowledgements came on a retry through another node. Why is not established here: the run does not record the reply of a refused write, so it cannot tell a refusal for a shard a Java node holds from any other failed try.

**After the not-owner fix (docs/specs/proactive-takeover AC-23), 1 run, 20 s window (provisional, RustFS 1.0.6 and the Java shell):** first-try acks for bulks sent first to a Rust node rose to 29 of 33 (Java 77 of 86), retries 21 against 52 before. The soak still fails in cycle 2, the first Rust kill: Java readers miss acknowledged documents (found 1,123 and 3,304 of 4,360). What the runs show (2 runs with logging, not kept in the tree): a Rust reaper takes the killed owner's shard 4 to 6 s after the kill and publishes it within 2 s after that, and the Rust nodes keep publishing it as writes arrive. Yet a Java reader answers 200 with `_shards.failed: 1`, `complete: false` and the reason `shard_behind_log_exception` ("this copy of shard 3 of mixed may not hold a write its writer answered as refreshed -- retry") for that shard for the whole judging time, so the documents are not lost: that Java reader's own check (`ReaderValidation.validateReader`, which refuses a reader behind a node log when it does not find the shard's owner live) never clears. The ledger judge counts such a partial answer as missing. Why the check does not find the Rust owner live, or why it finds the log ahead of the commit, is not yet known.

Not covered: the Rust nodes' own view after a Java owner is killed beyond cycle 1 (it passed there), a kill of a node that holds no shard, a run past the first Rust kill (the run stops at the first failure), and whether a Java-only fleet shows the same after a Java owner is killed (the Java side is not changed here).
