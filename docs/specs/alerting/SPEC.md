# Alerting, native: monitors, triggers, destinations, alerts

## Serves

R15.4's alerting, under [ADR 0075](../../adr/0075-alerting-is-ported-natively.md), which supersedes [ADR 0046](../../adr/0046-plugin-requests-are-proxied-to-java-nodes.md) for alerting. The owner's decision (2026-11-28): the stock plugins are ported to Rust, not proxied. A client of the stock Alerting plugin (`opensearch-project/alerting`) must work unchanged against a Rust node.

## Change

Six slices, one PR each, none behind an enable switch (see "Switches").

1. **Store.** `oss-meta`: a tenant's monitors are one index register `alerting/<tenant>/monitors/_index` naming immutable body blobs `blob-<content>` beside it and carrying each monitor's enabled flag, schedule and update time (`oss_format::MonitorIndex`; the document-set marker cannot, so the runner would read every body); destinations and channels, and alerts, are document sets (a marker register naming immutable content blobs, the stored-scripts shape) under `alerting/<tenant>/channels/` and `.../alerts/`. Nothing lists. Bounds: a monitor 1 MiB, 1,000 monitors a tenant, 100 triggers a monitor, 100 actions a trigger.
2. **Monitor and destination routes** of the stock plugin, on `/_plugins/_alerting` and `/_opendistro/_alerting`: `POST|PUT|GET|DELETE /monitors[/{id}]`, `POST /monitors/_search`, `POST /monitors/{id}/_execute` (with `dryrun`), `POST /monitors/_execute`, `GET /monitors/alerts`, `POST /monitors/{id}/_acknowledge/alerts`, `GET /alerts`, `GET /destinations` and `/destinations/email_accounts|email_groups` (kept for the legacy shape), `GET /_stats`. Notification channels are the Notifications plugin's `/_plugins/_notifications/configs`; this slice takes channel ids as stored documents and serves the configs routes needed to create the webhook, Slack, Chime and custom-webhook kinds. SNS and email are refused 400 with a message saying so, not silently accepted. Monitor `_version`, `_seq_no` and `_primary_term` follow the set's change count; the plugin's optimistic `if_seq_no` and `if_primary_term` map onto the marker's version.
3. **Query-level monitors.** `monitor_type: query_level_monitor`: the `inputs[0].search` (indices, a query, aggregations) is run through the reader as a search with `size` as the monitor says, the trigger's `condition.script` is evaluated over `ctx` (`ctx.results[0]`, `ctx.monitor`, `ctx.trigger`, `ctx.periodStart`, `ctx.periodEnd`) by the reader's painless subset; a script outside that subset is refused 400 at put, not at run. `{{period_end}}` and `{{period_start}}` are rendered into the query with the Mustache renderer search templates use.
4. **Bucket-level monitors** (`bucket_level_monitor`, composite aggregation `after_key` paging, `buckets_path` and `parent_bucket_path` selectors) **and document-level monitors** (`doc_level_monitor`, queries over a document set). The document-level match uses [`lucene-monitor`](https://github.com/huyz0/lucene-rust/tree/main/crates/lucene-monitor) (the percolator already in lucene-rust: a presearcher narrows the registered queries before a batch is matched), not a per-document search. See "Reuse from lucene-rust" below.
5. **The runner.**
   - *Discovery without LIST:* a registry of 256 shard markers `alerting/registry/<0..255>` (hash of tenant), each naming the tenants with at least one enabled monitor (bounded 4,096 a shard; past it a put of a monitor is 429). A node reads the 256 markers every `serverless.alerting.refresh_ttl` (default 300 s) and the monitor marker of each tenant it places. This is the only standing cost and AC-8 counts it. The 256 x 4,096 bound (about 1.05 million tenants) is the intended ceiling of this design; more shards is a later format decision and ADR. *Registry writes:* an enabled put writes the monitor, then **always CASes its tenant's shard** (adding the entry if absent; if present, rewriting it unchanged so the shard's etag moves), and is acknowledged only after that CAS. A removal (a delete or disable that leaves the tenant no enabled monitor) reads the shard (etag E), **then** re-reads the tenant's monitor marker, and removes the entry by CAS against E only if no enabled monitor shows. The shard is a register, so an unchanged rewrite is a swap that moves its generation. The adder's shard read and swap come after its own monitor write has landed and never use the runner's cached shard. A monitor's marker inlines each monitor's id, enabled flag and schedule (about 100 bytes a monitor, 100 KB at 1,000 monitors, checked by a size test), so one GET answers both the removal's check and the runner. If the remover's swap lands first, an adder's swap fails or reads the entry absent and adds it. Proof: if an adder's shard CAS lands after the remover's shard read, the remover's CAS fails and it re-reads the marker; if it lands before, the adder's monitor write came before it and so before the remover's marker re-read, which then shows the monitor and keeps the entry. No crash of either side loses an acknowledged monitor: a crashed remover leaves a stale entry (one empty marker read a TTL), a crashed adder was never acknowledged and the client retries. Each CAS has at most 8 attempts with jitter, then 503. An add past the shard's 4,096 bound is 429 and the monitor just written is disabled by that put with a re-read swap that flips only its own flag, never restoring an earlier read of the marker. A node that reads an empty marker for a tenant it places runs the removal protocol, so stale entries do not accumulate; tenant ids are at most 64 bytes. Deterministic-hook interleaving tests cover an adder's write and shard CAS against a remover's shard read, marker re-read and CAS in every order, and a remover killed between any two steps; each fails against a protocol without the always-CAS, and a mutation dropping the CAS or the marker re-read fails one. A monitor created or deleted on another node is acted on within `refresh_ttl`; a deleted monitor may fire once more until then, stated and not hidden. A monitor enabled on another node is therefore first run within `refresh_ttl` plus one slot; this is stated, not hidden.
   - *Owners:* a **tenant's** monitors are placed on the top 2 nodes by the placement hash over the tenant id, so a node reads only the monitor markers of tenants it places; no other node tries a claim, which bounds failed claims to 1 a slot.
   - *Slots:* the next slot is derived from the schedule (`period` interval and unit, or `cron` with timezone; a cron slot skipped by a DST gap is skipped, one doubled by it runs once) and the clock. A node sleeps until the earliest slot; no poll. **Missed slots are never backfilled**: after an outage a monitor runs at its next slot only.
   - *Claim:* one marker register per monitor, `alerting/runs/<tenant>/<monitor>`, holding `last_claimed_slot`; a node claims slot S by compare-and-swap from a value below S to S. One PUT a run, no per-slot blob, nothing to reclaim, no LIST. A node runs a slot only once its clock is at or past the slot's end plus `serverless.alerting.max_skew` (default 5 s) plus `serverless.alerting.visibility_lag` (default 5 s, the time a written document takes to be searchable; refused at config if an index's refresh interval exceeds it), so no claim is early. The claim is an etag compare-and-swap: the claimer keeps the etag of its last claim and a loser (the second candidate) pays one failed PUT and a GET.
   - *Window:* a run's `periodStart` and `periodEnd` are the slot's boundaries, never `now()`, so a fast clock cannot read an incomplete window.
   - *Semantics:* **at most once per slot.** A node that wins the claim and dies before it finishes loses that slot; the next slot runs normally. This is deliberate (no lease, no retry timer), recorded in the monitor's run state and visible as an alert-less gap.
   - The run records its alert state, `last_update_time` and `enabled_time` as the plugin does, and starts no more than `serverless.alerting.max_concurrent_runs` (default 4) at once. Due slots are derived state (bounded by the monitors the node places), **claimed when a worker frees up, not when due**, so a tenant with 1,000 monitors on one minute boundary is worked off at the node's throughput; a slot is dropped and counted only once the next slot's end has passed unclaimed. A run holds at most `serverless.alerting.max_result_bytes` (default 4 MiB) of search results and `ctx`, reserved before held; an alert document is at most 256 KiB.
6. **Alerts and actions.** Alert states `ACTIVE`, `ACKNOWLEDGED`, `COMPLETED`, `ERROR`, `DELETED`; an alert is created when a trigger first fires, rises with `acknowledge`, completes when the condition clears; throttle windows and `action_execution_policy` (`per_alert`, `per_execution`). An action renders its `message_template` and posts to the channel's URL with a body bound of 1 MiB, a timeout of 10 s, no redirect and no private-address target unless `serverless.alerting.allow_private_targets` is set (a webhook is an SSRF vector). A failed action is recorded in the alert, not retried by a timer. The throttle's last-fired time is stored in the alert document, so another node claiming a later slot sees it; updating it is an alert PUT and is in the budget. The target host is resolved once, the resolved address checked, and the connect made to that address (no DNS rebinding).

## Reuse from lucene-rust

lucene-rust has `lucene-monitor` (the Lucene Monitor percolator: query registration, presearcher, batch matching; about 4,600 lines in `src/`), and nothing else alerting-shaped; a code search for "alerting" in that repository finds no hits. It is the matching engine of document-level monitors only. Monitors, triggers, scheduling, alerts and actions are the plugin's behaviour and are built here. Slice 4 depends on `lucene-monitor` at the same pinned revision as the other lucene crates; whether its query analyser covers the DSL queries a document-level monitor takes (`query_string` and `match` against a mapped field) is checked by a test first, and a query it cannot analyse falls back to matching by a plain query over an in-memory reader, with a batch of at most 1,000 documents and 100 fallback queries a run, past which the run is an `ERROR` alert.

Not here: SNS and email channels; painless beyond the reader's subset; cross-cluster monitors (`cluster_metrics` input beyond `_cluster/health`, `_cluster/stats`, `_nodes/stats` of this node); Java-shell interop; the plugin's `.opendistro-alerting-*` system indices (no index exists; `GET` of them is a 404).

## Acceptance criteria

- AC-1: a monitor is created, read, replaced, searched and deleted through the routes in the plugin's published shapes (`_id`, `_version`, `monitor` with `schedule`, `inputs`, `triggers`); a stale `if_seq_no` is 409; an invalid one is 400 `illegal_argument_exception`; a missing one 404.
- AC-2: put, read and delete are 1 GET and 2 PUTs, 2 GETs, 1 GET and 2 PUTs, no LIST, plus for an enabled put 1 GET and 1 PUT of the registry shard, and for a delete or disable that leaves no enabled monitor 1 GET of the shard, 1 GET of the marker and 1 PUT of the shard; these counts are uncontended: a removal that leaves other enabled monitors, and the delete of a disabled monitor, add 0 requests, the 429 path adds one PUT, and a retry adds its reads and PUT; each is a row in [request-budgets](../../request-budgets.md) that the count test pins; a search reads the marker and one GET per object of its page of at most 100.
- AC-3: a query-level monitor's `_execute` returns `input_results.results[0]` equal to the same search run directly, and `trigger_results` carrying the condition's boolean; `dryrun` stores nothing (asserted by the request meter).
- AC-4: a condition script outside the supported subset is 400 at put; a script that fails at run gives an `ERROR` alert with the message, never a panic.
- AC-5: a bucket-level monitor pages a composite aggregation to its end within a bound of 10,000 buckets and fires `trigger_results.agg_result_buckets` for the matching buckets only.
- AC-6: a document-level monitor matches each document of a batch against its queries and reports the matching query ids per document, equal to running each query alone, on a fixed fixture.
- AC-7: with a mocked clock, a monitor on `period: 1 MINUTES` runs once per slot across three nodes (only the tenant's top 2 by placement try the claim; one CAS wins a slot), a slot is never run twice, a node that dies after its claim loses that slot and the next slot runs on the surviving owner, missed slots after an outage are not backfilled, and with one node's clock 4 s fast the window of every run is the slot's boundaries while a fast clock never claims a slot before its end plus skew and lag; documents written inside the skew window are seen by exactly one window.
- AC-8: **no poll per monitor or per index**: with N enabled monitors and the clock advanced one hour with none due, the request meter reads exactly the registry reads (256 markers and the placed tenants' markers, each once per `refresh_ttl`) and nothing else, whatever N; with the clock advanced to a slot, the requests are those plus exactly the claim PUT (the second candidate adds one failed PUT and one GET), the monitor's search and its alert writes (a throttle-time update is one of them). A cluster with no monitors reads the 256 registry markers every `refresh_ttl` and nothing more.
- AC-9: an alert moves `ACTIVE` to `ACKNOWLEDGED` on acknowledge and to `COMPLETED` when the trigger clears, and is not re-created while active; a throttled action does not post twice inside its window.
- AC-10: an action posts the rendered message to a webhook with the bounds above; a redirect, a private address and a hostname that resolves to a private address (a test hostname resolving to loopback) are refused and recorded as `ERROR` in the alert; a slow target times out and the run completes.
- AC-11: memory is reserved before a monitor is held (4 x its bytes from the open-indexes pool) and before a run's search hits and a notification body are held; past the pool a run is skipped and counted, not failed with a 500.
- AC-12: a schedule interval below `serverless.alerting.min_interval` (default 60 s) is 400 at put; a tenant over its monitor count is 429; a monitor over 1 MiB, past 100 triggers or 100 actions a trigger is 400 (413 for bytes); a run past its result bytes is skipped and counted, never a 500, and with 1,000 monitors due in one slot the dropped share is set by throughput and not by a queue size (limit tests).
- AC-13: alerting has no enable setting: the routes and the runner are on from the day they land. With no monitor enabled, nothing runs and the only standing cost is the registry reads of the node's placed tenants (AC-8); a disabled monitor is stored and not run.

## S3 request budget

Management: the stored-scripts shape (a row in [request-budgets](../../request-budgets.md) per route when the routes land). Run: 1 conditional-create PUT to claim a slot, the monitor's search (the reader's cost, charged to the monitor's indices), and 1 to 2 PUTs for the alert document and its marker when state changes (an alert opening, closing, acknowledging, or a throttle time moving); a run whose trigger stays clear and that has no alert makes no write beyond the claim. Load: every node reads the 256 registry markers once per `refresh_ttl` (default 300 s), and the monitor marker of each tenant it owns a monitor of, so the standing bill is (256 + tenants placed on the node) / TTL a node, so the fleet pays 256 x nodes + 2 x tenants-with-monitors reads per TTL: it scales with nodes and tenants, not nodes times tenants, and never with indices, monitors in a tenant or searches; the registry's bytes read are about 16 MB a node a TTL at 1 million tenants, and the 4,096 shard cap assumes an even hash (a shard at 90% is a metric). This is a deliberate standing cost of a scheduler without a control plane; idle indices and monitor-less tenants add nothing to it. Depth: one round for the claim, then the search's own rounds; fan-out free. LIST: none.

The claim PUT per run is a bill that scales with monitors x runs, which is the feature's nature. Worst case per tenant: 1,000 monitors at the 60 s floor is 1.44 million claims and searches a day. The guards are the floor, the per-tenant count, a fleet-wide cap `serverless.alerting.max_total_monitors` (default 1,000,000, with the registry's shard bound as the hard limit), and the per-tenant request meter; the measurement for the default decides whether the per-tenant count is tight enough. AC-8 asserts nothing is paid between slots beyond the registry reads.

## Switch

There is no `serverless.alerting.enabled`: the plugin needs no switch to be on (owner's rule, 2026-11-28), so the store, the routes and the runner are on from the day each lands. The runner's standing cost (the registry reads, and a claim and a search per run) is paid only by tenants with an enabled monitor, and is bounded by the limits below. It is accepted on the evidence in VERIFIED.md before the first release: the stock recording of slice 2, the request counts of AC-2, AC-7 and AC-8, a run's search latency against the same search issued by a client, and the memory of 1,000 held monitors. `min_interval`, `max_monitors` (per tenant), `max_total_monitors`, `max_concurrent_runs`, `max_result_bytes`, `max_skew`, `visibility_lag` and `refresh_ttl` are limits with defaults, not switches; `allow_private_targets` is a security setting, default off, tested on only against a loopback target.

**End state.** Every alerting route is native and answers on the Rust node alone: no proxy fallback, no Java in the runtime path. The alerting prefixes leave the proxy list when the last route lands, not when the runner flips on. Java is used only in tests, for compatibility (the stock recording) and for performance and memory comparison against the Rust build; every behaviour also has a test that runs on the Rust node alone.

## Risks

- Reference behaviour is from the plugin's documentation, not its source (`opensearch-project/alerting` is outside this sandbox's repositories); shapes are provisional until a stock recording exists (AC-1 and AC-3 are marked `provisional` in VERIFIED.md until then).
- A scheduler without a leader depends on the claim create being atomic in every backend; the emulator and RustFS are checked by the conformance suite, the fs store by its single host.
- Clock skew: a claim is by slot number, the window is the slot's boundaries, and a node runs a slot only after its end plus `max_skew` plus `visibility_lag`, so skew costs a late or skipped run, never a double run or a read of an incomplete window. A slot a node was too late for is not backfilled. Membership disagreement lets at most the 2 placement candidates try, so the extra cost is one failed CAS a slot.
- A noisy tenant with many frequent monitors is a cost problem more than a correctness one: the interval floor, the monitor bound and the per-tenant meter are the guard, and the measurement for the default decides whether they are tight enough.
- `lucene-monitor`'s analyser may not cover every DSL query; the fallback is bounded but slower.
