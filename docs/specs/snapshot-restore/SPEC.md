# Snapshot restore, shallow

## Serves

[ADR 0045](../../adr/0045-shallow-snapshot-restore.md): `POST /_snapshot/{repo}/{name}/_restore` for a shallow snapshot a Rust or a Java node took, as the shell restores one.

## Acceptance criteria

- AC-1: A restore of a snapshot taken by Rust creates each captured index under its original name, or under `rename_pattern` and `rename_replacement`, with the captured mapping, settings and shard count, a new uuid, and each shard's files copied into the new index's first-term directory and its manifest landed; the restored index answers a search with what the snapshot captured. Test: a take, a restore and a search over the emulator.
- AC-2: The whole request is refused before any write when: the snapshot is missing (404 `snapshot_missing_exception`) or still being taken (409 `snapshot_in_progress`); a named index was not captured (404 `index_not_found`); two targets collide (400 `index_already_exists`); a target exists (400 `index_already_exists`); a system index is named, as a source or as a target (403 `system_index`; the names come from `serverless.system_indices.patterns`, none by default, as this node loads no plugin that would declare any); more than 100 indices or 4,096 shards (400 `snapshot_too_large`); a key the node does not serve is given (501), or an unknown one (400).
- AC-3: A failure after the first write (a store failing at each call, a manifest that cannot land because a writer published first, 409 `restore_conflict`) deletes every index this restore created and returns the first failure.
- AC-4: The copy streams through one bounded buffer: peak memory does not grow with the file's length. A request that cannot reserve the buffer is 429 and writes nothing.
- AC-5: Requests are one write a captured file and one ranged read for each buffer of its bytes (one for a file under the buffer), one manifest create a shard, one descriptor create and one swap that clears the restore mark an index, and the snapshot's read; no LIST, and the same for a 1 KB and a 100 MB file. A failed restore adds the index-delete service's requests for each index it created and no others. Budget rows `snapshot.restore_two.requests` and `snapshot.restore_cleanup.requests` (a restore that fails on its second shard, cleanup included), each spent by a gated test.
- AC-6: With any of the three switches off the restore answers 501 and makes no request; a snapshot that copied its data, or a record with a file of no recorded length, is refused 501 and written nothing.
- AC-7: A Java node reads an index a Rust node restored (recorded fixture and a Java-side test), and a Rust node restores a snapshot a Java node took (recorded fixture); the restore switch was held off until both passed.
- AC-9: A restore marks the index it creates with the setting `index.restore.in_progress` until every shard's manifest has landed, then writes the index's own settings back in one swap (a change that moved the register first is kept and the swap repeats from it). Until then a search answers 503 `cluster_block_exception` and a write finds no index, so a node that dies part-way leaves an index that refuses to answer, not one that answers from empty shards; a point in time, a snapshot take and an alias over it are refused (503, 503, 400), a delete clears it, and the restore of a snapshot whose index carries the mark is refused 501. The final swap leaves any index that is not the one this restore made, or no longer carries the mark, alone. A Java node knows the mark too (huyz0/OpenSearch #184): a search naming the index, by name or through an alias, is 503 `cluster_block_exception`, and a write finds no index (404 `index_not_found`), as on a Rust node; a get, a multi-get or a point in time on a Java node is not covered, and a Java writer may still open the marked index's shards in the background, though none takes a write while the mark is set. The cat, exists and health routes list a marked index as any other.
- AC-8: A record whose settings carry another index's identity (uuid, creation date, version, provided name, shard count, replicas) or a shard mode's unit layout is refused 501 before any write, so only settings a restored index may keep are applied; a record with a layout or split is refused 501 `unsupported_snapshot_layout` before any write; a search over a restored index with rollups never rules out a restored document; a failure inside the descriptor create still deletes the index.

## How it is held

AC-7 is held by `fixtures/snapshots/java-take/` (a record the shell's own classes wrote, restored by `a_snapshot_a_java_node_took_is_restored_by_a_rust_node`) and `fixtures/snapshots/rust-restore/` read by `CheckRestore.java` against the shell's classes (PASS, run by hand at `e71d4233`).

AC-1's search is held by `crates/node/tests/server/snapshot_restore_search.rs::a_restored_index_answers_a_search_with_what_the_snapshot_captured`: a real shard's three documents are published, taken and restored as `copy`, and a reader over the same store answers 3 for both indices.

AC-9 is held by `crates/meta/tests/descriptors/snapshot_restore.rs` (the mark is gone and the settings are the index's own after a restore; a restore that fails leaves it marked), `crates/meta/src/snapshot_restore.rs` (the unmarking against a moved register, and against a deleted index), `crates/node/tests/server/snapshot_restore_search.rs` (a marked descriptor is refused by the reader), `crates/node/src/descriptor_routes.rs` (and by the writer's routes) and `crates/format/src/restore_mark.rs`. AC-4's peak is measured by `crates/meta/tests/restore_peak.rs`: a counting allocator over a restore of a 48 MiB file through two buffers of 1 MiB. A Java node reading a marked descriptor is held by `fixtures/snapshots/rust-restore/descriptor-marked.bin` and `CheckRestore.java`: it reads and builds metadata from it without failing, and does not refuse the index.

## Out of scope

Standard snapshots, `include_global_state`, `partial`, `index_settings`, `ignore_index_settings`, `include_aliases`, and an asynchronous restore.
