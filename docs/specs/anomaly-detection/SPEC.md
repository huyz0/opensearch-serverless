# Anomaly detection, native: detectors, the Random Cut Forest model, scheduled runs, results

## Serves

R15.4's anomaly detection, under [ADR 0078](../../adr/0078-anomaly-detection-is-ported-natively.md), which supersedes [ADR 0046](../../adr/0046-plugin-requests-are-proxied-to-java-nodes.md) for anomaly detection. The owner's decision (2026-11-28): the stock plugins are ported to Rust, not proxied. A client of the stock Anomaly Detection plugin (`opensearch-project/anomaly-detection`, run live as 3.9.0.0 in [plugin-proxy](../plugin-proxy/VERIFIED.md)) must work unchanged against a Rust node.

## Change

Six slices, one PR each, each behind the setting below. Slices 1 to 3 need no scheduler. **Slice 4 is blocked until [alerting slice 5](../alerting/SPEC.md) has merged**; the extraction of its scheduler into `oss-meta::schedule` is then slice 4's first task, with its own criterion (AC-17).

1. **The model, `oss-anomaly` (a new leaf crate, pure compute, no dependencies).** A Random Cut Forest after Guha et al. (2016): `number_of_trees` (default 30) trees each over a reservoir sample of `sample_size` points (default 256, time-decayed sampling), a shared point store, anomaly score as the mean over trees of a score summing, over the nodes a point passes, the probability that a cut separates it there times `1/(depth + 1)`, plus the same for a leaf of equal points with a mass damping (scaled by `log2(sample_size + 1)`), over a ring of the last `4 x sample_size` points that every tree samples from independently (so a point's bytes are held once), a **thresholder** that turns the score into `anomaly_grade` in [0, 1] and `confidence` in [0, 1] from a running, discounted mean and deviation of past scores (the thresholded-RCF behaviour the stock plugin uses, whose constants are written in one module and checked by AC-2), **shingling** (`shingle_size` default 8, 1 to 60, a point is the last `shingle_size` feature vectors) and **imputation** of a missing window (`ZERO`, `FIXED_VALUES`, `PREVIOUS`, and the plugin's default for a gap). Seeded: the same seed and input give the same output. The model serialises to a versioned byte string (a checkpoint) and back, bit-exact. No `unsafe`, no allocation per scored point after construction (counting allocator), memory fixed at construction and reserved before it is held. Written from the paper and the library's documented behaviour: [lucene-rust](https://github.com/huyz0/lucene-rust) holds no anomaly code (a search of the repository finds only the names `FIT_RCF` and `BATCH_RCF` in a Java enum of ML Commons function names), and no Rust RCF crate exists on crates.io.
2. **Store and detector routes** of the stock plugin, on `/_plugins/_anomaly_detection` and `/_opendistro/_anomaly_detection`: `POST|PUT|GET|DELETE /detectors[/{id}]` (`if_seq_no` and `if_primary_term` map onto the marker's version; `GET` takes `job=true` and `task=true`; a delete of a running detector is 400), `GET|POST /detectors/_search`, `GET|POST /detectors/_count`; `GET /detectors/_match?name=`, `POST /detectors/_validate[/{type}]` and `GET /stats[/{stat}]` come with the runner slice, because a name match reads every detector and so wants an index of names. A `_search` serves `match_all`, `ids`, `bool` and queries on `_id`, sorted on `_id`; a query or sort on any other field is 400 saying it would read every detector. A detector is a document in a document set under `ad/<tenant>/detectors/` (a marker register naming immutable content blobs, the stored-scripts shape); nothing lists. Validation as the plugin does: name, `indices` (at least one), `time_field`, 1 to 5 features each with one metric aggregation (`max_anomaly_features`), `detection_interval` of at least 1 minute, `window_delay`, `shingle_size` 1 to 60, at most 2 `category_field`s, a `result_index` that starts `opensearch-ad-plugin-result-`, a `filter_query` the reader parses. Bounds: a detector 1 MiB, 1,000 detectors a tenant (the plugin's `max_single_entity_anomaly_detectors`; the 10 high-cardinality bound is enforced when the runner starts a detector, since counting them would read every detector). A feature whose aggregation or `filter_query` the reader cannot run is refused 400 at put, not at run (the double-field gap recorded in plugin-proxy VERIFIED is a reader gap and a precondition, not part of this port).
3. **Preview.** `POST /detectors/_preview` and `/detectors/{id}/_preview`: one bounded search through the reader (a `date_histogram` over `time_field` of the detector's interval with the feature aggregations, at most `serverless.ad.max_preview_points`, default 1,000 windows), a model trained and scored in memory, the plugin's `anomaly_result` answered, nothing stored and no checkpoint. A high-cardinality detector previews at most 5 entities, as the plugin does.
4. **Start, stop and the runner.**
   - `POST /detectors/{id}/_start` and `_stop` flip the detector's job record (`enabled`, `enabled_time`, `disabled_time`, `schedule`) in its set and the tenant's entry in the scheduler's registry. A stopped detector costs nothing. A body with `start_time` and `end_time` starts a **historical analysis** (slice 6).
   - The schedule, registry, discovery, claim and skew rules are those of alerting slice 5, reused by extracting that slice's scheduler into one shared module (`oss-meta::schedule`); AD's namespaces are `ad/registry/<0..255>` and `ad/runs/<detector>`. The extraction is a refactor PR with no behaviour change, done by the AD thread after alerting slice 5 merges; alerting's own tests must pass unchanged over the shared module (AC-17). **The registry's 256 shard markers are the same set as alerting's**, with a per-namespace entry for each tenant, so the standing read is one 256-marker pass whatever is enabled; AD adds its tenants' marker reads only while `serverless.ad.enabled` is on, and with it off adds 0 requests (AC-9). Same rules: no poll per detector or index, at most once per slot, a window is the slot's boundaries (`data_end_time` = slot end minus `window_delay`), missed slots are never backfilled, a run waits for the slot's end plus `max_skew` plus `visibility_lag`.
   - **Differences from alerting**, because a detector holds state: the owner is the **one** live node with the highest placement hash for the detector id (not the top 2), so a model stays on one node and a checkpoint is read only after an ownership change; during a membership disagreement two nodes may try and the compare-and-swap decides, the loser paying one failed PUT. The claim marker holds `last_claimed_slot` and the claimer's node id. **A node may use the model in its memory only if the marker names it as the previous claimer and its model's `last_fed_slot` is the slot before; otherwise it drops the model and reloads the checkpoint** (1 + chunks GETs) before running, and the loser of a claim marks its model stale. A flap therefore costs a checkpoint read, never two lineages feeding one detector (AC-17). A slot that nobody runs reaches the model as a **missing window**. The checkpoint stores the model's `last_fed_slot`; after a reload the gap from that slot to the current one drives imputation (not the claim marker's `last_claimed_slot`: slots the old owner fed after its checkpoint are lost with it and imputed), up to `serverless.ad.max_gap` (default 2 slots), past which the shingle restarts.
   - A run is **one search** for the slot: `time_field` in the window, the `filter_query`, the enabled features' aggregations; a high-cardinality detector adds a composite aggregation on its `category_field`s paged at `max_entities_per_query` (default 1,000) until the window is exhausted or `max_entities` (default 1,000 hot models a detector) is reached. The search's cost is the reader's, charged to the source indices' tenant. Each entity's feature vector is fed to its model; the result documents (below) are the run's output.
   - At most `serverless.ad.max_concurrent_runs` (default 4) runs a node; due runs are claimed when a worker frees up and dropped, counted, once the next slot's end has passed unclaimed.
5. **Model lifecycle and results.**
   - *Cold start:* a detector with no checkpoint trains on one bounded search of history before its first run: the `train_points` (default 512 windows, the plugin trains on up to a few hundred) windows before the first slot, as a `date_histogram`. Too few data points leaves the detector `INIT` (as the plugin) and it scores nothing until `shingle_size + min_train_samples` (128) points have arrived. A source index with no data in range is not an error.
   - *Checkpoint:* each owner writes its detector's models to the detector's checkpoint set every `serverless.ad.checkpoint_interval` (default 600 s, measured in runs, not by a timer: the run that finds the interval passed writes it) as immutable chunk blobs of at most 8 MiB and one marker compare-and-swap; the shingle state, the thresholder and `last_fed_slot` are inside. **The marker's compare-and-swap is conditioned on the etag the writer read when it loaded the model**: a paused or partitioned old owner's write fails against a newer owner's checkpoint, and a node whose checkpoint write fails drops its model and does not retry (AC-10). The total checkpoint is at most `serverless.ad.max_checkpoint_bytes` (default 64 MiB a detector, 8 chunks): a high-cardinality detector keeps as many hot entities as fit, and entities past it are skipped and counted like those past the cache. A graceful node shutdown writes the checkpoint of each dirty detector it owns (bounded by the shutdown time, then dropped and counted); a delete first CASes the job record to a tombstone, which a checkpoint write checks, then deletes the blobs (AC-18). A node that wins a slot with no model in memory reads the marker and its chunks (1 + chunks GETs, one round, then fan-out), then feeds the gap as missing windows. A stop writes a final checkpoint; a delete deletes the set's blobs through the batch delete.
   - *Memory:* each model is reserved at construction (the formula in the Risks, at most `serverless.ad.max_model_bytes`, default 2 MiB, all of it held up front) from a pool of `serverless.ad.model_cache_bytes` (default 256 MiB, taken from the open-indexes pool); past the pool a new entity is **skipped and counted** (`entities_skipped`), as the plugin skips entities past its per-node memory, never failed with a 500 and never evicting a model that has a checkpoint pending.
   - *Results:* each run writes one document per entity (one for a single-entity detector) to the tenant's result index (`opensearch-ad-plugin-result-<tenant>` by default, or the detector's `result_index`), through the node's ordinary write path (the per-node write log, [principles](../../principles.md#write-path)): the run adds **no PUT of its own** beyond the log's, and a node's writes in one flush share one segment. A document has the plugin's fields (`detector_id`, `data_start_time`, `data_end_time`, `execution_start_time`, `execution_end_time`, `anomaly_score`, `anomaly_grade`, `confidence`, `feature_data`, `entity`, `model_id`, `schema_version`, and `error` for a failed run). Retention is the tenant's lifecycle policy on the result index; this port deletes nothing on a timer.
6. **Profile, results routes, tasks and historical analysis.** `GET /detectors/{id}/_profile[/{type}]` (`state` from the job and model: `DISABLED`, `INIT`, `RUNNING`, `INIT_FAILURE`, `UNEXPECTED_FAILURE`; `init_progress`; `models`; `total_entities`; `error`), `GET /detectors/{id}/results`, `POST|GET /detectors/results/_search[/{result_index}]` (a search of the result index through the reader, nothing special), `POST /detectors/{id}/results/_topAnomalies`, `POST /detectors/tasks/_search`. A **historical analysis** is a task in node memory ([ADR 0072](../../adr/0072-tasks-are-node-local-memory-with-no-blob-requests.md)) that runs the model over `start_time` to `end_time` in bounded windows (`serverless.ad.max_historical_windows` per search, default 1,000, paged until the range is done), writing result documents tagged with its `task_id`; at most `serverless.ad.max_historical_tasks` (default 2) a node, a cap that gives a 429; a task is lost with its node and recorded as `FAILED`/`STOPPED` when read from another (as ADR 0072 does), never resumed by a timer.

Bounds a corrupt or hostile input meets: a window value at most 1e18 in magnitude, `max_gap` at most 1,024, every length of a checkpoint from the validated parameters, and a checkpoint is verified structurally (reachable and free nodes, per-leaf mass against the sampled points) before a model is returned.

Not here: the **forecasting** plugin routes of the same repository (`/_plugins/_forecast`, a separate plugin); **ML Commons' `FIT_RCF`/`BATCH_RCF`/`ANOMALY_LOCALIZATION`** (ML Commons thread); the plugin's `.opendistro-anomaly-detectors`, `.opendistro-anomaly-detector-jobs` and `.opendistro-anomaly-results` system indices (no such index exists; `GET` of one is 404); Alerting-style notification of an anomaly (the plugin does it through an alerting monitor on the result index, which needs alerting itself); flattened multi-index result aliases beyond the one result index of a tenant; Java-shell interop (the Rust store and the plugin's `.opendistro-*` indices are separate); rules and `rules`/`suppression` options (refused 400 with a message saying so, not silently ignored); the `frequency` option (read, stored and ignored, as it changes only when results appear).

## Acceptance criteria

- AC-1: the model is deterministic and bounded: the same seed and the same input give bit-equal scores, grades and checkpoint bytes; a checkpoint restored scores the next 1,000 points bit-equal to the model that was not stopped; `number_of_trees`, `sample_size` and `shingle_size` out of range are refused at construction, and the bytes a model reserves are at least the bytes it holds, measured over a grid of dimensions (up to 300), trees and sample sizes (the formula includes the thresholder, shingle buffer and imputation state); scoring a point allocates nothing (counting allocator, 100,000 points; seen red with an allocation planted in the loop).
- AC-2: **detection quality against fixtures.** On three committed synthetic series (a steady seasonal one with 10 injected spikes, one with a level shift, one with a missing-window stretch) the model flags (`anomaly_grade > 0`) each injected spike within 2 windows of it, and flags at most 1% of the steady windows, with a fixed seed; a series with a level shift flags the shift and returns to grade 0 within `sample_size` windows of it. Each fixture records what the stock plugin did on the same series (AC-15); **at least 80% of the windows the stock plugin flags are flagged here, and at least 80% of those flagged here are flagged by it**, computed and written to VERIFIED.md. These floors are set before the model is built and are not tuned to pass.
- AC-3: shingling and imputation: with `shingle_size` 4 a point is the last 4 feature vectors in order; a missing window is imputed by each of `ZERO`, `FIXED_VALUES` and `PREVIOUS` as the plugin documents; a gap past `max_gap` restarts the shingle; hand-worked small cases, seen red with a stub.
- AC-4: a detector is created, read, replaced, searched, counted and deleted through the routes in the plugin's published shapes ([shapes.md](shapes.md)); a stale `if_seq_no` is 409, a missing detector 404, an invalid one 400 `illegal_argument_exception` with the plugin's reason (names the field); (`job=true`, `task=true`, the name match and the running-detector refusal arrive with the runner.)
- AC-5: validation as the plugin does (every bound of slice 2), each a 400 at put naming the field: 0 and 6 features, a feature with two aggregations, an interval of 30 seconds, `shingle_size` 61, three `category_field`s, a `result_index` without the prefix, a `filter_query` that does not parse, an aggregation the reader cannot run; the 1,001st detector gives 429 and an over-bound body 400; `rules` is 400 with a message saying it is unsupported.
- AC-6: a create is 1 GET and 2 PUTs, a read 2 GETs, a replace 3 GETs and 2 PUTs (it reads the current detector first), a delete 1 GET and 1 PUT, a count 1 GET, no LIST; a search is 1 GET for the names and 2 for each detector of its page of at most 100, and a refused query reads nothing; a row in [request-budgets](../../request-budgets.md) for each, pinned by the count test.
- AC-7: `_preview` of a detector over a range returns the plugin's `anomaly_result` with a grade for each window of the range, issues exactly one reader search and **no** blob PUT (request meter over the emulator), and the same result a model fed the same windows directly gives; a range wider than `max_preview_points` windows is 400; a source index with no data in range answers an empty `anomaly_result`, not an error.
- AC-8: with a mocked clock, a detector on a 1-minute interval runs once a slot across three nodes (only the one owner by placement hash tries, and one CAS wins a slot), a slot is never run twice, an owner that dies after its claim loses that slot and the next slot runs on the new owner, the missed slot reaches the new owner's model as an imputed window, and with one node's clock 4 s fast every run's `data_end_time` is the slot's boundary minus `window_delay`.
- AC-9: **no poll per detector or index**: with N started detectors and the clock advanced one hour with none due, the request meter reads exactly the registry reads (256 markers and the placed tenants' markers once per `refresh_ttl`) and nothing else, whatever N; at a slot the requests are those plus exactly the claim PUT, the detector's one search, the log's append for the result documents, and (once a `checkpoint_interval`) the checkpoint's chunk PUTs and one marker PUT; a **stopped** detector adds nothing; a cluster with no detectors reads the 256 markers and nothing more.
- AC-10: a node that takes over a detector reads its checkpoint marker and chunks (1 + chunks GETs, in one round after the marker), is `INIT` for no longer than the checkpoint's own state says, and scores the next window equal to the model that wrote the checkpoint would have, given the same input and the windows after the checkpoint's `last_fed_slot` imputed (including slots the dead owner had scored after its last checkpoint); **a stale writer's checkpoint marker CAS fails and the newer checkpoint stays**, and the stale node drops its model; a corrupt or future-version checkpoint is ignored, the detector cold-starts, and the profile reports it (no panic, no 500).
- AC-17: the scheduler extraction changes nothing: alerting's AC-7 and AC-8 tests pass unchanged over `oss-meta::schedule`, and AD's own runner tests run over the same module; under a membership that flips the owner of a detector every few slots over 50 slots, every scored window is fed to exactly one model lineage, checkpoint reads number at most the ownership changes, and no slot runs twice.
- AC-18: a graceful shutdown of the owner writes the dirty detectors' checkpoints (a takeover then reads them); a delete racing a checkpoint write leaves no marker (the checkpoint CAS fails against the tombstone, asserted with a deterministic hook).
- AC-11: a high-cardinality detector runs one composite-aggregation search paged to at most `max_entities_per_query` an entity batch, keeps one model for each entity (each entity's results carry `entity: [{name, value}]`), and past `max_entities` or the cache bytes **skips** new entities and counts `entities_skipped` in `_stats`, never failing the run; the models held never exceed the pool (a held model is reserved first).
- AC-12: each run writes its results to the result index through the node's write path with no PUT of its own (request meter: the log's append and nothing else), the documents have every field of slice 5 and are found by `POST /detectors/results/_search` with the `anomaly_grade` range queries the Dashboards plugin issues; a failed run (the search errors, the index is gone) is one result document with `error`, the detector's profile shows it, the slot is not retried, and the next slot runs.
- AC-13: historical analysis: a task over a fixed range writes the same grades as the same range through `_preview` for a fixed seed, in windows of at most `max_historical_windows` a search; a third concurrent task is 429; a task read from a node that did not run it is `FAILED`/`STOPPED`, not 404; `_stop` ends it before the next window.
- AC-14: memory is reserved before a detector document, a model, a checkpoint chunk and a run's search result are held (4 x the document bytes from the open-indexes pool for a detector); past the pool a run is skipped and counted, not failed with a 500, and a `_preview` is 429.
- AC-15: **compatibility against the stock plugin.** The live run of the stock plugin on the Java shell (`crates/node/tests/mixed_fleet/live_plugins.rs`, the harness plugin-proxy VERIFIED describes) records, for each route of slices 2, 3 and 6, one request and the stock response into `fixtures/anomaly-detection/`, and the same series of the AC-2 fixtures run as a stock detector gives the flagged windows the fixture records. A shape test compares the Rust answer to each recorded response field by field (ids, times and scores excepted, scores compared by AC-2); a difference is written in the spec's Differences list, not silently kept. Until the recording exists the shapes in `shapes.md` are provisional and the default stays off.
- AC-16: with the setting off every route answers as today (400 `no handler found`, or the proxy when an upstream is set), no run starts, no AD tenant marker is read (the shared 256 shard markers are read only as alerting reads them), and the existing plugin-proxy tests pass unchanged; the new tests run with it on, and both run in CI.

## End state

Nothing of the plugin relies on Java. Every route of the stock plugin's anomaly detection API is served natively, with no proxy fallback; the AD prefixes leave the plugin-proxy list in the slice that completes the routes, not at the default flip. Java stays out of the runtime path and is never a fallback, but tests may use it: compatibility against the stock plugin (the recording and live run of AC-15) and performance and memory comparison against the Java build are kept where useful, alongside tests that hold every AC above on the Rust node alone. A route the port will not serve is refused with a reason that names it, never forwarded.

## S3 request budget

Management: the stored-scripts shape, a row in [request-budgets](../../request-budgets.md) for each route when it lands. Preview: the reader's one search, no blob PUT. Run: 1 conditional-create PUT to claim the slot, the detector's one search (the reader's cost, charged to the source indices), the result documents through the write log (the log's cost, one append for a node's flush, whatever the detector count), and once a `checkpoint_interval` the checkpoint's chunk PUTs and one marker PUT: at a 1-minute interval and the 10-minute default, 1 + (chunks + 1) / 10 PUTs a run: 1.2 at one chunk, and for a high-cardinality detector at its 64 MiB checkpoint cap (8 chunks) 1.9 a run. Checkpoint bytes are at most 64 MiB a detector every 10 minutes, which scales with bytes held, not with time alone. A run with no data in its window still claims and still searches (nothing else to learn from), writes no result document for an empty single-entity window, and checkpoints on its interval. Takeover: 1 marker GET and its chunks, once, not a standing cost. Load: the scheduler's standing reads of alerting slice 5, `256 x nodes + 2 x tenants-with-detectors` marker reads a `refresh_ttl`, shared with alerting's (the 256 shard markers are shared with alerting, so enabling AD adds no marker reads of its own beyond its placed tenants'). Depth: the claim, then the search's rounds; a takeover adds one round of marker then fan-out of chunks. LIST: none.

The claim PUT and the search per run are a bill that scales with detectors x runs, which is the feature's nature: a started detector is a standing job, a stopped or deleted one is free. Worst case per tenant: 1,000 single-entity detectors at the 1-minute floor is 1.44 million claims, searches and result writes a day, plus about 0.29 million checkpoint PUTs (1,000 x 144 x 2), and 10 high-cardinality detectors add about 13,000 more (10 x 144 x 9), plus one cold-start history search a start. The guards are the floor, the per-tenant counts of slice 2, a fleet cap `serverless.ad.max_total_detectors` (default 1,000,000, bounded by the registry's shard limit), `max_concurrent_runs`, and the per-tenant request meter; the measurement for the default decides whether they are tight enough. AC-9 asserts nothing is paid between slots beyond the registry reads.

## Switch

`serverless.ad.enabled` (`OSS_AD`), default **off**; with it off the anomaly-detection prefixes go to a plugin upstream when one is configured, and the proxy's prefixes for AD are removed when the default turns on, not before. It flips on only when VERIFIED.md records: the stock recording of AC-15, the request counts of AC-6, AC-8, AC-9 and AC-12, the agreement of AC-2 with the stock plugin's flagged windows, a run's search latency within 1.2x of the same search from a client, the checkpoint PUT count a day at the worst case above, and the memory of 1,000 held detectors (4 x their bytes, AC-14) and 300 held models. `min_interval` (60 s, the plugin's floor), `max_gap`, `checkpoint_interval`, `max_entities`, `max_entities_per_query`, `max_model_bytes`, `model_cache_bytes`, `max_concurrent_runs`, `max_preview_points`, `max_historical_windows`, `max_historical_tasks`, `max_total_detectors` and `refresh_ttl` are limits with defaults, not switches. The model's own parameters (`number_of_trees`, `sample_size`, time decay) are the plugin's defaults and are not exposed per detector (the plugin does not expose them either); a settings override per cluster is a later change.

## Risks

- **The stock source is not in this sandbox** (`opensearch-project/anomaly-detection` is outside the repositories the session can read), so route shapes come from the plugin's published documentation and are provisional until AC-15's recording exists; every AC naming a shape is `provisional` in VERIFIED.md until then.
- **Scores are not comparable bit for bit**: the stock library samples randomly and exposes no seed, so compatibility is by flagged windows and shape (AC-2, AC-15), not by score. The thresholder's constants are the likeliest place to differ; they are in one module, tested against the fixtures, and the agreement is measured, not assumed.
- **Model memory.** A model reserves the capacity of every array the model owns, summed by `Params::reserved_bytes`: about `trees x sample_size x 88 B` for the trees' arenas, samples and slot maps, plus `4 x sample_size x dims x 4 B` for the ring of points (dims = features x shingle, at most 300 in the plugin, 512 in the crate), plus a fixed 16 KiB for the thresholder, shingle buffer and imputation state; no bounding box is stored (a worker's `Workspace` holds the boxes it computes, shared by every model it runs): at 30 trees, 256 samples, 5 features, shingle 8 that is 0.87 MiB and at the worst plugin dims (5 features, shingle 60) 1.89 MiB, under the 2 MiB default (measured by `Params::reserved_bytes`, provisional: the sum of capacities, not a process measurement); a worker's workspace is 0.16 MiB and 1.17 MiB at the worst. The 256 MiB cache therefore holds a few hundred models; a high-cardinality detector over a million entities cannot be served and skips entities, as the plugin does at its own limit. The skip count is a metric.
- **A scheduler without a leader** depends on the claim create being atomic in every backend (alerting has the same dependency, held by the conformance suite). Clock skew costs a late or skipped run, never a double run; an ownership flap costs one failed PUT and one checkpoint read.
- **A takeover loses up to one `checkpoint_interval` of model updates**: the new owner's model is older than the old owner's and sees the gap as missing windows. Accepted (the plugin loses the same on a node crash); the interval is a setting and the cost of shortening it is counted in AC-9.
- **Determinism is per build**: scores and sampling keys use the platform's `ln`, `log2` and `sqrt`, so the same seed and input give the same output and checkpoint bytes on one binary and platform, and nodes of one build agree; a takeover by a node of a different build still restores the checkpoint and continues correctly, but its future sampling may differ from the old owner's in the last bits. The cost of one `feed` is O(nodes x dims) a tree for each of its box passes, bounded by the parameters (up to about 4,000 nodes x 512 dims x 100 trees at the maximum) and not measured in this slice.
- Results written through the write log are visible after the log's refresh; a result query for the latest window inside the visibility lag can miss it (`visibility_lag` bounds the slot wait, not the result's visibility).
- Two scheduler extractions racing (alerting slice 5 and AD slice 4) would conflict on files. The mitigation is the order rule in slice 4 and the coordinator's notice, not parallel work on `oss-meta::schedule`.
