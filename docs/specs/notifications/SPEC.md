# Notifications, native: configs, channels, features, send

## Serves

R15.4's Notifications plugin, under [ADR 0081](../../adr/0081-notifications-is-ported-natively.md). The owner's decision (2026-11-28): the stock plugins are ported to Rust, no Java in the runtime path (no proxy, no fallback); Java is a test oracle only (recorded stock answers as fixtures) and a perf and memory comparison. Alerting ([ADR 0075](../../adr/0075-alerting-is-ported-natively.md)) and ISM ([ADR 0077](../../adr/0077-index-state-management-is-ported-natively.md), whose `notification` action is refused at policy put today) both send through it. A client of `opensearch-project/notifications` must work unchanged against a Rust node.

## Change

Five slices, one PR each, behind the setting below. Nothing in lucene-rust applies (it holds no notification code). The building blocks are here: [document sets](../doc-sets/SPEC.md), the REST router, the `ureq` crate (the sender builds its own client in `notifications_route`; it shares nothing with the proxy).

1. **Store, config routes, `features`, `channels`.** `DocKind::NotificationConfigs`: one document a channel config under `notifications/configs/` of the deployment's base (the tenant's base, as ISM and LTR keep theirs; two bases never see each other's configs), a marker register naming immutable content blobs, the stored-scripts shape, and `DocKind::NotificationCatalogue`: one document, `catalogue`, under `notifications/catalogue/`, holding the non-secret summary of every config (`config_id`, `name`, `description`, `config_type`, `is_enabled`, created and updated times, and the config's `seq`, a counter kept in the config as ISM keeps its `seq_no`), at most 1,000 entries and 2 MiB (`max_doc_bytes` gains an arm; a test fills 1,000 maximal entries). The catalogue is written by `DocSet::update(name, f)`, a new primitive that **rebuilds the document from a fresh read on every swap attempt** (up to 10 attempts, then 409), because `put`'s retry of the same bytes would lose a concurrent writer's entry. Routes on `/_plugins/_notifications`: `POST /configs` (body `{"config_id"?, "config": {...}}`), `GET /configs/{id}` and `GET /configs` (`config_id`, `config_id_list`, `from_index`, `max_items`, `sort_field`, `sort_order`, `config_type`, `is_enabled`, `name`, `description`, `text_query`), `PUT /configs/{id}`, `DELETE /configs/{id}` and `DELETE /configs` (`config_id`, `config_id_list`), `GET /features`, `GET /channels`. A config is validated at put per type (below), including `header_params` (token names, no CR, LF or NUL, never `Host`, `Content-Length`, `Transfer-Encoding` or `Connection`); one outside the supported types or with a missing required field is 400 naming it, never a failure at send. Bounds: a config 64 KiB, 1,000 configs a tenant, a page of at most 100.
2. **Send.** An in-process `Notifier` (`send(config_id, message)` for alerting and ISM, and `POST /feature/test/{config_id}` for the plugin's test route) delivering to the HTTP-shaped channels: `webhook` (method POST, PUT or PATCH, headers from `header_params`), `slack`, `chime`, `microsoft_teams`. The body is bounded at 1 MiB, the time at the call's deadline (5 s connect, 30 s total by default), TLS verified, **no redirect**, every resolved A and AAAA address checked and refused when it is private, loopback, link-local, unspecified, carrier-grade NAT, multicast, unique-local, IPv4-mapped or NAT64 of any of those (a test row each, `169.254.169.254` among them), then connected to by the address checked with the original name kept for SNI, certificate check and `Host` (no DNS rebinding; the resolver is injectable so a test can answer differently the second time), a URL with userinfo or a non-canonical IP literal refused, ports 80, 443 and a configured list only, and a host deny list as the stock `host_deny_list`. `allow_private_hosts`, the deny list, the account allow-list and the port list are **node operator settings read from the environment or a file at start, never cluster settings**, so no tenant administrator can turn the guard off. The same guard fronts SMTP, SNS and SES; an operator-declared account's own host is exempt from the private-address refusal only (it is still resolved, checked for the other rules and pinned), so an internal SMTP relay needs no global `allow_private_hosts`, and a test row shows a webhook to the same private address still refused. `DocSet::update` reuses the marker it read for its swap, which is why it is 2 GETs and 2 PUTs. The catalogue's `seq` is what a client's `if_seq_no`-style check would read; nothing else does. A response is the plugin's `status_list` entry (`delivery_status.status_code`, `status_text`); a delivery failure is a status entry, not a 5xx, as in the stock plugin. No retry here: the caller (alerting's throttle and retry, ISM's step retry) owns retry. A per-node cache of configs keyed by `config_id` (it stores the content id), freshness a TTL checked lazily by a send (the LTR shape, default 30 s): inside the TTL a send costs 0 requests, past it 1 GET of the config's marker and 1 more only when its content id changed, with one flight a config so concurrent sends past the TTL share it, never a timer. A deleted or disabled channel is still sent to for up to the TTL; that bound is also a security bound and is stated to the operator.
3. **Email.** `smtp_account`, `email_group`, `email`: an SMTP client over rustls (`ssl`, `start_tls`, `none`). **Credentials are bound to an operator-declared account, never to a tenant-chosen host**: the node's account file (`OSS_NOTIFICATIONS_ACCOUNTS`) lists account ids with host, port and credential; a tenant's `smtp_account` names an id from it (a config naming an unknown id is 400) and never sets a host or port of its own. The stock plugin keeps credentials in the keystore, message size bound `email.size_limit` (10 MiB), recipients from the group ids resolved at send, at most 100 a message.
4. **SNS and SES.** `sns` and `ses_account`: SigV4-signed requests to the service's HTTPS endpoint with the credentials and the `role_arn`s the operator's account file allows (a tenant's `role_arn` outside the allow-list is 400, so the node's credentials cannot be used as a confused deputy), `region` matching `^[a-z]{2}(-[a-z]+)+-[0-9]$` so it cannot inject a host; these are the only non-blob AWS calls and are not S3 requests (never counted against the S3 meter, counted by their own `notifications_sends` counter).
5. **Wiring.** Alerting resolves an action's `destination_id` through `Notifier` instead of its own channel documents, and ISM's `notification` action is accepted at policy put and sends through it. Both files belong to those threads, so this slice is agreed with them first and is a change they merge or approve.

Not here: `GET /_plugins/_notifications/stats` beyond the node-local counters, the plugin's `.opensearch-notifications-config` system index (no index exists; a read of it is a 404), the stock plugin's `access` (backend roles) filtering beyond the security layer's action table, Java-shell interop, Opsgenie, PagerDuty and ServiceNow channels (not in the plugin).

### Config shapes (provisional until a stock recording exists)

`config_type` is one of `slack`, `chime`, `microsoft_teams`, `webhook`, `email`, `sns`, `ses_account`, `smtp_account`, `email_group`. The config object carries `name` (1 to 256 chars), `description` (at most 1,024), `config_type`, `is_enabled` (default true) and one block named for the type: `slack.url`, `chime.url`, `microsoft_teams.url`, `webhook.url` with optional `header_params` (object of strings) and `method`; `email` with `email_account_id`, `recipient_list` (`[{"recipient": "..."}]`) and `email_group_id_list`; `sns` with `topic_arn` and optional `role_arn`; `ses_account` with `region`, `from_address` and optional `role_arn`; `smtp_account` with `account_id` (an id of the operator's account file, which holds host, port, method and credential) and `from_address`; `email_group` with `recipient_list`. URLs are `http` or `https`. An unknown key anywhere is 400 `illegal_argument_exception`. The stored object adds `config_id`, `created_time_ms` and `last_updated_time_ms`.

## Acceptance criteria

- AC-1: a config is created, read, replaced and deleted through the routes in the plugin's published shapes (`{"config_id"}` on create and replace, `{"start_index", "total_hits", "total_hit_relation": "eq", "config_list": [{"config_id", "last_updated_time_ms", "created_time_ms", "config": {...}}]}` on read, `{"delete_response_list": {"<id>": "OK"}}` on delete); a missing config is 404 with the plugin's message, a second create of an explicit `config_id` is 409, a config of an unknown type, a missing type block, a non-http URL, an unknown key or a name over 256 chars is 400 `illegal_argument_exception` naming it.
- AC-2: `GET /features` answers `allowed_config_type_list` (all nine types by default, narrowed by `serverless.notifications.allowed_config_types`, and a config of a type outside it is 400 at put) and `plugin_features`; `GET /channels` answers `{"start_index", "total_hits", "total_hit_relation", "channel_list": [{"config_id", "name", "description", "config_type", "is_enabled"}]}` and lists only channel types (not `smtp_account`, `ses_account`, `email_group`).
- AC-3: **requests do not scale with records.** Every route's count is a constant independent of the number of configs, asserted by running the same call against 5 and against 1,000 configs and reading the same request meter; none lists. A create is the config set's `put_counted` (1 GET, 2 PUTs) then the catalogue's `update` (2 GETs, 2 PUTs), a replace adds the existing config's read and 1 DELETE for the replaced content blob of each set, a delete drops the catalogue entry first (2 GETs, 2 PUTs, 1 DELETE) and then the config (1 GET, 1 PUT, 1 DELETE), a read of one config 2 GETs, `channels` and a filtered `configs` list 3 GETs (the config marker and catalogue marker in one round, then the catalogue content), plus for `configs` 1 GET a config of the page, so at most 100 more in one round: bounded by the page, not by the configs. The exact figures, DELETEs included, are rows in [request-budgets](../../request-budgets.md) that `check-budgets.py` pins at the slice, and a test fails below as well as above.
- AC-4: the catalogue heals without a write on a read path being a stampede. A create or replace writes the config first and then the catalogue entry; a delete drops the catalogue entry first, so a crash between leaves a missing entry (never a dangling one). A list compares the config marker's names with the catalogue's ids: a name with no entry costs 1 GET of that config and is added, an entry with no name is dropped; the repair is one `update` (its swap loses quietly when another node repaired first, and the list answers from what it computed), and a list that finds nothing to repair writes nothing. A crash between the two writes of a replace leaves the old summary until the client's retry, which it must make because it was never answered; the test plants each gap. N concurrent creators (N = 16, then at 1,000 configs) all succeed or answer 409 `version_conflict_engine_exception` after 10 attempts, never lose an entry (asserted by the catalogue's content after the run), and never answer 500.
- AC-5: `from_index`, `max_items` (clamped to 100), `sort_field` (`name`, `config_type`, `last_updated_time_ms`, `created_time_ms`), `sort_order`, `config_type` (repeatable), `is_enabled`, `name` (exact), `description` (exact) and `text_query` (a case-insensitive substring of name or description) select and order as a table of cases pins now; `total_hits` counts matches, not the page. Equality with the stock plugin is AC-12.
- AC-6: a webhook, Slack, Chime or Teams send posts the rendered body to the config's URL exactly once, with its `header_params` and method, to a local test server; the answer is the plugin's `status_list` entry with the delivery's status; a refused connection, a timeout, a non-2xx and a redirect each is a failed `delivery_status` (no 5xx from the node, no follow of the redirect, no second call); a disabled config is not sent and says so.
- AC-7: the egress guard of the Change refuses each listed address class, an IPv6 or mapped form of each, a name with any bad record among good ones, userinfo, a non-canonical literal (decimal, octal, hex), a port outside the list, a body over 1 MiB (before any connection), and reads at most 64 KiB of a response; a name that resolves differently the second time is not followed. A failed delivery's `status_text` is one of a fixed set (`refused`, `timeout`, `status <code>`, `blocked`, `too large`) and never carries the target address, the response body or the resolver's words, so the answer is no oracle for the internal network (a test asserts it with a body that contains a marker string). The same rows run against SMTP, SNS and SES targets.
- AC-8: a send inside the cache TTL (30 s) makes no store request; the first past it makes 1 GET (the marker) and a second only when the content id changed; 64 concurrent sends past the TTL make one flight; a replace, disable or delete is seen by a send within the TTL and never earlier than the replace; over an hour of N sends a second with no change the store requests equal (configs used x nodes x hour / TTL) whatever N, asserted over many sends (**no poll, no timer**); an idle node makes none.
- AC-9: memory is reserved before a config, the catalogue (and its rebuilt copy, so the peak is counted twice) or a delivery body is held (4 x the bytes from the open-indexes pool); a test fails when the reservation is removed, and a send past the pool is a failed delivery counted as skipped, not a 500; deliveries run at most `serverless.notifications.max_concurrent_sends` (default 32) at once and a send past it waits in a bounded queue of 256, then fails as `rejected`.
- AC-10: email: a message to a group is one SMTP session to the operator-declared account's host, recipients resolved from the group at send, a config that names a host or port of its own is 400, a message over `email.size_limit` refused before connecting; SNS and SES requests carry a valid SigV4 signature (the signer's published test vectors), a `role_arn` or `region` outside the rules is 400, and none is counted as an S3 request. No credential appears in a stored or shown body, the catalogue blob, a log line or an error (a test plants one and searches all four); the catalogue blob carries no URL and no header.
- AC-11: with `serverless.notifications.enabled` off every notifications route answers as an unknown route (400 `no handler found`), no cache is built and no send is made; the existing tests pass unchanged; the new tests run with it on, and both run in CI.
- AC-12: shapes of AC-1, AC-2 and the `feature/test` answer equal recordings of the stock plugin run (the Java shell with the released Notifications zip) for one request of each route; until the recording exists they are `provisional` in VERIFIED.md.
- AC-13: Java is never in the runtime path: a tree check `check-notifications-no-proxy` fails when `notifications_route` references `plugin_proxy` or `OSS_PLUGIN_UPSTREAMS`; it has a planted violation in `scripts/selftest-checks.py` and a row in [mechanical-gates](../../mechanical-gates.md), in slice 1.
- AC-14: two bases are two tenants: a config id of one is 404 for the other, a list of one never shows the other's, and a send under one cannot use the other's config.
- AC-15: a `GET` of a config shows its URL and `header_params` as the stock plugin does, so those routes are `notifications.read` actions in the action table ([ADR 0051](../../adr/0051-authorization-at-the-route-by-action-table.md)) and the completeness test covers them; `channels` returns neither.

## Test plan

Slice 1: `crates/format` unit tests for the two kinds' keys, `crates/node/tests/server/notifications_routes.rs` through HTTP with the request meter for AC-1 to AC-5 (red first by a stub that stores nothing; the heal test by a planted missing entry). Slice 2: the same file with an in-process HTTP target for AC-6 to AC-9 (red first by a stub that sends nothing; the rebinding test with a resolver that answers differently on the second call). Slice 3: an in-process SMTP server for AC-10. Slice 4: SigV4 vectors and a local signing-checking server. Slice 5: alerting's and ISM's own test files, with their owners.

## S3 request budget

Management: AC-3's rows. Send: 0 store requests inside the cache TTL, 1 GET (the marker) past it per config, a second only when the content id changed; none per message. SNS, SES and SMTP are not object-store requests and carry their own counter. Idle makes none; there is no timer in this port. Load: bounded by configs used times nodes over the TTL, never by send rate or by the number of configs.

## Switch

`serverless.notifications.enabled` (`OSS_NOTIFICATIONS`), default off until slices 1 and 2 pass; limits (`max_configs`, `max_concurrent_sends`, `cache_ttl`, `allow_private_hosts`, `allowed_config_types`) are settings with defaults, not switches. With it off the routes are absent (there is no Java upstream to hand them to). It flips on when VERIFIED.md records the request counts of AC-3 and AC-8, the memory peak of AC-9 with 1,000 configs, the write latency of a create at 1,000 configs, the stock recording of AC-12 and a send end to end from an alerting action; the owner's rule applies: on by default if no downside is measured.

## Risks

- Reference behaviour is from the plugin's published documentation, not its source (the Notifications plugin documentation on opensearch.org for 2.x; `opensearch-project/notifications` is outside this sandbox's repositories); shapes, the allowed-type list, `plugin_features` and the `status_list` text are provisional until a stock recording exists.
- Webhook URLs and Slack hooks are secrets stored in blobs and shown by `GET` as the plugin shows them; the node's own security layer ([ADR 0051](../../adr/0051-authorization-at-the-route-by-action-table.md)) is the only gate, and `feature/test` and `send` make the node an HTTP client for its callers, which is what the egress guard bounds (SSRF).
- A catalogue rewrite is up to 1,000 entries (up to about 1.3 MB with maximal descriptions) a config write, and writes to one register serialise; a tenant that writes configs in a loop pays bytes, not requests, and the pacing of [tenant-write-pacing](../tenant-write-pacing/SPEC.md) applies. The two swaps are not atomic; AC-4's heal is the answer, and a test plants the gap.
- A cache TTL is a staleness bound: a disabled channel may still be sent to for up to the TTL after the disable.
- Slice 5 changes the ISM spec's wording on `notification` (it refuses it today) and alerting's channel wording; the three specs are edited together then.
- Alerting and ISM files are owned by other threads; slice 5 waits for their agreement.
