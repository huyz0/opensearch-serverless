- AC-8 (emulator with the Java latency profile, `crates/node/tests/warm_evidence.rs`, `--ignored`, in-process nodes on one machine, provisional; the peer's own switch must be on for it to serve, and the test sets it). An index of 20,000 documents in 8 shards (7.1 MB of pages), five runs each, copy off against on:
  - Peer search p99 while the joiner starts: 48 to 50 ms off, 48 to 49 ms on, against 48 to 50 ms before the join. No movement.
  - Joiner: ready after 328 to 345 ms off, 1,490 to 1,605 ms on. Its first search takes 550 to 604 ms with 98 to 101 store reads off, and 43 ms (3 ms in one run) with 0 to 2 reads on. Store reads from start to the first answer: 106 to 113 off, 111 to 115 on, so the copy adds no request. The time from start to the first answer is longer on (about 1.55 s) than off (about 0.9 s).
  - One run of 30,000 documents in 32 shards (37 MB): ready after 364 ms off, 4,698 ms on; first search 1,804 ms with 557 reads off, 52 ms with 0 reads on; reads from start to first answer 565 off, 580 on.
  - Process CPU over the start (all nodes and the load thread share one process): 0.12 to 0.22 s off, 1.4 to 2.1 s on (11.8 s in the 32-shard run). It is not split by node, and the load loop makes more searches while the copy takes longer (1,738 against 100 in the 32-shard run), so it is an upper bound on the copy's CPU, not a measure of it.
  - A peer whose switch is off does not serve the action: the joiner got an unreachable outcome, nothing was copied, and it was ready after 228 to 250 ms. A Java peer that does not know the action should be the same case (an error answer); it was not run against a Java node.
  - NOT-RUN: a peer holding 1,000 shards (the rig's 30 s client timeout failed index creation at 100 and 1,000 shards, so the largest here is 32), the peer's bytes served and CPU on their own, an index large enough that the copy's rate limit dominates, a Java peer, and RustFS.
  - Decision: the default stays off. Readiness takes 1.2 to 4.3 s longer and the start-to-first-answer time is longer, which is a measured downside, and the CPU cost is unsplit. The first search after ready is 13 to 35 times faster with no extra request, so it stays a setting for fleets that value that. What would flip it: a split CPU number, a 1,000-shard peer, and a Java peer run.
- AC-7 (the 90% gate on booted nodes, `crates/node/tests/warm_ready_evidence.rs`, `--ignored`, emulator with the Java latency profile, 20,000 documents in 8 shards, the copy throttled to 524,288 B/s, one run per percent, provisional): the peer named 1,701,768 bytes. At `OSS_WARM_READY_PERCENT=90` the joiner answered 503 for 3.1 s (about 136 polls at 20 ms) and was let in with 1,701,768 of 1,701,768 bytes copied; at 50 it was let in after 1.1 to 1.2 s with 1,047,418 copied (61.5%); at 100 after 3.1 s with all copied. - AC-8 (a peer holding 1,000 shards, `crates/node/tests/warm_scale_evidence.rs`, `--ignored`, emulator with the Java latency profile, 4,000 documents in 1,000 shards (138.5 MB of pages in the peer's tier), two runs each, provisional). The joiner is a separate `oss-node` process, so its processor time is its own; the peer, the emulator and the paced load (one search every 100 ms or more, one at a time) share the test process, so the peer's time is split by thread name, and the on arm ran 92 s against the off arm's 60 s, so times are compared as cores. The peer's own switch is on in both arms:
  - Peer search p99, over the whole run after the join starts: off 204 and 212 ms (against 137 and 171 ms before), on 273 and 280 ms (against 204 and 196 ms before). The before figures differ by 20 to 40% between runs of the same arm, so a 1.2 to 1.5 times rise after the join starts is inside that spread: off 1.49 and 1.24 times, on 1.34 and 1.43 times. The slowest search: off 235 and 248 ms, on 338 and 322 ms. This includes the peer answering the hot-set listing of 1,000 shards.
  - Peer processor time: off 29.7 and 30.5 s over 60 s (0.495 and 0.508 cores), on 48.7 and 49.1 s over 92 s (0.530 and 0.534 cores): about 0.03 cores more, or 6%. By thread, transport-worker (the handlers) 0.20 to 0.21 cores off and 0.225 on; the rest unchanged. The paced load made 8.9 searches a second off and 7.9 on, so the on figure is not inflated by more searches.
  - Joiner: ready after 0.4 and 0.5 s off, 91.9 s in both runs on (the equal figure is not explained; the test polls ready every 0.3 s or so). First search 12,474 and 12,846 ms off, 316 and 248 ms on. Joiner processor time over the run plus its first search: 16.7 and 17.6 s off, 18.5 and 18.8 s on, so the copy costs the joiner about 1 s more than it spends reading cold. Pages held after the first search: 138,457,088 bytes in all four runs.
  - The joiner answered 503 for 92 s at this size, longer than the default `OSS_WARM_MAX_WAIT_SECONDS` of 60 (the test sets 600). Traced: `copy_from_peer` opened each shard the peer named one after another, each reading its commit from the store, so the time grew with the shard count (100 shards 8.9 s, 1,000 shards 91.9 s, about 90 ms a shard) and the byte rate was not the bound. Fixed: `open_shards` opens up to 16 at once (`warm_copy/tests.rs` `the_peers_shards_are_opened_side_by_side_and_each_once`, red before with 1 open at once and 2.9 s for 64 shards of 40 ms). After the fix, one run on the same rig: 100 shards ready after 0.9 s, 1,000 shards after 10.1 s, first search 289 ms, joiner processor time 16.8 s, peer processor time 30.2 s over 60 s (0.50 cores, the same as off). The peer's p99 over the 60 s was 411 ms (192 ms before, slowest 499 ms): the same copy now lands in 10 s and not 92 s, so the peer's searches during it are slower than before the fix (273 to 280 ms) while the copy runs, and no slower once it ends. One run, not the two the earlier arms have.
  - A Java peer, read from the `feature/serverlessshell` branch and not run live (it needs the Java shell built and a Rust and a Java node on one bucket). The Java shell names its actions `internal:serverless/cache/hot_set` and `internal:serverless/cache/blocks`, Rust `internal:serverless/warm/hot_set` and `internal:serverless/warm/pages`, and the payloads differ in kind: Java asks with `(joinerId, maxBytes, recentMillis)` and names block-cache keys as strings; Rust asks with `(joiner, max_shards, max_bytes)` and names pages by file key, page number and length for a page cache of fixed page size. The two caches are not the same structure, so the names stay distinct and a node of one kind does not answer the other's action. That case is an unknown action: the Rust server answers `ActionNotFoundTransportException` (`crates/transport/src/server/mod.rs`), and the Java side is the stock OpenSearch transport, which does the same; read, not run. The Rust joiner takes any error answer as an unreachable peer and is ready at once (`warm_copy/tests.rs` `a_peer_that_does_not_answer_or_names_another_page_size_gives_nothing`, and the switch-off peer above).
  - Decision: the default stays off, and nothing here changes it. At 1,000 shards the first search is 40 to 50 times faster and the peer's processor time shows no rise, but while the copy runs the peer's p99 doubles (192 to 411 ms in the one run after the 92 s fix) and the node is held out for 10 s. What would flip it is a decision on that p99, which is the measured downside, and a Java peer run.
