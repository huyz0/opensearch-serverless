- AC-8 (emulator with the Java latency profile, `crates/node/tests/warm_evidence.rs`, `--ignored`, in-process nodes on one machine, provisional; the peer's own switch must be on for it to serve, and the test sets it). An index of 20,000 documents in 8 shards (7.1 MB of pages), five runs each, copy off against on:
  - Peer search p99 while the joiner starts: 48 to 50 ms off, 48 to 49 ms on, against 48 to 50 ms before the join. No movement.
  - Joiner: ready after 328 to 345 ms off, 1,490 to 1,605 ms on. Its first search takes 550 to 604 ms with 98 to 101 store reads off, and 43 ms (3 ms in one run) with 0 to 2 reads on. Store reads from start to the first answer: 106 to 113 off, 111 to 115 on, so the copy adds no request. The time from start to the first answer is longer on (about 1.55 s) than off (about 0.9 s).
  - One run of 30,000 documents in 32 shards (37 MB): ready after 364 ms off, 4,698 ms on; first search 1,804 ms with 557 reads off, 52 ms with 0 reads on; reads from start to first answer 565 off, 580 on.
  - Process CPU over the start (all nodes and the load thread share one process): 0.12 to 0.22 s off, 1.4 to 2.1 s on (11.8 s in the 32-shard run). It is not split by node, and the load loop makes more searches while the copy takes longer (1,738 against 100 in the 32-shard run), so it is an upper bound on the copy's CPU, not a measure of it.
  - A peer whose switch is off does not serve the action: the joiner got an unreachable outcome, nothing was copied, and it was ready after 228 to 250 ms. A Java peer that does not know the action should be the same case (an error answer); it was not run against a Java node.
  - NOT-RUN: a peer holding 1,000 shards (the rig's 30 s client timeout failed index creation at 100 and 1,000 shards, so the largest here is 32), the peer's bytes served and CPU on their own, an index large enough that the copy's rate limit dominates, a Java peer, and RustFS.
  - Decision: the default stays off. Readiness takes 1.2 to 4.3 s longer and the start-to-first-answer time is longer, which is a measured downside, and the CPU cost is unsplit. The first search after ready is 13 to 35 times faster with no extra request, so it stays a setting for fleets that value that. What would flip it: a split CPU number, a 1,000-shard peer, and a Java peer run.
- AC-7 (the 90% gate on booted nodes, `crates/node/tests/warm_ready_evidence.rs`, `--ignored`, emulator with the Java latency profile, 20,000 documents in 8 shards, the copy throttled to 524,288 B/s, one run per percent, provisional): the peer named 1,701,768 bytes. At `OSS_WARM_READY_PERCENT=90` the joiner answered 503 for 3.1 s (about 136 polls at 20 ms) and was let in with 1,701,768 of 1,701,768 bytes copied; at 50 it was let in after 1.1 to 1.2 s with 1,047,418 copied (61.5%); at 100 after 3.1 s with all copied. The copied counts came from a temporary stderr line in `finish_when_warm`, removed before the commit; the test prints the ready times only. Never below the percent: 61.5% is above 50 and 100% above 90. The overshoot is the batch size: progress is looked at after each batch, so the gate opens at the first batch boundary at or after the percent, and with the throttle on a 1.7 MB list one batch carried the copy from under 90% to the end. 90% takes about as long as 100% here (3.1 s), because the last batch is the one that crosses.
